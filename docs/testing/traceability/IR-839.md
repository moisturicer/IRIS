# IR-839 — Extraction failure classes and retry policy

**Affected requirement labels:** FR-M3-01 (PDF text extraction). Its matrix status does not change.

[Back to the matrix](../TRACEABILITY.md)

**Implementation:** `apps/ai/extraction/ports.py` adds `DocumentRejected` and `classify()`: `ExtractorUnavailable` is the one transient failure; every other `ExtractionError`, `EmptyExtraction` and any unexpected exception is permanent. Adapters declare `timeout_seconds` and may report `ExtractedDocument.failed_pages`. `apps/documents/tasks.py` retries a transient failure after 60, 180 and 540 s and fails a permanent one at once; an unexpected exception is logged with its traceback, never stored. `ExtractionTask.apply_async` gives every dispatch and retry a time limit of the Extractor's timeout plus 60 s, with a soft limit 30 s earlier so an overrun records itself; an overrun is transient. The reader sees one of two messages on `metadata-suggestions` and the upload extraction serializer (`message`): "This PDF can't be read automatically. Enter the details manually." or, after the last retry, "Reading is temporarily unavailable. Try again later."; IR-831's retry action is unchanged. Failed pages go to `PdfExtraction.warnings` (migration `documents/0017`, additive), shown only in the read-only admin and cleared on reset. No page-limit work.

**Contract suite:** `contract.py` gains `extractor_rejecting()` and checks the class of each failure: empty and rejected are permanent, connect/timeout/5xx transient, and a timeout is declared. `test_contract.py` checks `classify()` for each class, including an unexpected exception.

**Tests:** `apps/documents/tests/test_extraction_failures.py` (task and HTTP), `test_extraction_failure_workers.py` (two workers on their own PostgreSQL connections, as IR-831's tests run them: a superseded attempt's permanent, transient or unexpected failure neither fails the row nor schedules a retry).

**Changed tests:** `test_extraction_task.py` and `test_manuscript_extraction_task.py` asserted one message for both failures and that a rejection retries; they now assert each class's message. `test_accepted_source.py` used `RuntimeError` for its retry cases, which is now permanent; those cases use `ExtractorUnavailable`, and the failure case keeps `RuntimeError`.

**Evidence (2026-11-02, Linux `iris-backend` image, private test DB):** `pytest apps/documents apps/ai/extraction apps/ai/ingestion apps/ai/tests/test_celery_routing.py apps/records/test_metadata_suggestions.py apps/tests/test_traceability_shape.py` — 528 passed. Full suite (the 7 `asyncpg` collection errors ignored): 5475 passed, 119 failed; 118 of them fail on `origin/main` in the same environment (AI inference, runtime, admission and throttle tests reading the dev `.env`), and the other, `test_chat_identity_http.py::test_partial_stream_retry_does_not_generate_again`, passes on this branch when its file runs alone. Migration `documents/0017` applied to a copy of the dev database (44 extraction rows, from `documents/0012`): every row has `warnings = []`.

**Not verified:** no separate Celery worker process ran these paths, so neither time limit has fired for real (eager `apply()` ignores both); a hard kill would leave the row `running` until reset. A soft limit raised after the read, while saving, is not classified. The frontend does not yet show `message`.
