## IR-647

**Requirement:** **The API enforces the configured password policy** — no FR- id; subtask 4 of IR-644 (account-security findings, 2026-10-30)

**Design:** **ADR owed** — the basis is the configured policy itself, `AUTH_PASSWORD_VALIDATORS` in `config/settings/base.py`; Jira IR-647 tracks the work and is not authority (see CLAUDE.md)

**Implementation:** `apps/accounts/serializers.py`: `enforce_password_policy()` runs Django's `validate_password` and reports every message on the named field; `RegisterSerializer` calls it with an unsaved user built from the submitted email and names, `ChangePasswordSerializer` with the requesting user. Both serializers' own `min_length=8` is removed, so the settings are the only definition of the policy. **Defect fixed:** before this, `password123` and `12345678` were accepted through the API although the configured common-password and numeric validators refuse them. `features/auth/SignupPage.tsx` shows every server message on a field, not the first; `features/settings/SettingsPage.tsx` reads `new_password` and shows all of its messages

**Test:** `backend/apps/accounts/test_password_policy.py` (10, HTTP API: `password123` and `12345678` refused on `password` and on `new_password`, a seven-digit password reports all three broken rules on each endpoint, a strong password accepted by both, mismatched confirmation and wrong old password unchanged) · `frontend/src/features/auth/SignupPage.test.tsx` (+1: both messages as the Password field's description, axe) · `frontend/src/features/settings/SettingsPage.test.tsx` (2, new: both messages shown, wrong current password still named, axe)

**Evidence:** 2026-10-30 in the backend container against an isolated test database: each backend slice red then green (`201 != 400` for registration, `200 != 400` for change, the `min_length` short-circuit for the multi-message case). Frontend tests red then green.
