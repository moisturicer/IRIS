## IR-1001 · Production refuses to start with the sign-in lockout off (NFR-S6)

IR-865 turned the django-axes lockout off by default so it stopped locking the team
out during development, and said to turn it back on before launch. Nothing enforced
that, so a deployment that left out the line would run without it.
`config.settings.production` now reports `AXES_ENABLED` that isn't True as a
problem, in the same list as `DEBUG`, `ALLOWED_HOSTS` and CORS, so the process
refuses to start and names every problem at once. Development keeps the default
of off.

Decided by Ashlee Sean on 2026-11-09: refuse to start, rather than default to on
and allow `AXES_ENABLED=False`. The accepted cost is that turning the lockout off
in production takes a code change.

**Implementation:** `production_problems(axes_enabled=...)` in
`config/settings/validation.py`; `production.py` passes `AXES_ENABLED`. CI's
production-settings step boots with `AXES_ENABLED=True` and proves `False` is
refused. The e2e stack already sets it (`e2e/scripts/make-env.mjs`).

**Not met by this:** ASVS 2.2.1 stays Partial. The lock counts a username and
address pair, so guesses spread over many addresses meet only each address's
sign-in throttle (IR-999).

**Evidence:** `backend/apps/tests/test_production_lockout.py` imports the real
production module in a fresh process: unset, `False`, `0` and empty each refuse
with `AXES_ENABLED is not True`, `True` starts with the lockout on, and development
still defaults to off. `test_settings_validation.py` checks the pure rule and that it
is reported together with the other problems. `test_transport_security.py` and
`test_client_address.py` boot production with the lockout on.
2026-11-09: on the old settings, 14 of these failed; all 61 in these three files pass
on the branch. CI evidence is on the PR.
