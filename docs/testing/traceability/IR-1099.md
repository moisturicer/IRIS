# IR-1099: Delete Requests: Decline with a note, shown to the requester and on Decided rows

**Requirements:** follow-up to IR-1076 (audit WF-02), epic IR-920. The matrix has no `FR-` row for the Delete Requests queue. The behaviour is that of Download Requests (IR-688, ADR-048 decision 4): a decline says why.

## What was wrong

RDCO could only approve a delete request from the page. The server's decline route and `recordsApi.declineDeleteRequest` existed and nothing called them, so a request could sit Pending forever. A declined owner was told only a fixed sentence, never why, and by no email. `DeleteRequest` stored no decision reason, so the Decided tab could show only the requester's.

## What changed

**Model, `apps/records/models.py` + migration `0041_deleterequest_rdco_note`.** `DeleteRequest.rdco_note`, `CharField(max_length=DOWNLOAD_NOTE_MAX_LENGTH, blank=True, default="")`, the same column as `DownloadRequest.rdco_note`. One additive `ADD COLUMN` with a constant default; every existing row reads blank, which the page shows as "No note recorded". Reverse drops the column.

**Decline, `apps/records/views.py`.** `POST /records/delete-requests/<id>/decline/` takes `{note}`. The note goes through `clean_note` (promoted from `download_service._clean_note`, so the two queues refuse the same notes): trimmed, required, at most 500 characters, any non-string refused. A refusal is a 400 `{"note": [...]}`, before anything is written. The decline then runs in one transaction under a row lock (`select_for_update`), as `decide_download_request` does: two simultaneous declines are one decision and one refusal, a decline cannot overwrite a request an approval has just committed, and a restore that fails rolls the status back to Pending instead of leaving a declined request on a held record. The note is stored with the status in the same save. `approve` takes none and now takes the same lock, so the two cannot both win: whichever commits second reads the request as decided and is refused (400), and an approval cannot soft-delete a record a decline has just restored.

**Notification, `apps/notifications/services.py`.** `notify_delete_declined` now carries the note in the in-app message and sends an email (it sent none) with the note and a link to the restored record.

**Serializer.** `DeleteRequestSerializer` exposes `rdco_note`, read-only.

**Page, `features/admin/DeleteRequestsPage.tsx`.** A *Decline* button beside *Approve Deletion* on pending rows opens a note dialog; the note is required, limited to 500 characters in the box and again by the server, kept with the server's reason when refused. A decided declined row shows "RDCO's note: …" under its status chip, or "No note recorded". An approved row shows neither. No decided row offers an action.

**Shared dialog, `features/admin/RdcoNoteDialog.tsx`.** The note dialog that was private to `DownloadRequestsPage` is now one component both queues use, with `RdcoNoteLine` (the "RDCO's note: …" / "No note recorded" line under a status), so they cannot drift. Download Requests' behaviour and labels are unchanged (its tests pass unmodified). `DownloadRequestsPage`'s and the new file's pixel font sizes moved to type tokens of the same size; `fontSizeAllowance.ts` for `DownloadRequestsPage.tsx` is lowered 9 to 6 as that guard requires.

Also covered: an approval after a decline is refused and removes nothing (`test_an_approval_after_a_decline_is_refused_and_removes_nothing`); a second decline is refused and keeps the first note; the note cannot be written through the queue's read-only routes (405); a refused note leaves the request Pending, the record on hold, and sends nothing.

## Open for the reviewer

- **Backend scope.** The ticket marks the backend "(Jive)". It was built here with the frontend because the ticket is one card, with the assignee's go-ahead to touch the backend; Jive may still want to read `views.py`, the migration and `notify_delete_declined`.
- **`clean_note`'s refusal text** now reads "Say why, in a note the requester will see." for both queues (it said "reader"; a download requester is the reader and a delete requester is the owner).
- **Frontend still has two note limits**: `RdcoNoteDialog.NOTE_MAX_LENGTH` and `DownloadRequestModal.NOTE_MAX_LENGTH`, both 500 (the second is the reader's note, not RDCO's, and predates this change). Not consolidated here.
- **Behaviour change:** `approve` and `decline` now run under a row lock in a transaction (no change to a single, uncontested decision). A decline with no note, previously accepted by the API, is now a 400.
