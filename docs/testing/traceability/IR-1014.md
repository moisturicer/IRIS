# IR-1014: First-boot script for an IRIS server

**Requirements:** no FR- id. Epic IR-805 (S2 Epic: Deployment). It replaces steps done by hand over SSH in the first deployment, 2026-11-10 (IR-806).

## Decisions (Hermoine Zozobrado, 2026-11-11)

1. Docker comes from Docker's apt repository, after checking its signing key's fingerprint. `get.docker.com` is not used: Docker documents it for testing, not servers.
2. The DuckDNS name and token live in `/etc/iris/duckdns`, owned by root and readable by root only, written by a person. Not in EC2 user data, which the console shows to anyone with access to the instance.
3. Tested by a CI job that runs the script for real, twice, on GitHub's Ubuntu 24.04 VM. Docker's fresh install is proven by the manual EC2 run instead, because that VM already has Docker.
4. The script lives in `deploy/`, beside `deploy/caddy/`, not in `scripts/` (the ticket's example).

## What changed

- `deploy/bootstrap_server.sh`:
  - installs Docker and Compose;
  - adds the login user to `docker`;
  - creates a 4 GB `/swapfile` and lists it in `/etc/fstab`;
  - clones `main` into the user's home;
  - with `/etc/iris/duckdns`, installs `iris-duckdns.service`, which updates the address on every boot and once at install.
- Before changing anything, it refuses:
  - a run without root;
  - a system that isn't Ubuntu;
  - a missing user;
  - a non-clone folder where the clone goes;
  - a DuckDNS file others can read;
  - a malformed domain or a missing token;
  - a swap size that isn't a number then M or G.
- A step a stopped run left halfway is finished: a `/swapfile` never made swap is made again, and Docker installed but not running is started. A `/swapfile` line in `/etc/fstab` with other options is not added twice.
- The token reaches `curl` through stdin, so it is never in the process list. A rejected update fails the run.
- It never starts IRIS and never writes a `.env` file.
- A second run changes nothing and reports each step "already done". It never updates an existing clone.
- Each step prints one `IRIS bootstrap: <step>: ...` line, readable in `/var/log/cloud-init-output.log`.
- `deploy/tests/bootstrap_checks.sh` and the `server-bootstrap` CI job; `deploy/README.md`.
- `.gitattributes` keeps `deploy/**/*.sh` LF, because a CRLF copy breaks on the server and in user data.

## Evidence

- Local, 2026-11-11, Windows with Docker:
  - `shellcheck` v0.10.0 is clean on both scripts.
  - In an `ubuntu:24.04` container, every refusal above exits 1 with its message, and none created `/swapfile`.
  - In a second container, the Docker path checked the signing key's fingerprint and installed Docker 29.9.3 and Compose v5.7.0 from Docker's repository. It then stopped at `systemctl enable`, as expected, because a container has no systemd.
- CI (`server-bootstrap`, `deploy/tests/bootstrap_checks.sh`): five refusals (not root, a DuckDNS file others can read, a full domain, a missing user, a bad swap size), then three runs: the first does everything, the second reports each step already done and leaves `/etc/fstab` byte for byte, the third repairs a half-made swap file without a second fstab entry. Result on PR [#673](https://github.com/moisturicer/IRIS/pull/673), 2026-11-11: all 33 checks passed ([job](https://github.com/moisturicer/IRIS/actions/runs/42861309135/job/129987854178)). The first attempt failed two checks because GitHub's runner already has a `/swapfile`; the check now removes it first.
- Not covered by CI: the DuckDNS updater (it would call duckdns.org), Docker's fresh install (the runner has Docker) and the fallback to the `ubuntu` user when there is no `sudo` caller, as under user data. The EC2 run below covers all three.
- Under user data, DuckDNS is always skipped: its root-only file can't exist before first boot. Stated in `deploy/README.md`.
- **Not yet done:** the manual run on a fresh Ubuntu 24.04 EC2 instance, as user data, then a login to add `/etc/iris/duckdns` and run it again, then a reboot (swap still on, DuckDNS still right), which the ticket requires.
