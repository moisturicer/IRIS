## IR-367

**Requirement:** **Docling's `do_ocr`/`table_mode`/`do_formula_enrichment` become settings, not a hardcoded dict** — extends FR-M3-01 (stable label only, per the frozen-SRS rule)

**Design:** No ADR — configuration, not a design decision; defaults are unchanged, so ADR-016 is not amended

**Implementation:** `apps/ai/extraction/docling_client.py`: `DoclingExtractor.__init__` takes `do_ocr`, `table_mode`, `do_formula_enrichment` (validated against `TABLE_MODES`) and builds `_convert_options` per instance instead of reading a module-level `_CONVERT_OPTIONS` dict every deployment shared. `config/settings/base.py` reads `DOCLING_DO_OCR`, `DOCLING_TABLE_MODE`, `DOCLING_DO_FORMULA_ENRICHMENT`, refusing to start on an unrecognised `DOCLING_TABLE_MODE`; `apps/documents/tasks.py::_build_extractor` passes all three through. **Measured first, against a live docling-serve container on the dev stack (2026-09-30), one born-digital paper ("Nested Parallel von Neumann Architecture and Nested BSP", 158 text elements, 21,524 chars, no tables):** timings for the same `do_ocr=true, table_mode=accurate` option set ranged from 10.5s to 124.8s across repeated calls with no code or setting changed; `do_ocr=false` (`table_mode=accurate`) measured 363.8s on first use and 513.3s on an immediate identical repeat — ruling out "switching options is what's slow," since the second call changed nothing from the first and was slower, not faster; `table_mode=fast` (`do_ocr=true`) measured 451s, slower than three of the four `accurate` runs above it. **`do_ocr=false, table_mode=fast` was not run** — recorded as a gap, not silently skipped. `docker stats` showed `iris-docling-1`'s memory climbing across successive calls (46%→84% of its 8GB limit) independently of which flags were set, and its logs showed a full model-reload burst (RapidOCR, layout, TableFormer, CodeFormula) on requests that were not the container's first. **The individual flags are not the dominant cost on this container** — `DOCLING_SERVE_CONCURRENCY=4` and per-request model-loading variance swamp any signal from `do_ocr` or `table_mode` alone at n=1 per combination, so no combination reliably beat `true`/`accurate`. **Chunk counts** (AC1) were not separately measured: the test paper produced byte-identical extracted content (158 text elements, 21,524 chars, 0 tables) across every combination tried, because it is born-digital (OCR made no difference to a present text layer) and carries no tables (table_mode had nothing to act on) — so a post-chunking count would have been the same number five times over, not a fifth data point. Per AC2's rule ("defaults that keep today's behaviour unless the measurement justifies changing it"), **the defaults are unchanged** — `do_ocr=true`, `table_mode=accurate`, `do_formula_enrichment=true` — with OCR staying on because ADR-016 has no fallback extractor for a scanned submission with no text layer. **AC3 ("auto" OCR)**: not built. The assignee's call recorded here: since the default keeps OCR on, no per-document text-layer detection is needed to keep scanned PDFs working, and building one would be speculative given the measurement above did not isolate OCR's real marginal cost
