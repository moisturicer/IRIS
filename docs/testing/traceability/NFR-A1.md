## NFR-A1

**Requirement:** WCAG 2.1 AA on interactive controls

**Implementation:** **New row (IR-204).** No NFR previously covered contrast or control accessibility; [`../ui-ux/12-accessibility.md`](../../ui-ux/12-accessibility.md) held the findings with nothing tracking them here.

**IR-204** fixed the login screen: submit moved off gold (white-on-gold **2.76 : 1**, failing AA and the 3 : 1 large-text floor) onto the brand primitive, and both fields onto the `Input` primitive that has carried `aria-invalid`/`aria-describedby` since **IR-158**

**Evidence:** Contrast recomputed from what the browser actually paints: **12.34 : 1** resting, **9.53 : 1** hover (read from the compiled `.hover\:bg-\[\#8B1316\]:hover` rule). Errored fields carry `aria-invalid="true"` and an `aria-describedby` that resolves to an element that **exists**; error text `red-600` **4.83 : 1**. Targets ≥ 44 px via new `Button` `full` and `Input` `lg` steps. Keyboard pass: every control shows a focus indicator. **All browser-verified, no automated test** — the frontend has no test runner installed (true at IR-204; IR-210 has since added Vitest + axe). **IR-211 (headings):** login, signup and email verification each have exactly one `<h1>` at every width. `AuthLayout` owns it as `sr-only` text; the signup panel's display line is no longer a heading. Before the fix, Chrome's accessibility tree showed **no** level-1 heading on login at any width, and none on signup at 360 or 768 (IR-208's `hidden lg:flex` took it). After: one per screen at 360, 768 and 1440, and login/signup screenshots at 360 and 1440 are byte-identical to before. `features/auth/entryHeadings.test.tsx` (9 Vitest, seen failing first) pins one `<h1>`, no skipped level, and no breakpoint-hiding utility or `aria-hidden` on the `<h1>` or its ancestors

**Status:** **PARTIAL** — login only. Entry screens remain in `IR-205`/`IR-206`/`IR-207`; `SettingsPage` and three wizard fields still hand-roll inputs ([12](../../ui-ux/12-accessibility.md) §2E), and there is **no regression guard** until `IR-207` — except for heading structure, which `entryHeadings.test.tsx` guards on all three entry screens since **IR-211**. **IR-536 (sign-in errors):** `features/auth/loginFailure.ts` classifies a failed sign-in so only the server can say the password was wrong; no response, a 5xx or a reply with no JSON `detail` says "IRIS can't be reached right now" and names neither field, through the shared `AuthAlert` (`role="alert"`). "Forgot password?" is a disclosure (`aria-expanded`, `aria-controls`, a region named by its trigger, 44 px target) instead of a toast. `LoginPage.test.tsx` has one case per failure row, the disclosure by keyboard, and axe on both the error and the open state. **IR-539 (register):** every register control is named by its label through `Input` and the new `Select`, each error is its field's description with `aria-invalid`, the role is a radio group, and Register is maroon (12.34 : 1); `SignupPage.test.tsx` guards it with axe. **IR-414 (*Request documents* dialog):** it now uses `useDialogFocus` (focus in, Tab kept inside, focus back to its opener); `RequestDocumentDialog.test.tsx` adds three keyboard tests, two of them seen failing first. IR-414's pre-pass also measured contrast failures in real Chromium: `stone-500` on `stone-100` **4.39 : 1** (Paper View record bar, My Reviews counts, Review labels) and `stone-400` on white **2.52 : 1** (Ask IRIS) ([`evidence/IR-414/README.md`](../evidence/IR-414/README.md))
