## IR-718 — One research-read policy in PostgreSQL, read the same way by both runtimes

**Basis and scope.** IR-718 under IR-712; authority ADR-049 §5, §7, §9 (not yet committed to `main`). Shared research-read policy and its migration only: workflow-write authorization, `RecordViewSet` and the other workflow apps keep `visible_to`, and Conversation storage is untouched. Additive and off by default (`AI_RESEARCH_READ_POLICY=application`).

- **Policy.** Migration `ai/0035` (SQL only) adds `iris_authz.research_record_ids()` (SECURITY DEFINER, pinned search path) mirroring `Record.objects.visible_to`: not soft-deleted, and office role (KTTO/RDCO/ITSO/IERC), published, assigned adviser or `RecordOwner`; a `reader_run` grant with a Record narrows to that Record. The principal comes only from IR-717's verified claims; only `record_read` and `reader_run` read, so an `ingestion` grant reads nothing until IR-737. Row security is ENABLEd (not FORCEd) with one SELECT-only policy on `records_record`, `records_recordowner`, `records_author`, `records_recordversion`, `documents_pdfextraction`, `ai_chunkset`, `ai_documentchunk`, `ai_chunkembedding`, `ai_recordembedding`, `ai_recordoverview` and `ai_paperbrief`. The table owner the application connects as today is unaffected. The migration refuses to run as a runtime login.
- **Roles.** `provision_research_roles` grants both runtime roles SELECT on exactly those tables and the verifier the columns the policy reads; `--check` also reports a table without row security or its policy and any runtime write privilege. `--force-row-security` is the cutover step and refuses unless the maintenance login is superuser or BYPASSRLS.
- **Entry point.** `apps/ai/grants/reads.research_records(user, scope_record_id=None)` is the only research-read decision under `apps/ai/` (guarded by `test_ai_research_reads_have_one_entry_point`); every former `Record.objects.visible_to` caller there now uses it. With `AI_RESEARCH_READ_POLICY=database` it reads the Record ids through the row policy over the `research` DATABASES alias (`AI_RESEARCH_DB_USER`, configured only in that mode) with a `record_read` grant, or with the run's own `reader_run` grant while a queued answer runs (`durable._answer` binds it via `reads.bound_run`). `migrate` refuses a runtime login in either direction through a `pre_migrate` guard (`grants/migration_guard.py`); `provision_research_roles` revokes the verifier from a non-superuser maintenance login after handing the functions over; an unknown grant refusal answers `unavailable`. Django refuses to start in that mode without grants and credentials, or with a superuser, BYPASSRLS, table-owning or non-`iris_django_runtime` login.

**Tests.** `apps/ai/tests/test_research_read_policy_db.py` (15, real PostgreSQL, throwaway LOGIN roles in each restricted group): parity with `visible_to` for owner, adviser, every office role, catalogue reader, a second owner and a role-less account, under both `iris_django_runtime` (`record_read`) and `iris_ai_runtime` (`reader_run`); Paper Chat scope narrows and never widens; no context, forged settings and an ingestion grant read nothing; removed ownership, adviser reassignment, soft deletion, deactivation and locking take effect on the next read; direct reads of every dependent relation, embeddings included, follow the policy and read nothing without context; counts and title lookups for a hidden and a missing id are identical; runtime roles cannot update, delete or insert; the policy's office and catalogue constants equal `STAFF_ROLES` and `PUBLICLY_VISIBLE_STATUSES`; the role check and FORCE step; the migration guard; and `GET records/<id>/` answers 200 exactly when the AI-side read sees the row, with identical 404 bodies for denied and missing. `test_research_reads.py` (10): the entry point in both modes, scope, anonymous and deactivated readers, and every startup refusal. `test_one_retrieval_stack.py`'s research-tool guard was updated deliberately to name `research_records(ctx.user)`.

**Migration evidence.** Applied forward on a copy of the dev database (61 Records, 16 active accounts), reversed to `0034` (no table left with row security, function gone) and re-applied; with roles provisioned and `database` mode on, all 16 accounts read the same Record ids as `visible_to`. The copy was dropped.

**Not done here.** Database mode decides the authorized Record population through the restricted login, but dependent content is still read afterwards over the owner connection, filtered by those ids; running every content read under the restricted role is IR-719's Evidence interface. Each database-mode decision opens one short connection (no pool). The FastAPI runtime does not yet read; the AI-side read is demonstrated by tests under `iris_ai_runtime`. Disabled accounts are refused by the policy, while `visible_to` itself does not check `is_active` (authentication refuses them first). Switching Django to the restricted login and forcing row security are deployment steps not taken.

**Status.** Implemented; awaiting review.
