## IR-820 — A signed-in password change notifies the owner (ASVS 2.2.3, 2.5.5)

Found by IR-617. After a reset, `apps/accounts/recovery/service.py` calls `notify_password_changed`, which records a `PASSWORD_CHANGED` recovery intent that the delivery worker emails as "Your IRIS password was changed". `ChangePasswordView` wrote an audit event and told no one, so a password changed from a stolen session went unreported to the owner.

**Fix.** `ChangePasswordView` now schedules the same `notify_password_changed(user_id)` with `transaction.on_commit`, inside the transaction that changes the password. So:

- nothing is recorded unless the change commits, and a refused change (wrong current password) sends nothing;
- the notice is best effort, as after a reset: `notify_password_changed` already logs and swallows a failure to record it, so the new password stands;
- the email is the reset's: no password, no link that signs anyone in, and how to recover if it wasn't you.

## Evidence, 2026-11-15

Run by Claude Code at Ashlee Sean's direction, on a throwaway local `pgvector/pgvector:pg16` container. Not on iris-demo.

`backend/apps/accounts/test_password_change_notice.py` (through the real sign-in and change endpoints):

| Test | Shows |
|---|---|
| a change emails the owner the reset notice after it commits | one `PASSWORD_CHANGED` intent; delivered, it is one email to the owner, subject "Your IRIS password was changed", without the new password |
| nothing is sent before the change commits | no intent until the on-commit callback runs |
| a refused change sends nothing | wrong current password: 400, no intent, old password still works |
| failing to record the notice cannot undo the change | `RecoveryIntent.objects.create` raising: 200, the new password works, no intent |

With it, the neighbouring recovery and session tests (`test_credential_invalidation.py`, `test_password_recovery.py`, `test_recovery_delivery.py`, `test_session_invalidation.py`) still pass: 93 passed in all.
