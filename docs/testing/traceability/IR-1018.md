# IR-1018: Update the IRIS server with one command

**Requirements:** no FR- id. Epic IR-805 (S2 Epic: Deployment). Every update to `iris-demo` since 2026-11-10 (IR-806) was typed by hand.

## What changed

- **`scripts/deploy.sh`** updates a running server to GitHub's `main` in five steps, and stops at the first that fails, naming it:
  1. **pull:** fast-forward only. It refuses another branch, uncommitted changes, or commits on the server that GitHub doesn't have, and changes nothing.
  2. **check:** the three `.env` files, `docker compose config` and 5 GB free.
  3. **rebuild:** `up -d --build`. A failed `migrate` is named, and its log is shown.
  4. **health:** every service running, and healthy where it has a healthcheck, on three checks in a row. All of step 4 shares one timeout. After a rebuild, `frontend` is restarted (IR-200). Then `https://<IRIS_DOMAIN>/` and `/api/v1/colleges/` must answer. With nothing rebuilt, a page that answers and an API that doesn't gets one `frontend` restart.
  5. **report:** the deployed commit.
- It records the last commit it deployed in `.git/iris-deployed`:
  - A run with nothing new skips the rebuild and only checks health.
  - A run after a failed one rebuilds.
  - A failure after a pull prints the command to go back to the previous commit. It never goes back by itself.
- Its body runs inside `main()`, so the pull can replace the script while it runs.
- `deploy/tests/deploy_checks.sh` runs it against a throwaway git repository, with a fake `docker` and `curl` on `PATH`. The `server-bootstrap` CI job runs it and lints both files with shellcheck.
- `deploy/README.md` documents it and points the bootstrap's **Next** and **After a scheduled start** sections to it.
- `docker-compose.prod.yml` loses its obsolete `version:` line, which made every compose command print a warning.

## Evidence

- Local, 2026-11-11:
  - `deploy_checks.sh` has 17 cases and 75 checks, written first. The two refusal cases and the success and up-to-date cases were seen failing before the script did each.
  - The failure cases passed on their first run. So four faults were put into the script, one at a time, and each was caught:

    | Fault put in | Checks failing |
    |---|---|
    | health ignored | 1 |
    | deploy never recorded | 3 |
    | "up to date" judged by `HEAD`, not by the record | 3 |
    | any `migrate` exit code accepted | 2 |
  - The code review raised further faults: a failed pull still printed advice to go back; a commit on the server was deployed silently; a Docker error could end the run without naming the step; the timeout applied to each wait separately; a crash-looping service could pass on one look; a leading zero crashed the number check. Each got a failing case first: 12 checks failed, then passed after the fix. Three more faults were then put in and caught:

    | Fault put in | Checks failing |
    |---|---|
    | one ready check is enough | 2 |
    | commits on the server allowed | 3 |
    | no `frontend` restart when the API fails | 3 |
  - shellcheck 0.10.0 is clean on both files.
  - `docker compose ps -a --format '{{.Service}}|{{.State}}|{{.Health}}|{{.ExitCode}}'` against a real local stack prints `db|running|healthy|0`, the format the script reads.
  - `check_compose_prod.py` and `docker compose config` pass without the `version:` line.
