# IR-1005: the review-text reader loads its text encodings before the sandbox closes

**Requirements:** no FR- id. A fix to IR-871's reader ([ADR-058](../../adr/058-each-version-keeps-its-text-and-its-files.md) §1, and `docs/security/PDF_INTAKE.md` §Review text for the sandbox).

## What was wrong

`_preload()` in `apps/records/review_text/reader.py` runs before `confine()`, which stops the reader opening any file. It is meant to import everything a read loads lazily. For text encodings it decoded empty bytes, `b"".decode(codec)`. CPython takes a fast path for empty input that imports no codec module, so none of them was loaded.

A PDF with an embedded font maps its glyphs through a ToUnicode CMap, which pdfminer decodes as UTF-16BE (`pdfminer/cmapdb.py`). Most PDFs saved from a word processor have one. Inside the sandbox, loading `encodings/utf_16_be.py` then failed with `EMFILE`. The read was stored as `no_text` / `unreadable`, so the paper read "No text for vN" for every Version. Its Versions couldn't be compared (IR-873), and its threads were never placed in a later Version (IR-876).

The test PDFs never caught it: they are drawn in reportlab's built-in Times, which has no ToUnicode CMap. It was found in a Docker test of IR-876. That paper read 40 sections outside the sandbox and failed inside it, at `encodings/utf_16_be.py`.

## What changed

- `_preload()` calls `codecs.lookup(...)`, which imports each codec. It adds `utf-16`, which pdfplumber also uses.
- `review_text/testing.py`: `pdf(..., embedded=True)` draws in reportlab's own Bitstream Vera, embedded as a subset with a ToUnicode CMap, as a word processor's PDF is.

## Evidence

- PR: https://github.com/moisturicer/IRIS/pull/654
- `apps/records/test_review_text_sandbox.py`, two new tests, Linux only (CI):
  - *a PDF in an embedded font is read in the sandbox*;
  - *once confined, the child can still decode every encoding a read uses*: UTF-16BE, UTF-16LE, UTF-16, Latin-1, ASCII, cp1252 and UTF-8, after `_preload()` and `confine()`, in an isolated child as the sandbox runs it.
- **Run by hand on Linux, 2026-11-10,** in the backend image (Python 3.12, pdfplumber 0.11.10), running `reader.py` as the sandbox does:
  - **Before the fix:** the plain test PDF reads (exit 0), and the embedded-font one fails (exit 2, stored `unreadable`). The decode probe fails for UTF-16BE, UTF-16LE and cp1252 with `OSError`.
  - **After:** both PDFs read (exit 0), and every codec decodes.
- On Windows, where these skip: `test_review_text_sandbox`, `test_review_text`, `test_review_text_readings` and `apps/reviews/test_thread_places` give 69 passed and 10 skipped. flake8 is clean.

## Texts stored `unreadable` before the fix

A stored `no_text` counts as true for every reader. `readings.ensure_current` and `pair` never read it again, so a new reader version won't recover these papers either. Nothing is deployed, so they exist only in development databases. After pulling the fix and rebuilding, re-read them once from the repository root:

```powershell
@'
from apps.records.models import ReviewText, ReviewTextState
from apps.records.tasks import read_review_text
stuck = ReviewText.objects.filter(state=ReviewTextState.NO_TEXT, reason="unreadable")
ids = list(stuck.values_list("pk", flat=True))
stuck.update(state=ReviewTextState.PENDING, reason="", read_at=None)
for pk in ids:
    read_review_text.delay(pk)
print(len(ids), "queued for reading")
'@ | docker compose exec -T backend python manage.py shell
```

A file that is broken still reads `unreadable` again. A finished read also places the paper's review threads (IR-876).

This resets rows in place, which ADR-058 §1 otherwise rules out. It is a one-off for development data that a bug stored wrongly, not a code path. A deployed database would need its own decision, recorded in the ADR. Checked 2026-11-10 against a migrated empty test database, where it queued 0.
