## IR-695 People add a photo, bio and research interests to their account (NFR-S4, FR-M6-06)

**Basis and scope.** IR-695, subtask of IR-694 (public profiles and people search). The backend half; the Settings screen is IR-699. The contract is the comment on IR-695, unchanged except that **ORCID iD is dropped** (decided 2026-11-07): there is no `orcid` field on the account, in `PATCH /users/me/`, in `GET /users/me/` or in validation, and the Jira description no longer lists it. Public profiles (IR-700) and people search are not built here.

**What exists.**

| Piece | Where |
|---|---|
| `User.bio`, `User.photo`, `User.photo_version`; `ResearchInterest` (one row per tag, unique on `lower(name)`) and `UserInterest` (a person's use of it, with its place in their list). Migration `accounts/0019` | `apps/accounts/models.py` |

| Pillow named in the requirements (it was only a transitive dependency of pdfplumber) | `requirements/base.txt` |

**Decisions.**

- **The photo is re-encoded, never stored as uploaded.** Pillow opens it restricted to JPEG and PNG (so the check is on content, not the extension or the declared type), the EXIF orientation is applied, the chosen square is cut out, transparency is laid on white, and a 512×512 JPEG is written. EXIF (which can carry a GPS position), ICC profiles, animation and anything appended to the file do not survive. This also answers the question IR-699 left for IR-695: **the crop is measured on the image after its orientation is applied**, which is what the browser shows.
- **Never an open media URL.** The file sits under `MEDIA_ROOT` as `profile_photos/<random>.jpg`; `MEDIA_URL` is not routed (IR-152), the stored path is in no response, and `GET /users/<id>/photo/` needs a token. `Cache-Control` is `private`; a copy fetched under the current `?v=` may be kept for a day, any other revalidates. A person with no photo, a missing id and a deactivated account all answer the same 404.
- **`?v=` is `photo_version`**, a counter bumped on every set and remove and never reset, not a timestamp: two uploads in one second cannot share a version.
- **Only the person edits.** The write routes act on `request.user` and take no id; `UserSerializer`, which the administrators' endpoints use, does not carry the fields; there is no write route under `/users/<id>/photo/` (405).
- **Interests.** A tag is matched against existing ones by PostgreSQL's `lower()` on both sides, the function the unique index uses, so a lookup and the constraint cannot disagree. The first spelling stays. Whitespace is collapsed, blank entries dropped, and repeats in another case collapse before the 10-tag and 40-character limits are checked. A tag no active account uses is not suggested, and one nobody uses is deleted. Order is kept (`UserInterest.position`).
- **Deleting the account deletes the photo,** after the deletion commits (`post_delete` → `on_commit`), as does replacing or removing it; a failure deleting the file is logged, not raised, since the request has already succeeded. Photos are deleted through `FieldFile.delete` (`models.delete_photo_file`), not a direct storage delete, which `records/test_record_versions.py::SourceSafetyTests` forbids anywhere in app code so that no manuscript file is ever deleted by accident; CI's first run failed on exactly that, and the test was left as it is. A failed save removes the new file rather than orphaning it. Deleting the account also deletes any tag only it used.
- **Known and left alone.** (1) Two requests that race on the last user of a tag can end in a `500`: one deletes the now-unused tag after the other has matched it. It needs two accounts editing interests in the same instant. (2) A tag only a deactivated account uses is not suggested but is still matched, so a new person typing it takes its first spelling. (3) An outer rollback after `set_photo` returns would leave the new file on disk; no request wraps a view in a transaction today (`ATOMIC_REQUESTS` is off).
- **Two refusals the contract did not list,** each a `400` with a message the frontend shows as written: an image over 25 megapixels on `photo` (a 2 MB PNG can decode to hundreds of MB; refused from the header, before decoding), and a crop with only some of `crop_x`, `crop_y`, `crop_size`, on the missing ones. A blank interest is dropped rather than refused. **The contract comment needs these added**: they are for the IR-695 reviewer to accept.

**Tests.** `apps/accounts/test_profile.py`, at the HTTP level: bio at 500 and 501 characters, clearing, null bytes; interests at 10 and 11, 40 and 41 characters, case-insensitive matching, duplicates, order, orphan deletion, hostile input; suggestions (contains, case, most used first, at most 10, `%` and `_` as text, deactivated accounts, signed-out); photo JPEG and PNG, transparency, centred and chosen crops, EXIF orientation, metadata removed, a crop outside the image, partial and malformed crops, non-images named `.jpg`/`.png`, other formats, truncated files, the 2 MB limit on a real image, the megapixel limit, a refused upload keeping the old photo, replacement and removal deleting files, account deletion deleting the file; serving (bytes, signed-in only, no media URL, headers, 404 cases); and that nobody reaches someone else's fields. The matrix declares each new route as `SIGNED_IN` and `RouteDeclarationTests` fails on any route left undeclared.

**Not yet seen passing.** The tests were written against the contract and the image logic was exercised on its own (JPEG and PNG, centred and chosen crops, orientation, transparency, truncated, non-image, GIF, oversize and 30-megapixel inputs), but the backend suite needs PostgreSQL, so **it has not run locally and CI is the check**. `contracts/user-me.json` and `contracts/auth-login.json` (whose `user` is the same payload) gain `bio`, `research_interests` and `photo_url` by hand, with empty values, now that IR-699's `User` type declares them; `UPDATE_CONTRACTS=1` was not run, and the frontend `contract.test.ts` is for CI.
