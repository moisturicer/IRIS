## IR-821 — API responses stay out of caches and browser tabs, and nginx names no version (ASVS 8.2.1, 14.3.3, 14.4.2)

Found by IR-617:
- `no-store` was set on a few views only (recovery, the audit export, downloads);
- nginx sent its version in the `Server` header and on its error pages (`nginx/1.25.5`);
- API responses had no `Content-Disposition`.

**Django: `core.middleware.ApiResponseHeadersMiddleware`.** It sits second in `MIDDLEWARE` and applies to every response under `/api/`:
- **`Cache-Control: no-store`** (8.2.1). Public endpoints get it too, so there's no list of what is safe to cache to keep up to date. The frontend's own data layer does its caching in memory.
- **`Content-Disposition: attachment; filename="api.json"`** on JSON responses (14.4.2). **Decided by Ashlee Sean, 2026-11-15: applies.** A browser never renders an API response as a page. The app's fetch calls ignore the header; an API address opened in a tab downloads.
- **A view that sets either header keeps its own.** That is how a view opts out. The profile photo keeps `private, max-age=86400`, downloads keep their filenames, and Ask IRIS's event stream keeps `no-cache`.
- **Paths outside `/api/` are untouched:** the Django admin, static files.

**nginx: `server_tokens off`** (14.3.3), at the top of `frontend/nginx.conf`. The `Server` header and nginx's error pages say `nginx` with no version.

**A test changed deliberately.** `apps/records/test_download_grant.py::TheBearerLinkIsGoneTests` asserted that the retired download route's 401/404 carried no `Content-Disposition`, to show no file is served. Every JSON answer now names itself `api.json`, so the test now allows that header and nothing else.
