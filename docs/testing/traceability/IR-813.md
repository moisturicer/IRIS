# IR-813: KTTO releases IP-marked papers, and no office can clear the IP mark to get around that

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** ADR-052 decisions 11 to 13. No FR- id.

**The act:** `POST /records/<id>/ip-release/`, KTTO only, on a submitted paper marked `is_ip`. It stamps `Record.ip_released_at` and `ip_released_by` (migration `records/0028`), keeps the mark, and sends the paper on through `send_to_ai_on_commit`, as an embargo's release does. RDCO, ITSO, IERC, the Adviser and owners get 403. Who may act is checked before whether there is a mark to release. A draft, an unmarked paper and a mark already released get 400, each with its own message. `apps/records/ip_release.py::why_not_releasable` decides that for both the endpoint and the `release_ip` capability, so the two can't disagree.

**The check:** `apps/ai/policy/disclosure.py` refuses `UNRELEASED_IP` only while the paper is marked and not released. `DisclosureInputs.ip_released` defaults to False, so a caller that leaves it out is refused. Every path to a vendor reads the gate through `decision_for_record`, so no other code changed.

**Marking again needs a new release:** the check constraint `record_ip_release_needs_mark` refuses a release on a row with `is_ip` false, so a release can't outlive its mark. Clearing a released mark without also clearing its release is refused by the database. A paper can only be marked again after both are cleared, and it then starts unreleased. No code path clears the mark now: owners can't change `is_ip` after submission (`SUBMISSION_FIXED_FIELDS`), `tags/` refuses it, a release needs a submitted paper, and nothing returns a paper to draft. A future path that clears the mark must clear the release with it.

**The back door:** `PATCH /records/<id>/tags/` answers 400 to `is_ip: false` on a marked paper, for every office including KTTO, and changes nothing else in that request. Setting `is_ip`, `ip_type` and the other flags works as before, and `false` on an unmarked paper is still allowed because it clears nothing. `TagsPermissionTests` needed no change: none of its tests clears the mark. The frontend only sends `ip_type` to this route.

**Independent facts:** a paper under both an embargo and an IP mark needs both releases, in either order, and consent still applies. Tested over HTTP in `IndependentFactsTests`.

**Audit:** `IP_RELEASED` (migration `audit/0015`, choices only), with `ip_type`. Added to `docs/evaluation/AUDIT_EXPORT.md`. There is no backfill.

**`capabilities`** carries `release_ip`, offered to KTTO on a submitted, marked, unreleased paper. `apps/tests/access/table.py` has the route. Its world seats no KTTO member, so every role there is refused, and KTTO's success is covered in `test_ip_release.py`. `test_capabilities.py` probes the route for every viewer and state. The frontend's `Capability` type gains `release_ip`, and `src/types/audit.ts` labels `IP_RELEASED` for the audit log's filter. There's no screen for the release until IR-817.

**`TRACEABILITY.md` is unchanged, though the ticket asks for it.** ADR-055 changes a row only when a requirement's status changes, and no row's status changes here. This file is the update.

**Tests:** `apps/records/test_ip_release.py` (the constraint, each role and state over HTTP, the queue, independence, audit, `tags/`, capabilities) and `apps/ai/policy/tests/test_disclosure_policy.py::IpReleaseTests`. In `test_record_adapter.py`, the stub record gains `ip_released`, because the adapter now reads it. In `test_disclosure_policy.py`, `test_every_failing_input_is_reported_not_just_the_first` moved into a new `ReportingTests` class, unchanged, so `RefusingTests` stays about single refusals. No assertion changed.

**Evidence, 2026-11-03:**

- **Failing first:** the gate tests (6 failed), the adapter test (1), the endpoint tests (13 failed before the route existed) and the `tags/` tests (6) were each red before their code. The constraint tests passed on the first run, because the constraint was written in the step before them. With the constraint removed from `records/0028`, two of the three failed, and they passed again once it was restored.
- **A copy of one developer's dev database** (18 records, 5 marked `is_ip`) migrated forward from `records/0021` and `audit/0010` through `records/0028` and `audit/0015` with no error. It was rerun after merging `main`, whose `records/0027_duplicate_acknowledgement` took this change's original number, so `0028` now depends on it. The constraint exists, no row starts released, and all 5 marked papers are refused for `UNRELEASED_IP`. A release removed only that reason, and clearing a released mark was refused by the database. The checks ran in a transaction that was rolled back, and the copy was dropped.
- **Full backend suite on Windows:** 5,774 passed, 143 failed, 17 skipped, 1 xpassed. **Every failing test also fails on an untouched `main` worktree**, rerun by its exact ID, except `test_the_proxy_audit_pins_the_proxy_set_it_audited`. That one is the known local Windows line-ending hash mismatch on a file this change doesn't touch. The rest are local: `apps/documents/pdf_inspection.py` imports `resource`, which Windows lacks, so every PDF upload reports checking unavailable, and `test_parallel.py` needs `pytest-xdist`, which this environment lacks. CI on Linux is the record for those.
- **Frontend:** `npx vitest run --maxWorkers=2` passed 1,721 of 1,722. The failure was this change's: `AuditLogPage.test.tsx` checks that every backend event type is a filter option, and `IP_RELEASED` had no label. `src/types/audit.ts` now has it, and that test passes. `tsc --noEmit` is clean, and lint warns only in files this change doesn't touch.
- **`flake8`** and **`makemigrations --check`** are clean.
- **Review:** a standards review and a spec review ran on the diff. From them, a draft release got its own message instead of the embargo's, the endpoint and the capability share `why_not_releasable`, and this file's wording on the constraint was corrected.
- **Not run:** no real server over HTTP, no worker consumed the queued job, and no real vendor was called. There's no screen for the release until IR-817.

**Known limits:**

- **A mark set by mistake can't be removed,** only released. That's decision 12: clearing it is what would open the check with no release.
- **The access matrix shows only refusals for `ip-release/`.** Its world seats no KTTO member, and adding one changes every row of the table, so KTTO's success is proven in `test_ip_release.py` instead.
- **A release can't be undone,** and there's no act to hold a released mark again. The embargo can do that (ADR-052's IR-812 Amendment), and the ADR asks nothing like it of the mark.

**Status:** Implemented; awaiting review.
