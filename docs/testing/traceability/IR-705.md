## IR-705 — Only verified accounts reach RDCO, and unverified registrations expire or are replaced

**Basis and scope.** IR-705 under IR-671; authority ADR-051 decisions 22 to 26 (accepted 2026-11-01). Decisions made within them on 2026-11-11 are recorded on the Jira card. Backend only: the registration page's copy and the System Admin's "unverified" label are IR-804. No FR- id.

**What exists now.**
- **Unverified registration** (`CONTEXT.md`): an account whose registrant hasn't verified their email. `apps/accounts/unverified.py` decides which can be removed. One can be removed only if nothing links to it: no co-ownership, no Record naming it Adviser, and no reviewer seat or review in any state. Removing one deletes the row with its role request, links, notice answers and recovery tokens. It is not Account deletion.
- **RDCO sees verified accounts only.** The role request list filters on `user__is_verified`, and deciding an unverified account's request answers 404. The Users page and user detail filter the same way for RDCO; the System Admin still sees every account (`views._seen_by`).
- **Co-owners must be verified.** `owner_emails` resolves only verified, active accounts and says "Use existing verified accounts, …".
- **Registering again replaces.** `RegisterSerializer.validate_email` refuses an address held by a verified or linked account. Otherwise `RegisterView.perform_create`, in one transaction:
  1. asks `recovery.service.recipient_wait` (ADR-045's per-address windows, counting nothing). If it's too soon, it answers 429 with `retry_after` and a `Retry-After` header, and changes nothing;
  2. removes the earlier account, writing `REGISTRATION_REPLACED` (user = the earlier account's id, empty metadata);
  3. checks the address again and saves the new account.

  Then the existing `admit_request` issues a fresh link. The bucket lock taken in step 1 is held until commit, so the send that follows is decided on the same counts. The earlier link stops working because its token went with the earlier account.
- **Expiry.** `expire_unverified_registrations(now)` removes every unverified registration that registered at least `UNVERIFIED_REGISTRATION_DAYS` (default 30) before `now`. It skips linked ones and logs each by id only. It writes one `UNVERIFIED_REGISTRATIONS_EXPIRED` event per run, holding `{expired, skipped}` and no actor. Beat runs `apps.accounts.tasks.expire_unverified_registrations` daily at 19:00 UTC (03:00 Manila).
- **The email** names who registered (`get_full_name()`: first name, middle initial, last name) and says "If this wasn't you, ignore it. The account is deleted in N days." The text is composed at send time, so a resend says the same.
- Audit migration `0026_unverified_registration_events` adds the two choices.

**Tests.**
- `backend/apps/accounts/test_unverified_registrations.py` (18 tests):
  - registering again: a verified address is refused; an unverified one is replaced (the earlier link is refused, one fresh email names the new registrant, one pending role request); the audit event names only the earlier id; co-owner, Adviser and seat links each keep "already registered"; too soon gives a 429 with nothing changed;
  - RDCO's role request list, approval, Users page and user detail; the System Admin still sees the account;
  - `owner_emails` refuses an unverified account and accepts it once verified;
  - expiry: the boundary (30 days minus 1 second kept, exactly 30 days removed, an old verified account kept); linked skipped and logged by id; one audit event per run and a repeat run changes nothing; audit rows of a removed account stay; the period follows the setting; the beat entry;
  - the email's two sentences, on registration and on resend.
- `backend/apps/tests/test_authorization_matrix.py::test_rdco_sees_verified_accounts_only`: per role, the user detail and approval of an unverified account.
- `backend/apps/accounts/test_email_verification.py::test_the_email_says_what_it_is_for_and_nothing_about_approval`: **changed deliberately.** It asserted the sentence "If you did not request this, ignore this email.", which decision 26 replaces. It now asserts the two new sentences. Its check that the email says nothing about approval or roles is unchanged.

**Verification.** Run locally on 2026-11-11 against PostgreSQL in Docker (`DB_PORT=55432`). The full suite's result is recorded on the PR.

**Security review.** Decision 25 widens an existing risk: someone can replace a stranger's pending registration with their own name and password, and if the stranger clicks the new link their address is verified on an account the other person can sign in to. The ticket made Ashlee the reviewer; because Ashlee built it, the review moved to Hermoine Zozobrado (Jira comment, 2026-11-11). The outcome is recorded on the PR before merge.

**Not done here.**
- The registration page's wrong-email advice, and the System Admin's "unverified" label, are IR-804.
- RDCO's other account actions by id (change role, lock, unlock, office coordinator) don't hide unverified accounts. ADR-051 decision 22 names only the role request list, the Users page and the user detail view.
