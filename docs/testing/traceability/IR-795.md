# IR-795: The System Admin's Retention page

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** ADR-051 decisions 3 and 19 (subtask 16 of IR-779). Builds on IR-794's retention job and IR-667's settings API. No `FR-` id.

**Status: PARTIAL** until reviewed and merged.

**What was built**

- `frontend/src/features/admin/RetentionPage.tsx` at `/admin/retention`, listed as "Retention" in the System Admin's Administration section (`lib/access.ts`, `router/index.tsx`, `router/matrixRoutes.json`).
  - Each kind of data is a list item named by its label, with what it covers, its period ("Not set. Nothing is erased." when blank) and when the cleanup last ran, with how much of that kind it erased. The last run is the newest `RETENTION_CLEANUP_RUN` audit event (`GET /audit/?event_type=RETENTION_CLEANUP_RUN&page_size=1`).
  - A notice at the top says that a blank period erases nothing and that a period is entered only after the data protection officer has approved it, that the cleanup runs daily at 3:00 a.m. Philippine time, that erased data can't be recovered and that the Audit Log is never erased.
  - Saving a period first asks the server how many items it would erase now. When that's more than zero, a dialog states the count ("the notes of 12 download requests"), with Cancel focused, and nothing is saved until the System Admin chooses "Save and erase". A period that would erase nothing saves at once. Clearing a period saves at once without asking, because blank erases nothing.
  - A refused value, whether from the preview (`days`) or the save (`value`), shows under the field, which is marked invalid and described by the message.
  - The page lists the types in `RETENTION_TYPES`; a type registered in the backend later needs its row there.
- **Backend addition (agreed with the ticket's owner, since IR-794 offered no way to count before saving):**
  - `GET /settings/<key>/erasure-preview/?days=N` (`RetentionPreviewView`), the System Admin alone. It returns `{key, days, count}` and reads only. A blank `days` previews 0; one that isn't a positive whole number gets 400 `{"days": [...]}` with the PATCH's own message; a key that isn't a retention period is a 404; a type with no counter is a 501.
  - `RetentionType` gains an optional `count(cutoff)`, and `retention.preview()` uses it. Download notes count with the same `_due(cutoff)` query the eraser updates, so the preview and the erasure can't disagree.
- `e2e/smoke/support/screens.ts` has a `retention` row, and `dialogs.ts` a case that opens the erase confirmation, so the viewport matrix and axe scans cover both.

**Tests**

- `frontend/src/features/admin/RetentionPage.test.tsx`, 8 tests, querying by role and accessible name, with axe on the list, on the confirmation dialog and on a field error:
  - lists the type with its period and last run, and reads the right setting and audit filter;
  - the blank-erases-nothing and data-protection-officer statements, and the "never run" and "not set" states;
  - a period that would erase data opens the dialog with the count, saves nothing until confirmed, then saves and shows the new period;
  - cancelling the dialog saves nothing;
  - a period that erases nothing saves without a dialog, and clearing a period saves without asking the server to count;
  - a preview refusal and a save refusal each show against the field;
  - a failed load says so.
- `lib/access.test.ts` and `components/layout/Sidebar.test.tsx` pinned the System Admin's nav to four entries. Both now expect Retention as well, a deliberate change for this ticket.
- `backend/apps/audit/tests/test_retention_preview.py`, 8 tests: the count matches what `run_retention` then erases for four periods, asking erases nothing and writes no event, blank previews 0, malformed and missing periods are refused against `days`, non-retention keys are 404, a type without a counter is 501, RDCO gets 403 and a signed-out request 401. The existing `test_retention.py` is unchanged.
