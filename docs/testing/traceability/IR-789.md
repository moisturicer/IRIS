# IR-789: A person answers the notice, the data-privacy agreement and AI consent, per version

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** ADR-054 decisions 1 to 4 and 17. `FR-M6-02` and `FR-M6-06` (stable labels). The wording of the notice stays with IR-123; this ticket is the mechanism. ADR-054 decisions 5 to 16 (what a Yes or No *does*, the Contact person, Settings, the gate) belong to the other IR-779 subtasks and are **not** built here: nothing reads `User.ai_consent` yet.

**The model (`accounts/0019`):**

- `DataNotice`: numbered versions, `sections` as JSON in the shape the frontend renders. The current notice is the highest number. A published version is never edited (`save()` refuses). Migration 0019 creates **version 1 from `DataNotice.tsx` and `lib/dpaTerms.ts`**, copied, so a later edit to the frontend file changes nothing in the database.
- `NoticeAnswer`: append-only history, one row per answer with the version, `agreed_dpa`, `ai_consent` and the time. A check constraint says a stored answer always agrees to the data-privacy agreement.
- `User.answered_notice_version`, `ai_consent`, `notice_answered_at`: the person's **last** answer, copied from the history so the block is one comparison per request. All three are null on every existing account (decision 17). `consent_given` stays as a legacy column, is set when someone answers, and nothing reads it for a decision.

**The API:**

- `GET /auth/notice/` (`notice-current`): the current notice. Public, because registration shows it first. A signed-in caller also gets `answer` and `answer_required`.
- `POST /auth/notice/answer/` (`notice-answer`): `{notice_version, agree_dpa, ai_consent}`. 201 with the new state. Both booleans are required with no default, including in form posts, where DRF would otherwise read a missing box as False (`NoDefaultBoolean`). A `notice_version` that is not the current one gets **409 `notice_stale`** with the current notice in `notice`, so the person reads it first.
- `POST /auth/register/` now takes `notice_version`, `agree_dpa` and `ai_consent` **in place of `consent_given`**, a deliberate change. The old single box no longer registers anyone. Saying No still creates a normal account. `POST /auth/login/` adds `notice_answer_required`.

**The block:** `IdleAwareJWTAuthentication` refuses, for every account (office staff, the System Admin and a superuser included), any request that does not resolve to `notice-current`, `notice-answer` or `auth-logout` while the person's answered version is older than the current or unknown. The answer is **403 `notice_acceptance_required`** with `notice_version`. It sits in the authentication class so no view can opt out and a new route is covered by default. It is decided by URL name, so a new route is blocked until someone adds it to `notice.ALLOWED_WHILE_UNANSWERED`. Token refresh does not pass through it, so a blocked person keeps their sign-in while they read. **Request account deletion** is named in decision 3 but has no route yet (ADR-051); it joins that set when it exists.

**Last answer stands:** publishing a notice changes only which number is current. Nothing writes a person's stored answer except `notice.answer_notice`. Publishing is IR-790's act and is not built here: tests create a newer `DataNotice` directly.

**Audit:** `NOTICE_ANSWERED` (`audit/0016`, choices only), written by `answer_notice` in the answer's own transaction, with `notice_version`, `ai_consent` and the `previous_*` pair. Added to `docs/evaluation/AUDIT_EXPORT.md`. No backfill.

**`seed_demo`** answers Yes for every account it makes (decision 18), through `answer_notice`, so history and audit rows exist and a re-run restores a Yes. `load_corpus`'s loader account is not touched: it never signs in.

**Authorization matrix:** `notice-current` (public) and `notice-answer` (any signed-in account) are declared in `apps/tests/access/table.py`. `TRACEABILITY.md` is unchanged: per ADR-055 a row changes only when a requirement's status changes, and `FR-M6-06` stays PARTIAL until withdrawal and the DPO's review (IR-123).

**A deliberate change to the test harness:** `conftest.py` now gives every user a test creates a Yes on the current notice (`pre_save`, mirror fields only, no history or audit row). Without it every test that signs in with a real token would stop at the notice. It is a test default and not a weakening: `make_unanswered` (in `apps/accounts/tests.py`) undoes it, and `test_notice.py` exercises the block that way. No existing assertion changed. The only edit to an existing test is `test_password_policy.py`'s shared `registration()` payload, which carried `consent_given` and now carries the three new fields.

**Tests:** `apps/accounts/test_notice.py` (the notice, every answer rule, stale refusal, registration, the block for each role and each allowed route, new-notice blocking, last answer standing, audit, the exact set of fields an answer writes), `test_notice_migration.py` (existing accounts unanswered, v1 created, legacy `consent_given` kept and not read as an answer), `apps/tests/test_notice_block_every_route.py` (every declared case of every route, fired with a real token as an unanswered student), `SeedDemoAnswersTheNoticeTests` in `apps/records/test_seed_demo.py`, and the matrix rows.

**Known limits:**

- **The frontend's signup form still sends `consent_given` and gets a 400** until the consent screen is built (ADR-054's "new frontend work"). It also loads `/users/me/` after sign-in, which a person with an unanswered notice now gets a 403 for; the login response's `notice_answer_required` says to show the notice instead.
- **Nothing consumes `ai_consent` yet.** It is stored and mirrored, and IR-790, IR-791 and IR-799 build on it.
- **One extra indexed query per authenticated request** reads the current notice number.
- **Account deletion request** is not yet in the allowed set because the route does not exist, so that part of ADR-054 decision 3 is unmet until it does.
- **"Discoverable" is not a field on this branch,** so what the ticket's criterion can be tested as is that an answer writes only the four answer fields (`test_the_discoverable_setting_is_not_touched`). When that setting exists, its own test should assert an answer leaves it alone.
- **A signed-in client that sends an unanswered token to sign-in or registration is refused** there too. The frontend client attaches whatever token it holds, so it should sign out first, which is allowed.
