## IR-722 — Submit and reopen one AI-owned research run

**Basis and scope.** IR-722 under IR-713; authority ADR-049 §1, §6, §10-12, §21. Run admission, terminal commitment and deletion fencing in the FastAPI runtime only: queue dispatch (IR-723), checkpoint recovery (IR-724), provider admission (IR-725) and real provider transport are not built. Additive: Django's `ai_askrun`/`ai_conversation` and every existing reader route are untouched, and no traffic reaches the new routes until a later cutover.

- **Reader identity.** A fourth grant purpose, `reader_session` (reader and credential generation, bound to no run, Conversation or Record), issued by `POST /api/v1/ai/runtime/grant/` (`SIGNED_IN` in the access matrix) because a submission has no run to bind a `reader_run` grant to. Migration `ai/0036` (SQL only) teaches the verifier the purpose and adds `iris_authz.reader_status(bigint)` (`active`/`inactive`/`gone`), granted to `iris_ai_runtime` alone by `provision_research_roles`. IR-718's policy reads no Record for the purpose. The AI runtime holds no signing key.
- **Ownership.** Schema `iris_ai` (`ai/runs/migrations/0001_runs.sql`) has one migration owner, `python -m ai.runs.migrate` (maintenance login; refuses a runtime login; records applied files in `iris_ai.schema_migration`; re-grants each run), and one writer, `iris_ai_runtime`. `iris_django_runtime` has no privilege on it; neither runtime owns a relation or may delete attempt accounting.
- **Routes** (`ai/api/runs.py`, service secret plus `X-IRIS-Reader-Grant`, verified by `begin_research` per transaction): `POST /api/v1/ai/runs` (`Idempotency-Key`; 201 new, 200 the same run; 409 `request_mismatch`, `revision_conflict` with the current revision, or `run_in_progress`), `GET /runs/<id>`, `POST /runs/<id>/cancel`, `GET /conversations/<id>` (reopen) and `DELETE /conversations/<id>`. Foreign and missing are the same 404; no grant, a forged or wrong-purpose grant is 401; unset limits are 503 `unavailable`.
- **Run contract** (`ai/runs/store.py`). Admission persists the deadline, the allowance (`max_attempts`, input/output tokens, cost), pinned executor/protocol/schema versions, a fence and a row version; one active run per Conversation (partial unique index). A claim takes a lease under a new fence and reserves one attempt in `attempt_accounting`; past `max_attempts` the run fails. `commit_final` locks Conversation then run and, in one transaction, writes the Turn, its citations, the Conversation revision and the terminal journal entry, or ends the run as `deleted`, `cancelled` (reader no longer active), `expired` or `conflict`. A superseded fence raises and writes nothing; an ended run stays ended. Stop moves the fence. Unreported usage keeps its reservation. A run past its deadline is ended `expired` by the next claim or the next admission on its Conversation, so a dead attempt cannot hold the Conversation.
- **Executor.** Only `DeterministicExecutor` exists (`RUNS_EXECUTOR` accepts nothing else); it runs between the claim and the commit with no connection open. All six `RUNS_*` limits have no default and none is approved: any unset refuses every submission.
- **Retention.** An owner's Conversation deletion sets `deleted_at`, ends active runs under a new fence, and removes questions, their request hashes, Turns, citations and journal in the same transaction. `python -m ai.runs.purge` does the same for every Conversation whose account no longer exists; a deactivated or locked account is fenced (grants refused, no commit) but its content kept. `attempt_accounting` carries no content and no foreign key and is kept.

**Tests.** `apps/ai/tests/test_ai_runtime_runs_db.py` (20, real PostgreSQL, a throwaway LOGIN role in `iris_ai_runtime`, Django-issued grants): a repeated submission is one run and one Turn, reopened; the deadline, allowance and pinned versions are persisted; one identity with another question is refused; another reader cannot inspect, stop, reopen, delete or follow up, with identical 404s; no, forged, wrong-purpose grant or service secret is refused; a stale revision is a 409 that a resubmission at the current revision resolves; a second run on a busy Conversation is refused; an overdue run is expired rather than holding its Conversation or being claimed; Stop fences a claimed run; unset limits answer `unavailable`; the executor runs with zero `iris-ai-runs` connections open; a constraint failure while writing the second citation leaves no Turn, no revision change and a `failed` run; two independent processes released together commit one Turn (3 rounds); Stop racing a commit in two processes yields exactly one terminal outcome (4 rounds); a superseded lease cannot publish and both attempts stay accounted; attempts beyond the allowance end the run; deletion fences reads, writes and a claimed run and keeps only accounting; deactivation fences and account deletion purges; the role and migrator boundary. `test_reader_session_grant_http.py` (6): issuance, no cross-purpose replay, no Record read, live revocation and `reader_status`, unavailable and anonymous. `ai/tests/test_runs_config.py` (9): fail-closed limits and executor. CI's backend job now also installs `ai/requirements.txt` so it runs the integration tests (`backend/requirements/development.txt` is unchanged: the backend image cannot see `ai/`).

**Migration evidence.** On a copy of the dev database (62 Records, 16 accounts): `ai/0034`-`0036` applied, `0036` reversed (`reader_status` gone) and re-applied; `provision_research_roles --check` ok; `ai.runs.migrate` applied `0001_runs.sql` then nothing; `iris_ai_runtime` may insert runs and `iris_django_runtime` may not read them; `ai.runs.purge` purged 0. The copy was dropped.

**Open decisions.** ADR-049 §6 says AI reader grants "require the actual run binding"; `reader_session` binds none, because a submission has no run yet. The owner chose this on 2026-11-01, but ADR-049 is not yet on `main`, so the amendment recording it is still to be written. The retention rule above lives here and in `ai/runs/store.py`, not in an ADR or deployment policy. `reader_status(bigint)` takes a raw account id: it reveals only active/inactive/gone, to `iris_ai_runtime` alone. The conflict check for ordinal follow-ups is the Conversation revision; shown-paper and selection state are not modelled in `iris_ai` yet.

**Not done here.** Execution is inline in the submit request, once; a crashed worker's run is recovered by IR-723/IR-724, not here. `iris_ai` has no row security: ownership is enforced by the store's queries on the verified reader. No reverse proxy routes browsers to the gateway, and the reader UI does not call these routes. The runtime opens one short connection per transaction (no pool). Nothing measures capacity.

**Status.** Implemented; awaiting review.
