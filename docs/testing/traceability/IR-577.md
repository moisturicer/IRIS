## IR-577 Save a private custom feed from Discover's filters

**Design:** no ADR decides saved feeds; [ADR-044](../../adr/044-account-backed-research-library.md) owns the private library they live in, and an amendment for saved feeds may be owed. The behaviour follows the IR-557 spec text (user stories 15 to 17, "Private manual custom feeds") and the decisions Lee Jasmin Adolfo recorded as comments on the IR-577 card on 2026-11-07. Jira is not a requirements authority, so the decisions are restated here:

- **Cap:** 10 feeds per account, one constant (`MAX_SAVED_FEEDS`). An 11th is refused with a 400, `code: feed_limit` and "You have 10 saved feeds. Delete one to save another.", and nothing is replaced silently.
- **Retention:** until the owner deletes the feed or the account is removed (the foreign key cascades). No expiry and no job.
- **Names:** required, at most 60 characters, unique within the account ignoring case (a database constraint on `Lower(name)` and the owner, with a friendly check in front of it).
- **No empty feed:** at least one of keywords, Area, college, type, year or IP filter. A sort alone does not count. The decision text said "Area, keyword, type or year"; college and the IP filter are criteria too, because the feed stores every Discover key, so the message names them.
- **Stale values: correction first.** A feed holding an Area, college or type that no longer exists is reported stale, its stored query is never rewritten, and the page holds its list back until the reader corrects it.
- **Placement:** one "My feeds" menu beside the For you, Latest and Trending tabs. No new main navigation entry and no public sharing.
- **Storage:** `SavedFeed` in `apps/library`, holding Discover's own URL keys (`q`, `type`, `college`, `classification`, `year`, `ip`, `sort`) so there is no second filter representation.
- **A single year, not a range.** The card's example said "years 2018 onward", but Discover filters by one year, so it is built as one year. A range is a separate Discover change (IR-947).
- **Every Discover key is stored,** including college and the IP filter, which the card's field list omitted. Otherwise opening a feed would silently show a wider list.
- **Save is offered on Latest and Trending only.** Trending is saved as sort "most viewed". For you is a personal ranking, not a catalogue query, and it ignores the search box.

**What was built**

- **Backend:** `apps/library/models.py` (`SavedFeed`, `MAX_SAVED_FEEDS`), migration `library/0002_savedfeed`, `apps/library/feeds.py` (validation and stale reporting), and `SavedFeedListView` / `SavedFeedDetailView` in `views.py` at `GET` and `POST /api/v1/library/feeds/` and `PATCH` and `DELETE /api/v1/library/feeds/<id>/`. The owner always comes from authentication; another account's feed id is a 404 identical to a missing one. The limit and name checks run under a row lock on the owner so two simultaneous saves cannot both pass. The values are checked against the taxonomy (`Classification`, `College`, `RecordType`), ids are stored sorted and once each, and the default sort is omitted, as Discover writes its URL. `GET` returns the stored query untouched plus a `stale` map, and the account's `limit`. Renaming never touches the criteria, so a stale feed can still be renamed, while replacing them re-checks every value. The routes are declared in the IR-615 access table with a `feed` world fixture, owner-only. Like saves, feeds are not in Django admin and write no audit event.
- **Frontend:** `store/feeds.store.ts` (cleared and fenced on every session change, written only with the server's say-so), `features/discover/MyFeeds.tsx` (the menu, the save form with the criteria in words and the match count, rename and delete behind a confirmation), saved-feed helpers in `discoverQuery.ts` (`feedQueryOf`, `feedSearchParams`, `sameFeedQuery`, `feedCriteria`), and `DiscoverPage.tsx` (the `myfeed` URL key, the open-feed bar, "Save these filters to this feed", "Leave feed", and the correction panel). Opening a feed is navigating to Discover with the stored query in the URL, so preview and results are the ordinary Discover list and cards. Until the reader's feeds are known, or while a correction is pending, the list is not fetched, so a stale feed's remainder never shows as if it were the feed.
- **Not built:** a year range (IR-947), public sharing, prompt compilation, and an ADR amendment.

**Tests:** `apps/library/tests.py` (`SavedFeedTests`) covers create, list, rename, replace and delete, removal with the account, name rules including the case-insensitive duplicate and the database constraint, the empty-feed refusal, every value being checked with nothing written on a refusal, the cap and room after a delete, stale Areas and colleges reported without the stored query changing, renaming a stale feed, the refusal to re-save a stale value, ownership in every direction including identical 404s, and two accounts on one client. `store/feeds.store.test.ts` covers loading once, refusals handed back with the server's reason, replacement by the server's answer, and dropping answers after an account switch. `MyFeeds.test.tsx` covers the menu states, opening, saving from Latest and Trending, refusals keeping what was typed, the For you note, the full-account message, rename, delete and axe. `discoverQuery.test.ts` covers the saved-feed helpers, and `DiscoverPage.test.tsx` ("saved custom feeds") covers opening a feed as the ordinary query, reload, a foreign feed id, holding a stale feed back, correcting it, saving changed filters into the open feed, leaving and deleting an open feed, and axe.

**Not verified here:** the backend tests, the access-matrix additions and the migration were written and compile, but were not run, because this machine has no Django or Postgres environment; `makemigrations --check` was not run either. They first run in CI. No `contracts/` fixture was recorded for the new list endpoint (that needs `UPDATE_CONTRACTS=1` against a database).
