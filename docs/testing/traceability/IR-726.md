## IR-726 — Stop and reconnect to the same investigation across worker races

**Basis and scope.** IR-726 under IR-713; authority ADR-049 §2, §11, §21 (amended by this ticket) and the ticket's acceptance criteria. The reader's lifecycle over the runs IR-722/723/724/725 built: Stop, reconnect and an explicit Retry. Not in scope: renewing a running run's grant (IR-880), and the foundational run, queue and accounting work.

**What already existed, found before adding anything.** Stop (`POST /runs/{id}/cancel`, `RunStore.cancel`) already commits `cancelled` and moves the fence in one transaction under the Conversation-then-run lock order; `commit_final`, `save_checkpoint`, `claim`, tool reads (`ResearchTools`) and provider admission (`Ledger.admit`, IR-725) already refuse a run that is terminal or on another fence. Reconnect already renewed a lapsed grant (`RunStore.status`). What was missing: a **journal cursor** for reconnect, an **explicit Retry** in the AI runtime (Django's AskRun has one, IR-548; `iris_ai` had none), and cross-process tests of Stop against a *takeover*, an *in-flight* request and the whole request/worker seam.

**Code.**
- **Reconnect cursor** (`ai/runs/public.py`, `ai/api/runs.py`). `GET /runs/{id}?after=N`, reader protocol only (406 without it, 422 for a negative or non-integer `N`). Every run view now carries `cursor`; with `after` it also carries `journal`, the ordered entries past `N`. A position counts only the entries the reader may see (not the operator's raw `sequence`), so neither `cursor` nor a gap between positions says how many tool calls, model attempts or recoveries happened. The journal is folded whole (`_Progress`) so the slice never contradicts the folded plan, context and compaction, and each entry is allowlisted: lifecycle names alone (`admitted`, `started` and the terminal states), plan (validated), context (validated, an estimate) and compaction outcome with a turn count. Tool calls, model attempts, recovery, reason codes, revisions and sources are never replayed. A run whose sources are no longer readable replays nothing (cursor 0). Ownership, Paper Chat scope and Conversation deletion are the existing `_owned_run` rules: a foreign, out-of-scope or deleted run is the same 404 as a missing one.
- **Retry** (`ai/runs/migrations/0016_retry.sql`, `RunStore.retry`, `RunService.retry`, `POST /runs/{id}/retry`). Migration adds `ask_run.retry_of` (nullable self-reference) and a partial unique index, so a run has at most one retry. Only the reader's own run, under a grant of exactly its Conversation's Paper Chat scope (else 409 `scope_mismatch`, nothing written), that ended `cancelled`, `expired` or `failed`, whose Conversation is still at the revision it asked against and has no active run, and which is not a compaction, may be retried (409 otherwise; 404 for foreign, missing or deleted). The new run is inserted like any submission: the queue bounds (`503 busy`), a fresh deadline, the configured allowance, a freshly computed pin and its own ledger key. The first run's allowance, attempts and reservations are not read, copied, reset or touched. Asking again, with the same key or another, returns the first retry (200) even if that retry itself failed — the reader then retries the retry, which the control offers because it is the latest run; a key already naming another request is a 409. Both runs publish `retry_of` / `retried_by`.
- **Edge** (`frontend/nginx.conf`): the runtime location regex admits `/runs/<id>/retry`. `?after=` already passes through.
- **Reader** (`frontend/src/api/runtimeReader.ts`, `RuntimeReader.tsx`): a "Try this question again" control for the latest run when it ended without an answer, was not already retried and the Conversation is unchanged; one click is one request (`Idempotency-Key` kept across a reconnect); a 409 reopens the Conversation and offers Reconnect. The existing Stop and Reconnect controls are reused untouched.
- **IR-608 compatibility.** The new tests are registered in `apps/ai/evaluation/scenarios.py` `SUITES` (`access_and_recovery` and `durability`), so `manage.py eval_scenarios --workers` records them in the existing text-free measured/not_measured shape, with no new scenario name and no change to the campaign gate. Documented in `docs/evaluation/general-tools/scenarios.md`.

**Not verified.**
- The wider backend suite and the frontend suite outside `src/features/ai` were not run locally; CI covers them.
- The migration was tested only by the fixture applying `0001`–`0016` to an empty `iris_ai` schema and by `python -m ai.runs.migrate` semantics (additive `ALTER TABLE` and a partial unique index, no backfill; existing rows get a null `retry_of`). It was **not** run against a copy of a realistic database, as CLAUDE.md asks; do that before deployment.
- The nginx location change is a regex edit that has not been exercised against a running nginx.
- `eval_scenarios --workers` was not run, so no IR-608 result file was produced; only the registration and the underlying tests are verified.
- Everything uses a scripted provider: nothing here measures paid capacity, throughput or answer quality, and no live provider was called.
- `RunStore._admit` and `_retry` repeat the admission INSERT and conversation checks; a shared helper was considered in review and left out unverified.
- Retry is offered for `cancelled`, `expired` and `failed` runs. A run that ended `conflict` (Conversation revision moved) is not retried — the reader asks again against the new revision. That boundary is a design choice of this ticket and not stated in ADR-049 before the amendment.
- The browser does not yet use `after`/`journal` (it reads the folded plan and context each poll); the cursor exists for a reconnecting client and is tested at the API only. No manual browser exercise was done.
