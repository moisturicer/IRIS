## IR-725 — Admit and account for every outgoing provider attempt

**Basis and scope.** IR-725 under IR-713; authority ADR-049 §8, §10, §11 (not yet on `main`) and ADR-041 (Proposed) for the ledger's semantics. Stacked on IR-720 (#436, in review). The AI runtime now admits each physical provider attempt in the ledger Django's admission already writes (`ai_providercampaign`, `ai_providerreservation`, IR-545) — one ledger, the same campaign row lock, reserve-worst-case and settle-to-reported rules, abandoned-lease handling and `AI_ADMISSION_*` limits. Additive migration `ai/0038` adds `owner` (`django`, the default for every existing row, or `ai`), `purpose` and `purpose_version`; `provision_research_roles` grants `iris_ai_runtime` SELECT and INSERT on the two ledger tables and UPDATE only on settlement columns and campaign totals (never DELETE, never a reservation's reserved figures). A run's ceiling is its persisted AskRun allowance, summed over every fence and every campaign, so neither redelivery nor a rotated campaign renews it.

**Code.** `ai/admission/` (`limits`, `ledger`, `guard`, `transport`, `scope`, `report`); `RunService.execute` binds the run and fence around the executor; `AgentExecutor` refuses a paid provider that is not admitted and maps refusals, timeouts and transient failures to `unavailable`; `AgentRequest.max_output_tokens` carries the reserved completion cap to the wire. `python -m ai.admission.report <run_id>` is the operator surface: purpose, version, model, state, reserved and charged usage, unreported attempts and the remaining allowance — no prompt, answer or opaque payload, because the ledger holds none.

**Tests.** `apps/ai/tests/test_ai_runtime_admission_db.py` (17, real PostgreSQL, restricted `iris_ai_runtime` login, Django-issued grants, recording provider): an answered run settles one `ai` reservation to reported usage with the cap it sent; a retry is a second admitted attempt and the failed one keeps its reserved charge; an unanswered attempt times out at its reservation; a dead worker's reservation is abandoned at full charge; unset limits, an unadmitted paid provider, an exhausted run allowance, the protected reserve (spent by a Django charge) and a Django attempt holding the shared lane each send nothing; Stop and access revoked between admission and send release the attempt unsent; a provider without a no-training policy and tool results carried in a request are withheld by the transport; redelivery under a new fence still counts the earlier fence's attempt, and the stale fence admits nothing; the runtime login cannot rewrite a reservation; two independent processes racing for the last campaign attempt admit exactly one. Migration `0038` applied to a copy of the dev database (200 existing reservations, all `owner = 'django'`).

**Not done here.** The AI runtime has no disclosure decision of its own, so its guard withholds any payload built from Record evidence rather than authorize it; IR-720's guard covers Django only. No streaming caller exists, so there is no lease renewal on the AI side. Row ownership is not enforced in the database: the runtime may settle or abandon any row's settlement columns, as Django's sweep also does. A settlement lost to a doubly cancelled task stays open and is abandoned at full charge. The race test pits two AI workers; Django against AI is exercised through shared limits, not a concurrent race. Embedding and reranking have no AI-runtime caller (ADR-024 keeps embedding in Django, already admitted by IR-545); repair and compaction callers belong to their own tickets. The gateway's legacy `/api/v1/ai/ask` path is not admitted and stays undeployable (ADR-014). No route builds the agent executor, no live provider was used, and no limit is approved.

**Status.** Implemented; awaiting review.
