# IR-1028: Admin actions confirm in ConfirmDialog and report in a toast, not confirm() and alert()

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** no FR- id. Epic IR-518 (S2 Epic: Frontend). Relates to IR-1077 (Users: Lock behind a confirm that names the person), which set the pattern.

## What changed

- **Three native prompts are gone.** Approving a delete request (`DeleteRequestsPage`), approving a download request (`DownloadRequestsPage`) and revoking a session (`SessionsPage`, which also used `alert()` on failure) each ask in `ConfirmDialog`. The dialog names the paper and the person (the requester, the reader, or whose session it is), and says what will happen. Delete approval and Revoke use the destructive button; approving a download is not destructive, so it uses the primary one. Cancel is focused first, and `Modal` returns focus to the button that opened the dialog.
- **The result is a toast, success or failure.** A refusal shows the server's own reason through `errorDetail`, with the old sentence as the fallback only when the server gave none. The inline error banner on the two request pages is removed, since a toast replaces it.
- **In flight.** The dialog's confirm button is disabled and reads "Please wait…", and Cancel is disabled, so the action cannot be sent twice. The row buttons no longer carry their own "Deleting…" / "Approving…" / "Revoking…" label, because the open dialog covers the page.
- **`no-alert` is an ESLint error** for `src/**` outside tests (`eslint.config.js`), so a native prompt cannot come back. A probe file with `confirm()` and `alert()` failed lint; removing it restored a clean run.

## Tests

- `DeleteRequestsPage.test.tsx`, `DownloadRequestsPage.test.tsx`, `SessionsPage.test.tsx`, each with: the dialog opens and names the paper and person (axe clean) without calling `window.confirm`; Cancel calls nothing, shows no toast and returns focus to the trigger; confirm calls the API once, shows a success toast and reads the list again (Sessions drops the row); the buttons are disabled and labelled while in flight; a refusal shows the server's reason in an error toast (Sessions also asserts `window.alert` is never called).
- No existing assertion was changed. The mocks gained resets, and `approveDeleteRequest` / `revokeSession` became resettable mocks so they can be asserted.

## Evidence

- Run locally 2026-11-15: `tsc --noEmit` clean; `npm run lint` no errors (two warnings in files this change did not touch); the three admin test files plus the rest of `features/admin` passed; the full frontend suite passed once (216 files, 3,020 tests); `npm run build` completed. CI runs the whole suite.
- **Not checked:** a browser, a screen reader on the dialogs, or a real server refusal.
- **Left as they are, on purpose:** Decline (Delete and Download) and Revoke (Download) still use `RdcoNoteDialog`, which asks for a note the requester is sent and already shows its failure inside the dialog; the ticket names approve and revoke-session only. After a successful approval the row leaves the Pending list, so the trigger no longer exists and focus has nowhere to return to; Cancel and a failure return it. `SessionsPage` is unrouted, so it is verified by unit tests only.
