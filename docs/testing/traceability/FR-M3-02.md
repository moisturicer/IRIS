## FR-M3-02

**Requirement:** Semantic indexing

**Design:** ADR-013 (§Decision "Retrieval scope," amended 2026-09-08), ADR-007, ADR-015

**Implementation:** `apps/ai/chunking/` (domain, strategies, context path, normalizer, regions, re-chunk diff) · `apps/ai/repositories.py` (ChunkSet persistence; atomic swap behind the `one_active_chunk_set_per_record` partial unique index; incremental re-chunk with vector carry-over and `deleted_at` tombstones) · `apps/ai/ingestion/` + `models/ingestion_job.py` (lifecycle transition table, hash-derived staleness, job idempotency key) · `apps/ai/ingestion/pipeline.py` + `ai.tasks.chunk_extraction`, queued through the single `documents.tasks._queue_chunking_if_manuscript` guard that both extraction tasks call — IR-89 A–H, rescoped to the manuscript only by IR-195, and keyed on `PdfExtraction.kind` rather than on which task ran by IR-239. **IR-131 / [ADR-036]** add grounded answers with citations. Adapters key on the **wire protocol, not the vendor**: `OpenAICompatibleAdapter` serves Groq (development), OpenRouter (production), OpenAI, vLLM and Ollama alike, so switching vendor is a `.env` change with no new code. **Anthropic is not used** — it had been chosen in an import statement rather than a decision record, was never declared as a dependency, and so silently degraded every environment to extractive answers; `ANTHROPIC_API_KEY` and `AI_LLM_MODEL` are removed. Prompt assembly numbers sources deterministically and `apps/ai/answers/citations.py` parses the markers back to chunk, record and page, **dropping any marker outside the supplied range** — a citation pointing at nothing reads as evidence. The marker pattern accepts the CJK lenticular (`【1】`) and fullwidth bracket forms as well as `[1]`, and re-emits `[n]`: the configured default model, `openai/gpt-oss-120b`, cites in the lenticular form, and against the original ASCII-only pattern **every** citation on the real vendor resolved to nothing — zero citations, `is_grounded` false, and the raw marker rendered into the answer. `LLM_MODEL` itself was `llama-3.3-70b-versatile`, which Groq has withdrawn, so every call returned 404 while `/api/v1/ai/status/` still reported generative mode; the model id is corrected here.

**IR-252** is that reporting gap, re-scoped 2026-09-21 once IR-285 deleted the extractive lane it was originally filed against (`GroundedAnswerService`'s `UNAVAILABLE` state on vendor failure was already covered by `test_service.py::VendorFailureTests`, unchanged here) and **closed for `/api/v1/ai/status/`** on 2026-09-28: `CompositionRoot.generation_configured()` no longer reports `generative: true` from a key string alone. Past `is_configured()`, it asks the new `apps.ai.resilience.llm.any_provider_reachable()`, which reads the IR-321 circuit breaker already kept for each configured provider — a breaker only trips after a real `generate()` call actually failed against it, so an open one is evidence the vendor is down rather than a guess from the key. The one configured provider's breaker has to be tripped for this to report `False` (IR-385 deleted the second-vendor entry this used to walk). The disclosure gate runs before the prompt is built, because an LLM call always leaves the deployment; a vendor failure returns an explicit unavailable state with the sources still listed, never a fabricated answer (ADR-008).

**IR-132** adds the resilience stack in `apps/ai/resilience/`, composed *around* the ports rather than inside the adapters — an adapter that retries or breaks its own circuit cannot be tested for the failure it hides. A circuit breaker with an injected clock (every transition testable without sleeping), bounded retry with backoff that never retries a rate limit, and a **Redis** token bucket rather than a process-local counter: the reference implementation ADR-015 borrows from counts in process memory, which is correct with one process and wrong with four. Separate ingestion and query budgets are the bulkhead, with the query lane given the larger share because a person is waiting on it. Query embeddings cache on normalized question text **plus the embedding space id** — mandatory, since a vector cached under a retired space and served against a current index is a cross-space comparison that survives a redeploy. `apps/ai/retrieval/degraded.py` degrades an open circuit or spent budget to chunk-level FTS through the *same* `visible_to` predicate, not `publicly_visible()`, so the answer does not depend on whether the vendor was up; the result carries `degraded` for a caller that wants to say so — as a field on the frozen `RetrievalResult` since **IR-279**, not on the `list` subclass it originally rode on, which every decorator stripped.

**IR-320** classifies a vendor failure by *kind* (`auth`, `rate_limit`, `network`, `timeout`, `context_overflow`, `unknown`) rather than by exception type alone -- `LLMUnavailable`/`VoyageError` stay the one exception type per vendor (the anti-corruption boundary is unchanged) but now carry `.kind`, read from the vendor's own HTTP status or SDK exception class first and a closed message-heuristic fallback only when the vendor gives nothing better. `DegradableRetriever`'s `degrade_on` became a predicate rather than a hand-maintained exception-type tuple, because a single `VoyageError` can be either an outage worth degrading past or a bad key that fails identically against full-text search -- `composition._vendor_failures()` degrades only on `rate_limit`/`network`/`timeout`, never `auth`, so a misconfigured key surfaces as an error instead of a quietly worse answer. `retry_with_backoff` gained `give_up_on_kind` for the same reason, unwired to a call site yet (retry counts and the circuit breaker's threshold are the next ticket's).

**IR-321** is that ticket: `apps/ai/resilience/llm.py` wraps `LLMProvider` in `RetryingLLMProvider` (retries only `network`/`timeout`, bounded to 2 attempts total -- not `retry_with_backoff`'s own default of 3, because a person is waiting on this call) and `CircuitBreakingLLMProvider`, composed the same way `apps/ai/retrieval/degraded.py` composes around `Retriever`. The breaker is process-lifetime and keyed by provider identity (`breaker_for`), not built inside `CompositionRoot.llm()` -- `composition_root()` returns a *new* `CompositionRoot()` per call when nothing is installed, so a breaker built there would never accumulate a failure past the request that saw it. `FallbackLLMProvider` switches to the next model in the list on `rate_limit`/`network`/`timeout` and gives up immediately on `auth`/`context_overflow`/`unknown`, recording which model actually answered on `.last_model_used` -- read by `GroundedAnswerService` onto `GroundedAnswer.model`, since ADR-023's recall measurement assumes one model per run and a silent fallback to a different one is exactly the confound that cannot survive undetected. **The contradiction IR-321 recorded here is resolved by IR-376**, which amended both ADRs on 2026-09-28: [ADR-008](../../adr/008-ai-degradation-to-fts.md) §Amendment permits a fallback list of models **inside one vendor account** and confirms cross-vendor failover stays rejected, and [ADR-036](../../adr/036-openai-compatible-inference-provider.md) §Amendment replaces "one provider per environment" with one adapter per protocol and the **vendor chosen per Inference task** — two vendors serving two different tasks is not failover. **IR-385 made the code match**: the `LLM_FALLBACK_*` second vendor is deleted rather than disabled -- settings, `cross_vendor_fallback_config()` and the config it built are gone, and setting one of those variables now refuses startup (`apps/ai/inference/startup.py`'s retired-namespace rule). What remains is a Profile's ordered `LLM_<TASK>_FALLBACK_MODELS` on one account, and who walks it is the vendor's dialect's to say: IRIS loops one request per model for Groq, and hands OpenRouter the whole list in its native `models` field for one request (`VendorDialect.resolves_fallback`). **IR-386 changes what `breaker_for` is keyed on**: `build_task_llm` (`apps/ai/resilience/llm.py`) replaces `build_resilient_llm` for a Profile's own list, wrapping the whole thing -- one model or several -- in a single breaker keyed on the Inference task (`InferenceTask.breaker_key`) rather than on `base_url::model`, so two tasks pointed at the same vendor and model no longer share one; a busy `summary` run tripping its own breaker leaves `answer` untouched. Because the breaker now sits above `FallbackLLMProvider` rather than around each candidate inside it, a switch-worthy failure handled by moving to the next model never counts against the breaker -- only every model in the list failing within one call does, which is the ticket's "not the first model's failure" rule (`apps/ai/resilience/tests/test_llm.py::FallbackExhaustionOpensTheBreakerTests`). `reset_llm_breakers()` needed no change to keep clearing every task's breaker between tests, since it already clears the whole registry regardless of key shape. Exhausting the list raises, which the answer path renders as the explicit unavailable state with the sources still returned (ADR-008). Evidence: `apps/ai/inference/tests/test_fallback.py` (the Groq walk, the kinds that stop it, the OpenRouter delegation, and that no second vendor is reached when every model fails). **IR-388 (M · Contract) deletes the untasked accessor those tickets built around**: `CompositionRoot.llm()` and its `_default_llm` cache are gone, so `llm_for(task)` is the only way any caller reaches a model. `build_resilient_llm()` and `_wrap()` (`apps/ai/resilience/llm.py`) go with it -- `llm()` was their last production caller, and every Inference task already reached its model through `build_task_llm` instead (IR-386); `_configured_providers()` stays, because `any_provider_reachable()` still reads it for the flat account `answer` inherits. `apps/ai/tests/test_llm_access_is_tasked.py` fails if the accessor comes back, via `hasattr(CompositionRoot, "llm")`. Django had **no** `CACHES` at all before this, so `django.core.cache` was per-process local memory — the same defect the rate limiter exists to avoid.

**IR-130** wraps retrieval in `RerankingRetriever`, a decorator rather than a change to the retriever, so IR-129's visibility guarantee stays a property of one place. Recall is widened to ~100 candidates before reranking, because reranking what stage 2 already narrowed improves nothing. The **disclosure gate is applied before the reranker is called, never to its output** — filtering afterwards means the text has already left the deployment — and only when the reranker actually transmits, declared as `Reranker.transmits_externally` rather than inferred, since `NoOpReranker` makes no outbound call and gating it would cost recall to protect nobody. Rerank results cache on question plus candidate id set, so the same question over a changed corpus is a different entry; the Redis-backed replica-safe cache is IR-132's.

**IR-129** adds the `Retriever` seam in `apps/ai/retrieval/`: stage 1 ranks records on the summary-level `RecordEmbedding` **with `Record.objects.visible_to(user)` applied before anything is scored**, stage 2 ranks chunks belonging only to the records stage 1 kept. Retrieval runs in Django, never the gateway (ADR-014 precondition 4), and reuses the one visibility predicate `RecordViewSet` already applies on every action (IR-153) rather than growing a second — ADR-014 rejected that on the grounds that two definitions of who-can-see-what will drift, and the drift is a confidentiality breach. The headline suite asserts at the seam that a chunk the asker cannot read is never returned, across every ground `visible_to` distinguishes (stranger, owner, office staff, assigned adviser vs. the adviser role alone, public catalogue, anonymous), plus that a permitted record ranking beside a forbidden one does not carry it along — the case that catches filtering *after* scoring. It runs against a deterministic offline embedder, because a security test that only runs where a paid API key is configured does not run.

**IR-280** makes the Embedding Space the only thing in IRIS that names an embedding model: the `AI_EMBEDDING_MODEL`/`AI_EMBEDDING_DIMENSIONS` settings family is deleted, and with it the third disagreeing opinion about one number — 1536 in settings, 1024 in `VOYAGE_EMBED_DIMENSIONS`, and `all-MiniLM-L6-v2` in `.env.example`. Both vector columns were `vector(1536)`, a literal frozen into migration 0002 and then copied into 0004 — the hardcoding ADR-015 introduced `EmbeddingSpace` to remove, reintroduced by the newer migration. **`voyage-context-4` emits 2048, 1024, 512 or 256 dimensions and never 1536**, so every write of a real vector would have failed. Migration `0007` writes the `voyage-context-4`/1024/cosine space first and then reads the column width back *off that row*, so nothing in it names a dimension twice; the one number the schema still has to declare in Python lives as `apps.ai.models.VECTOR_COLUMN_DIMENSIONS`, because a column width is a schema fact and cannot follow an environment variable. The superseded space is **retired, not deleted** — `ChunkEmbedding` points at a space with `on_delete=CASCADE`, so deleting one takes its vectors with it. Vectors from a superseded space *are* deleted, deliberately and irreversibly: a 1536-vector cannot be cast into a 1024 column, and a vector from a model IRIS no longer calls is not comparable with one from the model it does. That is free today, when neither table holds a row, and a full re-index after IR-281 — which is why this is sequenced ahead of it. `VOYAGE_EMBED_DIMENSIONS` goes too: what the adapter asks Voyage to emit and what the column can hold are one number, and while they were two settings `VOYAGE_EMBED_DIMENSIONS=512` would have produced 512-vectors for a 1024 column — the same bug one hop along. **Two contradictions recorded rather than reconciled.** First, migration 0003's `RunPython` body is edited, against CLAUDE.md §Migrations' "never edit an applied migration" and `docs/engineering/DEVELOPMENT.md` §94's "supersede it": the settings it read are deleted, so left alone it raises on every fresh database, and the frozen literals reproduce byte-for-byte what it seeded. No applied database re-runs it. Second, `ai.tasks.embed_record` still posts to the gateway route ADR-024 records as non-existent; IR-280 changed only the `model_name` label it writes, because the setting that supplied it is gone, and replacing the call with the `EmbeddingProvider` port is IR-281's work. **The deletion of superseded vectors is deliberate, irreversible and more than the ticket asked for — it wants a reviewer's explicit sign-off.**

**IR-281** computes the first chunk vectors IRIS has ever held, and takes the indexing path off the AI gateway (ADR-024). Two defects, both of which had hidden behind the fact that nothing on this path ever produced a vector. The adapter posted to the flat `/embeddings` endpoint, which serves the *standard* models: `voyage-context-4` is a **contextualized** chunk embedder served from `/contextualizedembeddings`, and its entire value is that a chunk is embedded with its sibling chunks from the same document in view — flatten that and "this approach reduced error by 12%" stops meaning anything once retrieved alone, while the vector itself still looks perfectly well-formed. `EmbeddingProvider` grows `embed_document_chunks`, which takes chunks **grouped by document** and returns vectors in the same shape; `embed_documents` and `embed_query` now route through the same endpoint, each text as its own one-chunk document, so there is one wire format rather than two to keep in step. The batching unit becomes the document — `batch_documents_by_token_budget` never splits one, because half a document's chunks in view is not the context the model was chosen for. `tasks.embed_record` stops posting to `{AI_GATEWAY_URL}/api/v1/ai/internal/embed/`, a route the gateway never registered at an endpoint whose `EmbedResponse` carries no `embedding` field, and embeds in-process through the port; a test walks every module under `apps/ai/` and fails if any reads the gateway URL, so the deployment promise is asserted rather than trusted. `apps/ai/indexing.py` is the new seam both tasks and IR-282's backfill share: it checks the active `EmbeddingSpace` against the vector columns **and** against the provider's own width, applies the disclosure gate, and confirms there is something left to embed — all **before** a metered call, since a vendor call that turns out to have been unnecessary is the cheapest bug to prevent and the hardest to spot afterwards. Vectors are keyed by chunk **and** space; "already has a row in this space" *is* the unchanged-text skip, reusing the carry-over the repository already does rather than inventing a second definition of unchanged. `ai.tasks.embed_chunk_set` runs it on the `embedding` queue and `chunk_extraction` queues it whenever a run wrote a new active chunk set, so an upload reaches vectors with no manual step. **One limitation recorded rather than reconciled:** the disclosure gate refuses **every** record today, because `Record` carries no embargo field and an undetermined embargo is treated as an embargo (IR-250) — the correct failure direction, and the reason a real corpus cannot be indexed until that ticket lands. Nothing here works around it; the way past a fail-closed gate is to supply the missing fact. A second, smaller trade: an incremental re-chunk sends only the changed chunks, so their context is the changed passages rather than the whole document, because restoring full context means paying for every chunk — `force=True` chooses the other trade.

**IR-282** makes indexing a corpus an operator command with the bill shown first, and makes promotion a separate, refusable decision. `manage.py backfill_embeddings` walks Records, prints a pre-flight estimate of chunks, tokens and approximate cost, and **refuses to start** when the estimate exceeds `AI_EMBEDDING_TOKEN_CEILING` — a live risk rather than a theoretical one, since `AI_CHUNK_MAX_TOKENS` counts whitespace words and undercounts real BPE tokens by roughly 44% (IR-243). It is **resumable and idempotent by construction, not by a checkpoint file**: what it embeds is "active chunks with no vector in this space", recomputed each run, so a crash at record 3,000 resumes there and bookkeeping cannot be lost in the same crash that made it necessary. `--queue` hands each record to `ai.tasks.index_record` on the `embedding` queue with one `EmbeddingJob` per record, so a failed record records why; inline, a record's failure is reported and the run continues, leaving it pending for the next one. **The 4,910 placeholder uploads are skipped by construction** — sixteen bytes of `%PDF-1.7 fake bytes` never extracted, so they have no chunk set — and are *counted and named* in the report, because five thousand silently absent records look exactly like a broken run; nothing deletes them. `manage.py promote_embedding_space --space N` is the second half and is deliberately a separate command: it **refuses while any active chunk lacks a vector in that space** and lists which records are short and by how much, retires the superseded space rather than deleting it (vectors point at a space with `on_delete=CASCADE`), and promotes nothing automatically. `--space` on the backfill fills a **pending** space so it can be promoted once complete; **recorded limitation** — that mode writes chunk vectors only, because `RecordEmbedding` is one row per record with no space key, so a summary vector cannot exist in two spaces at once. **Review pass on IR-281/IR-282** closed four gaps the two-axis review found. A record whose chunks are all embedded but whose **summary vector** is missing was never walked again — stage 1 ranks records on `RecordEmbedding` before stage 2 ranks chunks within them, so such a record is invisible to retrieval however complete its chunks are; the plan now counts summaries owing, gated on the record having chunks at all so the 4,910 placeholders do not walk straight back into the run the stub skip keeps them out of. An **inline failure is now written to an `EmbeddingJob` row**, not only printed: a terminal that is then closed is not a record of anything, and the ticket asks that a failed per-record job say why. **Promotion refuses a retired space and a space of the wrong width**, not only an incomplete one — `indexing._checked_space` already refused to *write* to a retired space and the two disagreed about the same row. The partial-context trade-off on an incremental re-chunk is now carried as `EmbeddingOutcome.partial_context` rather than living only in a docstring, because partly-contextualized vectors are indistinguishable from fully contextualized ones. "A record's active, non-deleted chunks" was written out four times and is now one `indexing.active_chunks()`; four copies of a predicate that decides what a run pays for is a bill, not a wrong number.

**IR-128** adds the query lane's vendor seams in `apps/ai/providers/`: an `EmbeddingProvider` with `embed_documents`/`embed_query` as separate methods (ADR-015 rule 3 — a boolean flag makes the wrong asymmetric call possible), a `Reranker` port with `NoOpReranker` as the production default so IR-133 can measure reranking's value by configuration rather than by code path, and the Voyage adapters for both. Batching enforces ADR-015's **token** budget rather than an item count; since

**IR-287** it counts with the same tokenizer the chunker uses rather than a words-times-1.4 factor, so there is one definition of a token on both sides of the seam. Deterministic hash-based fakes keep the whole lane testable without a vendor account, which matters because IR-129's retrieval tests are the security tests. The empty `cohere_reranker.py` and `vector_retriever.py` prototype stubs are deleted — ADR-015 rejected Cohere on one-vendor grounds.

**IR-249** aligns the two timeouts governing one Docling conversion: the worker waited `DOCLING_TIMEOUT_SECONDS=900` while docling-serve, with `DOCLING_SERVE_MAX_SYNC_WAIT` unset and so at its own default of 120, abandoned the request and returned 504 — the server's cap being the binding one. A 45-page submission converts in about a minute alone, so every single-document run passed and **bulk ingestion failed entirely**, with the API returning 201 either way. `apps/tests/test_docling_timeouts.py` reads both Compose files and fails if the two values disagree, because the extraction tests run against a fake extractor and cannot observe container configuration — the blind spot that also let IR-240 ship green.

**IR-248** stops an unnumbered heading evicting the numbered section it belongs to: Docling promotes a great deal to `section_header` that carries no number — 61 of 92 headings on a real SRS — and at level 1 each displaced its parent, so `1.3` and `1.4` were trailed to a bullet-list lead-in rather than to `1. Introduction`. An unnumbered heading now sits one level below the deepest numbered entry open. Recorded trade-off: a trailing unnumbered section such as an appendix is nested under the last numbered section instead of beside it, which the numbering-sequence check IR-242 also wants would resolve. Depth on record 30 moved from 54/20/1 across depths 2/3/4 to 8/18/34 plus 15 at depth 5, with record 29 improving too and not regressing.

**IR-314** teaches the outline reader the two numbering styles it did not know: roman-numeral sections (`I.`, `IV.`) and lettered subsections (`A.`, `E.`), which is how most scientific papers number and which matched nothing, so every heading in such a paper reported "no depth" and the whole document flattened — all 717 chunks of the corpus at path depth 2. The recognition moves into the domain as `chunking/numbering.py`, which `docling_mapping.py` now imports rather than duplicating by shape, and which reads the whole heading *sequence* rather than one heading: `I`, `V`, `X`, `L`, `C`, `D` and `M` are simultaneously letters and roman numerals, so `C. Committors` between `B.` and `D.` is a subsection while the same string opening a paper is section 100, and only the run it does or does not continue tells them apart. A letter's depth is relative to the numbered section open above it — depth 2 under `I.`, depth 3 under `3.2` — or it would evict its own parent. Dotted decimals are unchanged and asserted so, and the decimal false positive IR-242 recorded (`3.5 kg of Feed`) is neither widened nor narrowed: both new styles require a separator a measurement does not have.

**IR-241** folds a heading-only chunk forward into the section it labels: `_sectionize` opens a section at every heading, so a heading whose first child is another heading formed a section of one element that section-scoped merging could not reach, and a real 47-page submission produced six such 2–3 token chunks. The fold is the one narrow exception to “never merge across a heading” (IR-89 user story 21) and is scoped to chunks carrying no content — a label rather than a topic; two sections that both have a body still never merge. Because a chunk can now span a heading, `context_path.py` takes the trail at a chunk’s *last* word rather than its first, without which the fold would have silently made the path less specific than before. `PdfExtraction` keys on `upload` *or* `record` (`resolved_record_id`) and carries an explicit `kind` (manuscript/supplementary, defaulting to supplementary so an unmarked row stays out of the corpus); both creation sites — `SubmitDocumentView` and `RecordViewSet` — set it explicitly

**IR-247** detects running furniture by repetition across pages rather than by the extractor's label: Docling labelled the same footer `page_header` 18 times and `paragraph` 27 times in one document, and the 27 survivors reached 20 of 75 chunks. Eligibility is deliberately narrow — short `PARAGRAPH` elements only, counted by *distinct pages* — so a repeated table header, which IR-111 works to preserve in every fragment of a split table, can never be swept up.

**IR-245** emits the captions Docling hangs off `#/pictures/N` and `#/tables/N`: `_items_in_reading_order` walked `body.children` only, so on a real 45-page SRS 13 of 15 captions were dropped — including `Figure 1. - IRIS System Flow Diagram` in a document carrying 33 figures, whose captions are the only retrievable text a figure has. Each caption keeps its own `prov`, so a citation highlights the caption rather than the whole image, and the existing `seen` set keeps a caption listed in both places from being emitted twice. docling-core's own `HybridChunker` retains 11 of the 15 on the same document; this retains all 15.

**IR-242** derives heading depth from a heading's own section numbering in `extraction/docling_mapping.py::_level` (`3` → 1, `3.2` → 2, `2.1.1` → 3), applied as a floor and never a ceiling: Docling reports `level` 1 for every `section_header` — all 74 on a real 47-page submission — so `context_path.py`, which evicts everything at level >= N, collapsed to a depth-1 trail on every chunk. Confirmed not IRIS-specific: docling-core's own `HybridChunker` flattens the same document identically.

**IR-244** makes section exclusion compare headings with their section number stripped and whitespace collapsed — the old whole-text match never fired on a numbered heading, so both real CIT-U submissions kept their bibliography.

**IR-246** adds the navigation indexes (`Table of Contents`, `Contents`, `List of Tables`, `List of Figures`) to the shipped exclusion default, answering the front-matter half of IR-116's open question from the same run: a table of contents holds every section name and none of their content, and ranked within 0.005 of the correct answer on an FTS query against record 30. The title block is deliberately still chunked — it carries the document's identity; acknowledgements remain undecided, neither test submission having one.
