## IR-724 — Resume a worker-interrupted investigation without restarting its allowance

**Basis and scope.** IR-724 under IR-713; authority ADR-049 §12, §14, §20 and the ticket's acceptance criteria. Step recovery for the real AGENT loop (IR-728/IR-729). Before this, a run whose worker died was reclaimed after its lease and started its investigation again from nothing, with a fresh in-process budget. Compact-state recovery is IR-734's; Stop races are IR-726's.

**Code.**
- **Checkpoint table** (`ai/runs/migrations/0013_checkpoint.sql`, granted in `ai/runs/migrate.py`). `iris_ai.run_checkpoint` holds one row per running run: the fence that wrote it, the step and the body. It is content, so `RunStore._end` deletes it when the run ends for any reason, and Conversation deletion ends active runs first. The pinned `state_version` stays `0004_agent.sql`: the change is additive and no run's interpretation moves.
- **What a step saves** (`ai/agent/checkpoint.py`). After each completed gathering step (a model turn plus every result of its tool group, after context packing), the executor saves: the whole ordered Conversation as typed entries, with stable call ids and any opaque continuation artifact unread under its binding; the Investigation's source pointers (passage handles with their Source revision, paper handles, exact counts with their counted Records, focus, plan and its revision, seen evidence, tool calls made); the task key (a digest of the question, the prior Turns and the Conversation state); the pin and the Bounds; the steps taken and the no-progress count; and the budget spent. A final, repair or clarification turn is never saved: a takeover then repeats it as a new attempt.
- **Fenced writes** (`RunStore.save_checkpoint`). One transaction: the run must be `running` under the caller's fence and before its deadline, or it raises `Fenced` and writes nothing; it renews the lease by `RUNS_LEASE_SECONDS`, and a step never goes backwards. The executor ends a run whose save is fenced (`run_ended`) before sending anything more. Admission (IR-725) and `commit_final` already refused an old fence; a test now proves all three for one delayed worker.
- **Resume** (`ai/agent/executor.py` `_resume`). A claim carries the checkpoint and the tokens the shared ledger has charged the run over every fence (`RunStore._claim`, from `ai_providerreservation` by `run_key`). The executor restores a checkpoint only if its format, pin, Bounds and task key match this run and every tool group in it is answered in order under this pin's binding. It then reauthorizes every recovered handle under the run's grant, scope and fence (`ResearchTools.reauthorize`: each handle still resolves to the source it was issued on, each passage still exists, every counted Record is still readable; nothing journalled). A match is journalled `recovery` `resumed`; otherwise `rebuilt` with `incompatible` or `stale`, and the investigation starts again from the question and the Conversation. A grant that no longer verifies ends the run. Restored evidence confers nothing: the answer is still checked and its sources rechecked before delivery.
- **No allowance reset.** The in-process budget starts at what the ledger has charged, attempts and tokens (an uncertain attempt counts at its reservation), raised to the checkpoint's if larger; the checkpoint records its own attempts too. The steps a checkpoint saved stay taken even when the investigation is rebuilt. A step that was never saved (killed after its response or tool result) is repeated and its step number reused, so step and tool-call Bounds are preserved up to the last saved step, while its tokens and attempts stay charged in the ledger. The ledger's per-run ceiling already counted every fence (IR-725). Recovery guarantees at most one Turn, through the fence on `commit_final`; it does not guarantee exactly-once billing: a repeated step is a separately admitted physical attempt, and the attempt a dead worker never settled keeps its reservation.
- `Investigation.results` (a list kept only to be counted) became `reads`, an integer, so it can be saved.
- **A rebuild's dependencies** (`ai/runs/store.py`). A rebuilt run's Turn depends only on the tool sources read after its last `recovery` `rebuilt` event, both in `CURRENT_SOURCE_TURN` (reopen) and in the run projection. Before this, the dead worker's sources stayed listed, so a rebuild after a stale source reopened as "sources changed" although its answer never used them.

**Tests.**
- `apps/ai/tests/test_ai_runtime_checkpoint_contract.py` (no database, recording provider, the IR-728 in-memory corpus): a replacement sends exactly the Conversation the dead worker was sending, with call id `c-1`, its opaque artifact and its tool result, searches nothing again, reauthorizes both handles, cites the restored passage and continues at step 2; ledger spending at the allowance refuses any further attempt, with or without a checkpoint; a replaced source rebuilds from the question with the step kept and nothing recovered sent; a lost fence sends nothing more; seven ways a checkpoint is not this run's (format, pin, Bounds, task, an unanswered call, a foreign artifact binding, a malformed body) are refused and rebuilt; counts, focus, plan and seen evidence survive a JSON round trip.
- `apps/ai/tests/test_ai_runtime_recovery_db.py` (real PostgreSQL, restricted runtime login, Django-issued grants). IR-725's guard withholds every request carrying a tool result from a paid provider (`ai/admission/guard.py`), so an admitted run never sends after a completed step; the tests are split accordingly.
  - *Unadmitted* (`ai.tests.agent_worker.unadmitted`: as `ai.runs.worker.build`, with the AGENT executor sending to the recording provider without admission; `spec["admitted"] = false` for the independent worker). An independent worker process is killed outright with `os._exit` after a provider response, after a tool result, just before a checkpoint commit and just after one. In each case the in-process replacement restores step 1 with call `s1` and not `s2`, continues at steps 2 and 3, delivers one Turn, keeps the original deadline, allowance and pin, holds no runtime connection during either inference, and leaves no checkpoint. A source rewritten after the checkpoint, and a Record deleted after it, each rebuild from the question with no recovered content sent; the rebuilt Turn reopens with its citation and `sources_available` true, and false once the source it did read is rewritten. Two replacements racing for one interrupted run answer it once.
  - *Admitted, real ledger and guard*. Killed after its first provider response (the one kill point an admitted run reaches with nothing saved), with `max_attempts = 2`: the replacement starts over, gets exactly one attempt, and the run ends `unavailable` with no Turn; the dead attempt stays `open` at its charge and nothing is released. Killed just after its step-1 checkpoint: the replacement resumes step 1 and its next request is withheld (reserved, never sent), so the run ends `unavailable` with no Turn and the dead attempt stays charged. A delayed worker that lost its lease can neither save, admit nor commit, and the new holder commits once.
- `apps/tests/test_parallel.py`: `test_ai_runtime_recovery_db.py` is registered in `testing/parallel.py`'s `ROLE_MODULES`, so it shares the Postgres role scope.
- The shared fixture's TRUNCATE list adds `iris_ai.run_checkpoint` (a fixture change, no assertion weakened).

**Evidence (2026-11-04).** Tests not run locally: this machine has no Python environment with the backend's dependencies, and by the team's standing rule CI is the gate. The changed files compile (`python -m py_compile`). CI results are recorded on the PR.

**Migration, on a copy of one developer's dev database (2026-11-04).** `pg_dump` of `iris_local` (21 Records, Django migrations through `ai/0038`, no `iris_ai` schema) restored into a throwaway `pgvector` container; this branch's `manage.py migrate` (29 pending) and `provision_research_roles` run against the copy; then `python -m ai.runs.migrate` as the maintenance login:
- Fresh: applied `0001_runs.sql` … `0013_checkpoint.sql`; a second run applied nothing.
- Upgrade: schema dropped, `main`'s migrator applied `0001`–`0012`, then this branch's applied only `0013_checkpoint.sql`; a further run applied nothing.
- Grants: `iris_ai_runtime` holds SELECT, INSERT, UPDATE, DELETE on `iris_ai.run_checkpoint` and not TRUNCATE; `iris_django_runtime` cannot SELECT it.
- The container, its network and the dump were removed afterwards; the dev database itself was only read. No existing `iris_ai` rows were upgraded, since that database had none.

**Not done here.**
- **Recovery has no live effect for a run that has read anything.** Under IR-725's guard a restored Conversation always carries tool results, so in production a resumed run is withheld at its next request and ends `unavailable`; resuming to an answer is proven only unadmitted. It takes effect once the AI runtime has a disclosure decision for sending Record evidence to a paid provider. No Jira ticket owns that decision as of 2026-11-04; IR-827 (vendor no-training evidence) and IR-791 (the disclosure check reads the Contact person's answer) are preconditions, not it.
- The ticket's independent demonstration is covered by the four parametrized kill points rather than one recorded run.
- A running executor still keeps the grant it was claimed with; renewing a grant mid-run (IR-723's note) is not built and is tracked as IR-880. A checkpoint save renews the lease, which is not a heartbeat: a single step longer than the lease can still be taken over.
- No checkpoint is written for the final, repair or clarification turn, so a takeover repeats it.
- "Around checkpoint commit" is tested just before and just after the save call; a kill inside its transaction is not separately simulated (PostgreSQL rolls it back, which is the "before" case).
- A database error during reauthorization ends the run `executor_failed`, as any tool's store error does, rather than rebuilding.
- The ADR-049 amendment recording the checkpoint format is not written. ADR-049 itself is not in `docs/adr/` (the numbering goes from 048 to 050), so it has to be recorded first, by Jive or Lee; this ticket does not write it. No live provider call, deployment or production limit is implied.
