## IR-739 — Promote or roll back a verified Embedding Space safely

**Basis and scope.** IR-739 under IR-716; authority ADR-049 §23 (build a pending space, validate coverage / dimensions / retrieval, promote atomically; Record- and Passage-level vectors both carry a space identity; never mix embeddings or dimensions; keep a compatible previous revision for rollback, subject to current access and deletion), ADR-015 (`EmbeddingSpace`, query/document semantics) and the ticket's acceptance criteria. Its blocker IR-752 (pending-space storage and readiness) is merged and Done. **This ticket owns activation and rollback only.** Building a space and the schema expansion stay IR-752; executing an upgrade against production stays a deliberate operational act; removal of the legacy `ai_recordembedding` table waits for the controlled contract phase; IR-742 (cutover rehearsal) is not started here.

**What exists now.**
- `apps/ai/space_activation.py` — `check_activation()` (read-only verdict), `activate_space()` (verify, then flip in one transaction, or `dry_run`), `rollback_target()`, `reopen_rollback_target()`, `reader_probe()`. `apps/ai/promotion.py::promote()` now delegates to it, so the old entry point is the verified one too.
- **Refusals** (each a coded `Refusal`, all reported together, nothing changed): state (promotion takes a pending space; a retired one is refused), width and metric, a stored vector of the wrong width, query/document semantics (the provider that would embed queries for the space must name its model and width), Record summary coverage (missing / stale / for a promotion unverified), Passage coverage, an active chunk set that is not the Record's current Manuscript revision, and an index-health failure (HNSW recall against an exact scan on the space's own rows). Coverage is over the Records readers can use: deleted Records and Records the disclosure gate refuses (ADR-052) are not owed a vector.
- **Atomic activation.** One transaction takes `FOR UPDATE` on every space row (concurrent activations serialize), re-verifies inside the lock, retires the old space, activates the target and writes an `EmbeddingSpaceActivation` row (`ai/0041`: kind, space, previous space, actor, the verification report). `expect_active` makes two operators acting on one picture unable to both land; a lock wait past `LOCK_TIMEOUT_MS` refuses (`busy`) and changes nothing. No vector is written, copied or deleted.
- **Writers honor the flip.** `indexing._hold_space` share-locks the target space row inside both vector-write transactions, so a write that began against the then-active space either commits before the promotion's final check (and is counted) or finds the space retired and writes nothing. `_checked_space` also refuses a provider that names a different model than the space it would write into (an old-model worker cannot fill the new space).
- **Readers move as a pair.** `apps/ai/record_vectors.py` is the one way to reach Record summary vectors, always by space. Ask IRIS stage 1 (`TwoStageRetriever`), related works (`similarity`), the duplicate screen and `find_records` now read `ai_recordspaceembedding` for the space they resolved once per request, the same space stage 2 reads. `TwoStageRetriever` returns nothing, and logs, when its embedder names a model that is not the space's. The `ai/` runtime's `iris_ai.research_record_vectors` reads the keyed table for exactly `p_space` while that space is active (`ai/runs/migrations/0017`), and `ai_recordspaceembedding` joined the research-read policy (`ai/0042`, `PROTECTED_TABLES`).
- **Rollback.** Returns only to the space the last activation replaced, under the same verification against today's corpus (an unverified legacy-copied summary is tolerated for a rollback, since that is what served readers). A target that fell behind is refused naming the shortfall; `--reopen-rollback-target` returns it to `pending` so IR-752's build can catch it up. Rollback reactivates a space and reads no more than it already held, so a source deleted, hidden or tombstoned after the promotion is as unreachable through the old space as through the new.
- **Operator surface.** `promote_embedding_space` gains `--dry-run` (full verification, exits non-zero if it would be refused), `--rollback`, `--reopen-rollback-target`, `--probe-user EMAIL` (a before-and-after search whose citations are checked to be current, readable passages of the space, using stored vectors as queries so no vendor is called), `--actor`, `--skip-index-check`, `--json`. `--check` is unchanged (reports, exits 0).

**Tests** (`backend/apps/ai/tests/`, real PostgreSQL + pgvector, deterministic fake only):
- `test_space_activation.py` (37): each refusal and its coded reason; an incomplete space names every reason and changes nothing; a complete pair promotes, keeps the old space and records history; readers move as a pair and an old-model reader finds nothing; dry-run and `expect_active`; rollback restores and readers follow; only the replaced space is a rollback target; a target that fell behind is refused, reopened, rebuilt and rolled back; revoked sources (deleted, withdrawn, tombstoned, replaced manuscript) are not resurrected; the reader probe holds before and after promotion and rollback; the operator command (check, dry-run, probe, JSON, rollback, reopen).
- `test_space_activation_races_db.py` (10, `transaction=True`, independent threads and connections): a reader in flight while a promotion commits stays on one space; two operators promoting different spaces cannot both land; a writer holding the space makes the promotion wait and its committed row is counted by the final check; a promotion that cannot get the lock refuses; a writer that began before the flip writes nothing to the retired space; an old-model worker cannot write into the new space; **failed activations**: a failure writing the history, a real PostgreSQL error (`DataError`) after both state changes, and a failure *between* retiring the old space and activating the new one each roll back to the old space active and untouched, no history row, readers unchanged.
- `test_ir739_runtime_record_vectors_db.py` (3, role scope): as the restricted `iris_ai_runtime` login under a verified reader grant, the runtime's Record stage follows promotion and rollback; a Record deleted after the promotion is absent after rollback; the runtime cannot write the keyed table.
- Updated deliberately, not to make a failure pass: `test_backfill_and_promotion.py::test_a_complete_space_promotes...` (a space is complete only with summary and passage vectors and a provider naming its model, which is the new contract IR-752 deferred to this ticket); `test_pending_space_build.py`'s allowed-callers guard (IR-752 wrote "until IR-739 moves the readers"); seven retrieval / similarity / visibility / figure fixtures now seed the space-keyed row through one helper (`seed_record_vector` in `tests/corpus.py`) because the readers they exercise moved; truncations in two fixtures include the new table; `test_research_read_policy_db.py` lists the new protected table; `testing/parallel.py` registers the new role-scope file.

**Evidence.** See [the verification record](../evidence/IR-739/README.md).

**Not done here, and why.**
- **No live provider, no paid embedding, no production upgrade.** Everything runs on the deterministic fake. A real upgrade needs a pending space naming a real Voyage model, approved `AI_ADMISSION_*` limits (none are approved), a real indexed corpus with embargo answers (ADR-052) and a human release owner (ADR-049).
- **Queries follow the configured model, not the active space.** The composition root still builds the query embedder from `VOYAGE_EMBED_MODEL`. Promotion verification builds a provider for the *space's* model, and `TwoStageRetriever` refuses a mismatching embedder, but a deployment that promotes a different model must also move `VOYAGE_EMBED_MODEL` in the same operational step, or Ask IRIS returns nothing (safe, not wrong). Making the root follow the active space is a decision for Jive (see the PR).
- **A rollback target does not stay current by itself.** Records indexed after a promotion exist only in the newer space (dual-writing would double embedding spend). A rollback is therefore refused until the target is reopened and caught up with IR-752's build, which is a paid step on a real corpus.
- **The legacy `ai_recordembedding` table is still written** (and no longer read by any retrieval path); its removal is the contract phase.
- The HNSW recall check is run only on the space's own rows; on a tiny corpus the planner may not use the index (reported by `check_vector_index`, not by this check).
