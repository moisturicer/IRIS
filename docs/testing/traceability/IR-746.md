## IR-746 unread notifications belong to one signed-in session (NFR-S4)

The frontend's unread-notifications store is module state shared by the whole tab. It was never emptied, and a fetch wrote its answer whenever it arrived, so the next account to sign in on the same tab could see the previous account's notification text and record links. The store now empties whenever the auth store's `sessionEpoch` moves. `login` now bumps it as well as `logout` and `clearTokens`, because `/login` has no guard and a signed-in account can sign in as someone else with no sign-out in between; as a side effect, a token refresh still in flight for the replaced session is discarded by `client.ts`'s existing check instead of applied. A fetch drops its answer if the session that sent it has ended, and a failed fetch is caught, leaving the bell empty. This is a client-side confidentiality fix: `/notifications/` only ever returned the caller's own rows.

**Tests:** `frontend/src/components/layout/NotificationBell.test.tsx`, with the real auth and notifications stores and only the API mocked, queried by role and accessible name: B sees none of A's notifications after a sign-out while B's fetch is pending; B signing in over A with no sign-out, with A's late fetch and B's failed fetch, shows nothing of A's; `clearTokens` empties the bell; A's fetch answering after B signed in is discarded; B's failed fetch shows nothing of A's and raises no unhandled rejection. `frontend/src/store/notifications.store.test.ts` pins the store emptying on `logout`, `clearTokens` and `login`. Every bell case except `clearTokens` failed before its fix (red-first); the `clearTokens` case and the store test pin behaviour already built.

**Evidence:** run locally 2026-11-01, single files: the two files above, 8 passed; every test file touching the auth store or API client (22 files), 506 passed after `login` started bumping the epoch. `tsc --noEmit` clean; eslint clean on the changed files. The full suite is left to CI.
