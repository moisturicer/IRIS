## IR-620 — deadline reminders from an hourly beat task

**Authority.** [ADR-043 §7–§8](../../adr/043-review-turnaround-reminders-and-escalation.md), accepted. The ticket says no `celery-beat` service exists; it did exist in both Compose files, with nothing scheduled. This change gives it its only entry rather than adding a second service.

**Implemented.** `CELERY_BEAT_SCHEDULE` runs `apps.reviews.tasks.send_deadline_notifications` at minute 0 hourly on `default`. `apps/reviews/reminders.py` computes the one moment each running, unpaused, dated assignment owes now (`due_soon` from 2 Manila working days before, `due_today` on the date), so catch-up sends the latest and skips a superseded one. `DeadlineMoment` (reviews/0018) is unique on (assignment, due date, kind, step); the insert is the idempotency, taken under the record-then-assignment lock with the assignment rechecked. Recipients are live Seat holders that are not done, the office's coordinators for a pool with no live Seat, or the record's Adviser for an unseated Adviser assignment, each filtered through `Record.objects.visible_to`. Notifications are in-app only (`notifications/0007` seeds three types); a failed one is logged and the batch continues. Nothing reads a due date to decide.

**Evidence (2026-10-29).** Against PostgreSQL in a backend container: `test_reminders.py` **13 passed**; `test_document_requests.py` 46 passed; `makemigrations --check` reported no changes; scoped flake8 passed; `celery -A config beat -l debug` loaded `deadline-notifications` on `0 * * * *`. A run of `apps/reviews apps/notifications apps/audit apps/documents apps/tests` reported no failures, but later full runs were cut short by Docker Desktop running out of memory (`Errno 12`, engine 502s), so the complete totals are CI's Backend job, recorded on the PR. No migration was applied to a copy of a realistic database: both migrations only add a table and seed three rows. No human approval is claimed here.

`test_reminders.py` covers: T-2 and due-today moments, re-runs sending once, an unclaimed pool going to coordinators with no duplicate for a later claim, done/withdrawn Seats and completed assignments, catch-up, Extension re-arming, a paused clock, no Turnaround, the Adviser, an unreadable recipient, a failed notification, two simultaneous runs (`TransactionTestCase`, two threads) and the beat entry naming a registered task. A deliberate mutation (dropping the visibility filter, the due-today branch and the lock recheck) failed five of them.
