## IR-1274 · Profile paper cards show the first-page thumbnail

A person's profile (`/people/<id>`) drew every Papers and Advised card with the page outline and
never asked for the paper's first page, because `PersonProfileView` passed `available={false}` to
`PaperThumbnail`, and the profile paper payload had no flag to pass instead. Discover rows have
shown the first page since IR-1141 and IR-1241.

**Implementation:**
- `apps/accounts/public_profile.py`: `paper_payload` adds `has_manuscript`, by Discover's rule
  (`RecordListSerializer.get_has_manuscript`: an `abstract_file` or at least one record file).
  `_newest_first` annotates `file_count` in the list query, so it adds no query per paper.
- Frontend: `ProfilePaper.has_manuscript`; `PersonProfileView` passes it to `PaperThumbnail`, which
  fetches, caches and falls back exactly as on Discover (`/records/<id>/first-page/`, no audit event).

**Behaviour to note:** a paper whose only files are office attachments counts as having a
manuscript under Discover's rule, so its thumbnail asks once, gets a 404 and keeps the outline for
the session. That is Discover's existing behaviour, not new here.

**Deliberate changes to existing tests:** `PAPER_KEYS` in `test_public_profile.py` gains
`has_manuscript`, and the two profile test fixtures carry it, because the contract added a field.

**Evidence (local, 2026-11-21, Windows):**
- `npx vitest run src/features/profile`: 3 files, 60 passed, including the new
  "asks for the first-page thumbnail of a paper with a manuscript, and not of one without".
- `tsc --noEmit`: clean.
- `apps/accounts/test_public_profile.py`, including the new
  `test_a_paper_says_whether_it_has_a_manuscript_for_its_thumbnail`: **not run locally** (no
  `backend/.env` in this worktree); CI runs it.
