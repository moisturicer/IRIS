## IR-1304 — Edit profile moves from Profile into Settings

Editing your profile is an account action, so it is in Settings, not on the Profile page other accounts see. Settings has a new first section, **Profile** (`/settings?tab=profile`), which is also the section Settings opens on when the address names none. It holds the whole form IR-933 put on `/profile/edit`: photo, name, bio and research interests, behind one Save. Save stays on the section and says "Profile saved." with a "View your profile" link. **Discard changes** replaces Cancel and puts back everything saved, a chosen photo included; Save and Discard both wait for a change, and moving to another section with unsaved edits drops them without a warning. The photo still uploads only on Save. `/profile` is only the preview: its note says the profile is changed in Settings and it holds no control. `/profile/edit` redirects to `/settings?tab=profile`; its route, its `profileEdit` access entry and its route-matrix entry are removed. Help, the Settings header description, the design docs and the e2e smoke rows no longer point at the old page. This alters IR-933's "Edit profile holds the photo, name and optional fields behind one Save that returns to Profile". No ORCID iD work was needed: the account has none (`apps/accounts/test_profile.py::test_the_account_has_no_orcid`). Frontend only; the API is unchanged.

Evidence (Vitest, run 2026-11-23, `npm run test:changed`: 44 test files related to the 23 changed files, 1,158 passed and 3 skipped; one further failure, `config/institution.test.tsx`, was fixed and its file re-run, 4 of 4 passing): `src/features/settings/ProfileTab.test.tsx` (23 cases through the accessible tree with axe: the tab is first and the default, Save sends the changed parts and stays on the tab with the saved line and the link, the line goes away when the form changes again, the server's refusals, Discard changes for text, interests, an error and a photo, and the photo uploads or is removed only on Save), `ProfilePage.test.tsx` (no edit control, the note names Settings), `router/redirects.test.tsx` (`/profile/edit` lands on `/settings?tab=profile`), `SettingsPage.test.tsx`, `access.test.ts`, `viewportMatrix.test.ts`. `tsc --noEmit` and `eslint` on the changed areas were clean.

Changed deliberately: four `SettingsPage.test.tsx` cases and `config/institution.test.tsx` assumed Settings opens on Account & security, and now name the section or expect Profile; "points to the Profile instead of holding it" now says Settings holds the editing and still links to the Profile.

Not covered: the Playwright smoke rows (`profile`, `profile-settings`, `settings`) and the CSP walk were edited but not run here, so CI is their first run. Not checked in a browser at 360, 768 and 1280 px, including the photo crop dialog inside the tab.
