# IR-790: The consent screen at sign-up and sign-in

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** ADR-054 decisions 1 to 3, 6, 7 and 13, under IR-779. Builds on IR-789, which added the notice, the answer endpoint and the server-side block. No FR- id.

**Why it was urgent:** IR-789 made `POST /auth/register/` require `agree_dpa`, `ai_consent` and `notice_version`, and nothing sent them. From 2026-11-05 until this change nobody could register through the app on `main`: the signup page said "Registration failed. This field is required." three times, and the core journeys run of 2026-11-07 failed for the same reason (`docs/testing/runs/2026-11-07-core-journeys-f8784c67.md`).

**What changed:**

- `features/auth/notice/NoticeAnswerFields.tsx`: the server's notice (title, version, date, and its text as plain text with its line breaks, never parsed as markup), the data-privacy agreement, and a required Yes or No on AI with neither preselected. It says what each answer means: Yes lets AI read and index the person's papers, subject to the embargo and IP mark; No keeps the account normal and the papers away from AI, while their own Ask IRIS questions still go to AI companies; text already sent can't be recalled. Registration and the signed-in screen use the same component.
- `SignupPage.tsx`: reads `GET /auth/notice/` with the other form options and sends the two answers and the version shown. A 409 `notice_stale` shows the newer notice and asks for both answers again.
- `features/auth/notice/NoticeAnswerScreen.tsx`: the screen a signed-in person sees until they answer. It offers Save my answer, Sign out and Request account deletion (with a confirmation step). A 409 `notice_stale`, or a newer version found when the tab comes back into view, replaces the text and clears the answers.
- `ProtectedRoute` shows that screen in place of the page while `useNoticeStore().required` is set, so the address asked for is kept. It is set by the login response's `notice_answer_required`, by any `notice_acceptance_required` 403 (`api/client.ts`), and by `hydrateAuth` when a refresh's `GET /users/me/` is refused that way. That refusal no longer signs the person out: the session is kept and the account loads once they answer.
- Backend: `user-me-deletion-request` joins `ALLOWED_WHILE_UNANSWERED` in `apps/accounts/notice.py`. Its comment said the deletion route would join "when its route exists"; IR-785 added it.
- e2e: `support/people.ts` registers with the notice answers (Yes, as test data answers, ADR-054 decision 18). `00-account-lifecycle.spec.ts` answers both on the form. The smoke tier's signup screen mocks `GET /auth/notice/`.

**Changed deliberately:** `SignupPage.test.tsx` and `api/auth.test.ts` expected `consent_given: true` in the registration payload and the old interim notice's text. They now expect `agree_dpa`, `ai_consent` and `notice_version`, answer the AI question where a test completes the last step, and read the server notice's fixture text. `apps/tests/test_notice_block_every_route.py` kept only allowed names starting with `notice-` or `auth-`, so the new exemption failed it; it now names every exemption in an explicit `ALLOWED` set and checks it equals `ALLOWED_WHILE_UNANSWERED`, so a future exemption still fails until it is written there too. No test was changed to make broken behaviour pass.

**Not done here:**

- **No to Yes offering "all my papers" or "only papers from now on"** (ADR-054 decision 13, this ticket's fifth criterion) needs IR-791's change route, which isn't on `main` yet. Today the notice screen stores a Yes as the person's answer for later papers only, which is what IR-789's endpoint does. It is added once IR-791 merges.
- The header's "Data privacy" panel on sign-in and registration (`EntryFrame`) still shows the interim text from `DataNotice.tsx`. Showing the server's notice there is IR-800.
