# IR-1075: Notifications show when their review task has closed

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** no FR- id. Epic IR-671 (S2 Epic: Backend). Audit findings WF-01, US-10 and A11Y-07 ([`frontend_ui_audit_spec.md`](../../frontend_ui_audit_spec.md) §4.2). Decision D2, recorded as ADR-069 by IR-1072 (PR [#724](https://github.com/moisturicer/IRIS/pull/724), not merged when this was written). Thesis-critical: it makes clearance-aware resubmission visible where coordinators already look.

## What changed

- **Server.** `Notification` gains `task_kind`, `task_id`, `resolved_at` and `resolved_label` (migration `0011`, four additive nullable or blank columns). The list endpoint returns the last two. A resolved notification is left out of `?unread=true`, which is what the client's unread count is built from. It stays in the full list.
- **Which notifications resolve** (they ask the recipient to act, and are bound to the row their task lives on):

  | Notification | Bound to | Ends when |
  |---|---|---|
  | Record Routed, to an office pool | the office's assignment | anyone claims it (for every member at once), or the assignment closes |
  | Record Routed, to a nominee | the nominee's seat | they review, lose the seat, or the assignment closes |
  | New Record (to the Adviser) | the Adviser's assignment | the assignment closes |
  | New Version Submitted | the reviewer's seat | as a nominee's |
  | Revision Requested (to owners) | the revision request | a new version answers it, or it is withdrawn |
  | Document Requested, Document Rejected | the document request | fulfilled, or withdrawn |
  | Download Request Submitted, Delete Request Submitted, Role Request | the request | it leaves `pending` |
  | Deadline reminders and escalations | the assignment | the assignment closes |

  **Never resolved:** every informational notification (a decision, a publication, a comment, a mention, an office's outcome, a withdrawal notice), the embargo-review reminder, and **every notification sent before this change** (it has no task, so it is left as it was; nothing is backfilled).
- **Mechanism, and why (ADR-069 decision 6).** The ending is **stored on the notification**, written once and never cleared, and found by reading rows that never reopen: a closed assignment, a seat that exists or was withdrawn, a `Review` the seat holder wrote after the notification, a request that left `open`/`pending`. It is not derived on every read, because two paths reopen a row a task lived on: a resubmission reopens the same `RecordAssignment` and puts finished seats back in review (`reviews/new_version.py`), and rejecting an upload reopens a fulfilled `DocumentRequest`. A notification worked out from today's row would un-resolve itself and its unread count would rise on its own, which ADR-069 decision 5 forbids. Two things keep it final: `settle_record` runs **just before each of those two reopening paths**, and the notification endpoints settle what the reader can see before answering, so anything else that ended is stamped the first time it is looked at. The code is `apps/notifications/settling.py`.
- **A reset sends a new notification.** `notify_new_version` binds each reviewer's notice to their seat. A review the seat holder wrote before that notice does not answer it, so the old notification stays resolved and the new one is open.
- **Labels** are built only from workflow facts the recipient already sees (office, seat holder, date): "Claimed by Ana Cruz on 20 Oct", "Reviewed by you on 20 Oct", "Answered with a new version on 3 Nov", "Approved on 12 Nov". A seat withdrawn by a coordinator has no timestamp of its own, so its label carries no date and `resolved_at` is when it was first noticed.
- **Copy (ADR-069 decision 7).** The pool notice reads `RDCO Final sent "<title>" to ITSO. It waits in ITSO's pool until a reviewer claims it.` The sender is named the way the tracker names the party, which is "RDCO Final". The router's reason is no longer in the notice; the email still carries it on its own line.
- **Client.** `NotificationsPage` shows the server's `resolved_label` as a settled line, drops the unread dot, bold and mark-as-read control for a resolved row, and does not count it as unread. The type tag under each notification is plain sentence case ("Sent for review", "New version") instead of the system name (US-10). The bell needed no change: it lists `?unread=true`, which the server now filters.

## Tests

- `backend/apps/notifications/test_resolved_notifications.py` (REST seam, real routing, claiming, clearing, revision and resubmission):
  - the pool notice's copy;
  - claiming resolves it for every ITSO member and leaves each person's read state alone;
  - it stays resolved if the claimer later loses the seat;
  - a closed assignment resolves it with no claim;
  - a nominee's notice resolves when they review;
  - **under `RESTART_ALL`, a resubmission reopens ITSO's assignment and seat, the first notification stays resolved and a new, open one is sent**;
  - an owner's revision notice resolves on the new version and on a withdrawal;
  - informational and pre-existing notifications never resolve;
  - a resolver that fails or a row that is gone leaves the notification open and the list answering;
  - download, delete, role and document requests end on their rows, and a rejected upload does not undo a document request's.
- `frontend/src/features/notifications/NotificationsPage.test.tsx` (settled and open rows beside each other, the Unread filter and count, the all-caught-up message, plain type tags) and `notificationLabels.test.ts`.
