## IR-823 — The Content-Security-Policy is enforced (ASVS 14.4.3, 14.4.7)

IR-663 shipped the policy as `Content-Security-Policy-Report-Only`, to be enforced once a walk-through of the main screens showed no violation. That walk-through is now `e2e/specs/08-csp-walkthrough.spec.ts`, so it can be repeated whenever the policy or the app changes:
- It opens every main screen in a real Chromium, behind the real nginx and Django, as each role that reaches it.
- It records every `securitypolicyviolation` event and every CSP console message, writes them to `test-results/csp-walkthrough.json`, and fails on any.

**What the walk-through found:** zod 4 probes `new Function("")` the first time it validates, to decide whether it may compile validators. That probe was a violation (`script-src`, `eval`) on every signed-in screen. zod catches the refusal, so nothing broke, but every page would have logged it. `frontend/src/lib/zodConfig.ts` sets `jitless`, imported first in `main.tsx`, so the probe never runs. No other violation was found.

**Enforced:**
- **nginx:** `frontend/security-headers.conf` sends `Content-Security-Policy`.
- **Django:** `CONTENT_SECURITY_POLICY_REPORT_ONLY = False` in `config/settings/base.py`, which production inherits.
- **Development stays report-only** (`config/settings/development.py`). The debug toolbar injects inline scripts and styles, and DRF's browsable API has inline style attributes, so enforcing there would break both for whoever is developing. The dev edge (`nginx.dev.conf`) never sent the SPA policy for Vite's pages anyway.

**Tests changed deliberately:**
- `test_security_headers.py` pinned report-only on both servers. It now pins nginx's enforcing header and `base.py`'s enforcing value, checks production doesn't override it, and still checks development reports.
- CI's nginx header step expects `content-security-policy:`.
