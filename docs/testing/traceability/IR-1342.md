# IR-1342: guided tours for newly registered students

[Back to the matrix](../TRACEABILITY.md)

**Requirement:** Ashlee Sean asked for this on 2026-11-27 and settled its design the same day. The decisions are recorded on IR-1342. There is no ADR and no FR- id.

- A Student account created after this ships is walked through Discover, My Library, Ask IRIS, Calls & Conferences, Guidelines and Notifications the first time it opens each, and through Publish the first time the dialog opens. It never starts again on its own, on any browser.
- Accounts that exist when migration `accounts/0025` runs, seed_demo's included, count as having seen every tour.
- Only the Student role gets tours. Advisers, office roles and an account still waiting for a role get none.
- A tour is taken again only from Settings › Help. Pages have no tour button.
- The look is the Review tour's. It is the same `GuidedTour`, unrestyled.

## Design

**Backend**
- `User.tours_seen` (JSON list) holds the keys of the tours shown. The keys are a closed list, `apps/accounts/tours.TOUR_KEYS`.
- The only write is `POST /users/me/tours/<key>/`. It is idempotent, takes a row lock and writes nothing but `tours_seen`. An unknown key gets a 400. There is no id in the address.
- The field is read-only on `/users/me/`, absent from the administrators' `/users/`, and included in the personal data export (ADR-051 decision 13).
- Migration `0025_tours_seen` adds the field, then marks every existing account with the seven keys, frozen inside the migration.
  - Reversing it drops the field.
  - **Running it forward decides the cutoff once.** The accounts present at that moment are the ones marked.
- seed_demo marks every account it seeds.

**Frontend**
- `GuidedTour` moved to `components/tour/`. It gained three props:
  - `label`, the dialog's name. The Review workspace passes "Review workspace tour".
  - `onShown`, which fires once a step is drawn.
  - `container`, where the tour is drawn.
- `features/onboarding/useStudentTour` decides when a tour runs:
  - **It starts** for a Student who hasn't seen it, once the page has finished its first read and a step's target is on screen. A `MutationObserver` covers targets drawn later.
  - **It is marked seen** on Skip tour, Escape or Done, or on leaving the page with the tour open, and only if a step was shown. The mark is optimistic. If the request fails, the key still counts as seen for the session.
  - **One tour at a time.** A page's tour waits while `?publish=` is open. If Publish opens over a running tour, that tour closes without being marked and returns on the page's next visit.
- **Publish's tour is drawn inside the dialog's panel**, so it is part of the `aria-modal` tree.
  - Escape closes the tour alone, because `useDialogFocus` lets only the top surface hear it.
  - It starts once the form has loaded, on whichever step the dialog opened, and never moves the dialog.
- Steps are built from what is on screen.
  - The sidebar step becomes an Open menu step on a phone.
  - Ask IRIS's History step points at the phone's History button there.
  - The Calls tour on an empty board is its one board step.
- **Settings › Help** has a *Guided tours* section for Students only. It holds a link per tour (`?tour=<key>`) that starts the tour whether or not it was seen, then removes `tour` from the address.
- **Drift guard.** `frontend/src/features/onboarding/tourKeys.json` is the frontend's copy of the keys. A backend test holds it equal to `TOUR_KEYS`, and a frontend test holds the TypeScript list equal to the JSON.
