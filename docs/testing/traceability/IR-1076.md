# IR-1076: Delete Requests: Pending lists only pending requests

**Requirements:** audit finding WF-02 (High) in `docs/frontend_ui_audit_spec.md` (IR-1071), epic IR-920. The matrix has no `FR-` row for the Delete Requests queue's tabs.

## What was wrong

RDCO's Delete Requests *Pending* tab listed a request that had already been declined, with its row still in the queue. The page was not at fault: it sent `?status=pending`. **The server ignored it.** `DeleteRequestViewSet` declared no filter and had no `get_queryset`, so every request came back whatever the `status` parameter said. The sibling `DownloadRequestViewSet` filters by hand and was never affected.

## What changed

**Server, `apps/records/views.py`.** `DeleteRequestViewSet.get_queryset` honours `?status=`: `pending`, `approved` and `declined` match one state, and `decided` is everything that is not pending. The list is ordered newest first (it had no ordering, so pages were not stable). No status means every request, as before. An unknown status lists nothing, as `DownloadRequestViewSet` does.

**Page, `features/admin/DeleteRequestsPage.tsx`.** Two tabs, *Pending* and *Decided*, replace *Pending / Approved / All*, so a request is in exactly one of them. Pending asks for `status=pending` and is the only tab with the approve action. Decided asks for `status=decided` and shows each outcome (the status chip), the requester's reason and the date it was decided; its last column is headed *Decided on* and has no action. The empty Decided tab reads "No requests have been decided yet."

The fix is where the fault was: the server. The page does not filter again on the client, which would hide a server fault rather than fix it. It already offered the action only on a row whose `status` is `pending`; a test now pins that.

## Open for the reviewer

- **Decided "reason" is the requester's reason.** `DeleteRequest` stores why the owner asked (`reason`), not why RDCO declined. A decline reason would be a model change and is not in this ticket.
- **There is still no decline button on the page**, although the server has `POST /delete-requests/<id>/decline/`. Out of scope here; the old comment saying the backend had no decline action was removed because it was stale.
- **Behaviour change:** the *Approved* and *All* tabs are gone, replaced by *Decided*. An approved request is now found under Decided, with its Approved chip.
