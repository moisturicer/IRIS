## IR-442

**Requirement:** **A retrieval miss is detectable rather than silent** — no FR- id; the checker for the failure class [ADR-023](../../adr/023-retrieval-quality-evaluation.md) measures in aggregate but cannot see per-paper

**Design:** [ADR-023 §Amendment](../../adr/023-retrieval-quality-evaluation.md) · [ADR-007](../../adr/007-pgvector-vector-store.md) (HNSW is approximate by construction)

**Implementation:** `apps/ai/index_health.py` — `measure_index_recall` compares an index against an exact scan using stored vectors as seeded probes, reporting recall beside the `AI_HNSW_EF_SEARCH` depth that produced it. Two planner contexts make that comparison mean anything: `exact_scan()` forbids **both** index and bitmap scans, and `index_scan()` forbids the sequential alternative so a small table is not compared with itself — the same two flags IR-440's own test needs. `used_index` carries whether the plan really read the HNSW index (checked by `EXPLAIN` inside the measuring context), because a figure from a sequential scan says nothing about the index. `probe_titles` asks an injected retriever about each paper by name and names what came back instead. `apps/ai/management/commands/check_vector_index.py` is the thin shell, exiting non-zero below `--min-recall` and warning when no index was read. **Why both measures:** an index can be perfectly faithful to an exact scan whose top ten is still the wrong paper, and a stored-vector probe is an easier question than a real query vector (`input_type=query` lands elsewhere in the space), so the free check cannot replace the paid one

**Test:** `apps/ai/tests/test_index_health.py` (24 — recall arithmetic including the empty-exact and short-result cases, the pinned probe phrasing, the title probe against a fake retriever, and against real pgvector: perfect recall on a small table **asserting `used_index`** so a vacuous pass fails, sampling capped by rows, an empty index reported rather than crashing, the depth recorded, determinism per seed, both planner contexts setting their flags and restoring them including on an exception, and the command refusing below the floor, refusing `--titles` with no user, and refusing with no active space). The pgvector tests give each chunk a separated random vector rather than the deterministic fake, whose vectors for similar strings sit almost on top of each other — a near-tied top-k makes exact and approximate disagree legitimately and would measure the fixture

**Evidence:** `pytest apps/ai/tests/test_index_health.py` 24 passed 2026-10-01. **Two vacuous-pass bugs found and fixed while testing**, both of which made the checker report perfect health unconditionally: `SET LOCAL` survives a nested `atomic()`, so in any outer transaction (every `django_db` test) `enable_indexscan = off` outlived `exact_scan()` and the approximate side ran exactly too; and the approximate side never forced the planner onto the index, so on a small table both sides were sequential. **On the dev database:** `chunk_embedding_hnsw_idx` recall@10 0.995, `embedding_hnsw_idx` 1.000, both at depth 200, and 40 of 40 papers found by their own title. The 0.995 is the honest figure — it read 1.000 before the index was forced. **Bulk-load experiment** (scratch table, index created empty then filled the way `backfill_embeddings` fills it, 2,445 vectors, plan confirmed HNSW): recall **0.995 at depth 40 and 0.995 at depth 200**, against 0.978/0.995 after `REINDEX` — bulk loading does not degrade the index and `REINDEX` does not improve it, so **no reindex step was added**. **Eval identical** — `docs/evaluation/runs/20261001-141341-proxy-starter.json` reproduces IR-440's fusion-on run `…-182520-…` to four decimal places on every measure (rerank recall@10 0.8942, final-set 0.8750, no-rerank 0.6923/0.6250, `degraded_questions` 0), so the `REINDEX` moved retrieval quality by nothing this question set can see. **Compared against the fusion-on run on purpose:** this dev deployment's `.env` sets `AI_RETRIEVAL_FUSION_ENABLED` and `AI_KEYWORD_RETRIEVAL_ENABLED` to `True`, which the harness records per run, so the fusion-off baseline `…-182254-…` is not the comparable one. That same setting is why `apps/ai/retrieval/tests/test_fusion.py::SwitchTests` fails on this machine — the tests pin IR-402's documented default of off

**Status:** **IMPLEMENTED, tested, measured.** What is **not** explained: a real index on the dev database did fail a title-shaped question before a `REINDEX`, and a freshly bulk-loaded index does not reproduce it, so the cause is a history that can no longer be replayed. Recorded as unexplained rather than guessed at — the checker is what makes the next occurrence visible
