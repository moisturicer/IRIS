## IR-752 — Build a new Embedding Space while current search stays usable

**Basis and scope.** IR-752 under IR-716; authority ADR-049 §23 (build a pending space beside the active one; both Record- and Passage-level vectors must carry a space identity before a parallel model upgrade; never mutate the active index in place), ADR-015 (`EmbeddingSpace`) and the ticket's acceptance criteria. IR-751 (Done) published a current indexed Manuscript in the existing space. **This ticket is the additive expand-and-migrate slice only.** It cannot activate a space: promotion and rollback are IR-739, and removal of the legacy storage and its callers waits for the contract phase. No existing reader was changed.

**What exists now.**
- `ai_recordspaceembedding` (`RecordSpaceEmbedding`, migration `ai/0040`): one Record summary vector per `(record, space)`, HNSW cosine index, unique constraint. It mirrors `ChunkEmbedding`'s `(chunk, space)` identity at Record level. `source_hash` is the SHA-256 of the exact title-and-abstract text that was embedded.
- The migration copies each legacy `ai_recordembedding` vector under the space whose `model_id` equals the row's `model_name` (the active space first, else the newest retired one; **never a pending space**). A row whose model matches no space stays in the legacy table only. Copied rows carry `source_hash = ''` because the text they came from is not recorded, so no freshness is claimed. Reverse drops the table.
- `embed_record_summary` keeps writing the legacy row and now mirrors the vector into the active space's keyed row. With `space_id` it writes the keyed row of that space only and never the legacy row.
- `apps/ai/space_build.py` — `build_pending_space()`: refuses any space that is not pending, not cosine, not the columns' width, or whose provider does not name the space's `model_id` and width (`EmbeddingProvider.model_id`, new, non-abstract, `None` by default; Voyage returns its model, the deterministic fake takes one and salts its vectors by it). Embeds only what is owed (summary with no current-hash vector; active chunks with no vector in the space), on the `ingestion` admission lane, in `max_records` / `token_budget`-bounded slices, with a per-`(space, record)` advisory lock so a duplicate delivery skips a record another worker holds. Passage vectors are written only against the chunk set and `source_revision` that was active when the record's turn began; a replaced manuscript refuses and writes nothing. An admission refusal stops the run (`stopped = "admission:<reason>"`) and keeps finished records.
- `apps.ai.tasks.build_embedding_space` (queue `embedding`): one bounded slice, safe to redeliver.
- `space_readiness()` — read-only coverage: summaries current / missing / stale / unverified, passages embedded of total, stored-vector width mismatches, per-record shortfalls. Shown by `promote_embedding_space --space N --check` (which still promotes nothing) and `check_vector_index --space N` (HNSW recall against an exact scan, on the space's own chunk and Record rows). `backfill_embeddings --space N` on a **pending** space now plans and runs summaries too, through the build; on any other space it is unchanged.

**Why readers cannot see a pending space.** Isolation is by write separation, not a filter: a build writes only the pending space's rows and never `RecordEmbedding`, and every current reader (two-stage retrieval, similarity, the status counts, the research tools, `ai/` runtime) still reads the legacy table and, for passages, filters by the active space. `test_only_the_build_and_indexing_modules_name_the_space_keyed_table` fails if a new module starts reading the keyed table, so IR-739's reader move has to be deliberate.

**Tests** (`backend/apps/ai/tests/`, real PostgreSQL + pgvector, deterministic fake only):
- `test_pending_space_build.py` (31 tests): the live path keeps the legacy row and adds the keyed one; one vector per record per space; a build fills the pending space and leaves the active space's keyed rows, chunk vectors and the legacy row byte-identical; the two identities embed differently; only a pending, cosine, column-width space with a matching provider is built (nothing sent otherwise); nothing activates; a partial pending build changes no TwoStageRetriever result, similarity result or passage count, and the status endpoint is identical; a bounded build resumes and a finished one sends nothing; a token budget stops before the record that would exceed it; a failure keeps finished work and only the failed record is re-sent; a lock held by another connection makes the build skip that record with no send; embedding is charged to `ingestion`; an admission refusal stops the run and keeps what finished; a gate-refused record is never sent; a manuscript replaced mid-send publishes nothing and the next run builds the new chunk set; an edited abstract re-embeds only that summary; readiness partial vs complete, stale summaries, and the promote/check output; `check_vector_index --space`; `backfill_embeddings --space`; the default provider is built for the space's model; a record held by another worker does not use up the record bound; an oversized record is still built; a space promoted mid-run stops the build.
- `test_record_space_embedding_migration.py` (2 tests): rewinds `ai` to `0039`, seeds legacy vectors under an active, a retired, a pending and an unknown model, migrates forward and checks the copy, then rewinds and re-applies.

**Evidence.** See [the verification record](../evidence/IR-752/README.md) for what was run, the dev-database-copy migration check, and what failed or was not verified.

**Not done here, and why.**
- **No reader uses the keyed table.** Moving two-stage stage 1, similarity, the research tools and the `ai/` runtime's `iris_ai.research_record_vectors` onto `(record, space)` is IR-739 (it changes Ask IRIS retrieval, not in this ticket). Until then the legacy table is the only source those read.
- **`promote()` does not yet require summary vectors.** `promote_embedding_space` (unchanged) still checks passage coverage only. `space_readiness` reports summaries and dimensions beside it, but nothing forces them. IR-739 must make promotion refuse an incomplete or stale summary set, and switch the readers in the same step.
- **The new table has no row-level-security policy or runtime-role grant.** Nothing in the `ai/` runtime reads it yet; IR-739 must add it to `PROTECTED_TABLES` and `ai/0035`'s policy when a reader moves.
- **Query/document semantics are pinned structurally, not in a column.** The port has separate `embed_documents` / `embed_document_chunks` / `embed_query` methods (ADR-015 rule 3), a build can call only the first two, and the space row pins model, width and metric. There is no stored "input type" field because nothing would read it.
- **No live provider, no paid embedding.** The Voyage adapter's `model_id` is a one-line property and is not exercised against the vendor. Admission is exercised through `AdmissionDenied` and the `ingestion` lane marker, not through the real ledger; the existing ledger tests cover that path.
- **Concurrency of two real workers** is shown with an advisory lock held on a second database connection, not two worker processes.

**Update (IR-739).** The first three bullets above are superseded: promotion now requires a complete, current summary set and moves the readers (stage 1, similarity, duplicates, `find_records`, the `ai/` runtime's `research_record_vectors`) onto `(record, space)` in the same step; the keyed table has its row-level policy and runtime grant (`ai/0042`, `PROTECTED_TABLES`). See [IR-739](IR-739.md). The guard test named above now lists the modules that read it.
