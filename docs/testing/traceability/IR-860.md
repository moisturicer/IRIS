## IR-860 — Answer AGENT turns through the configured chat-completions provider with declared capacity

**Basis and scope.** IR-860 under IR-714; authority ADR-049 §13, §14, §17, §20 and IR-725's admission. The AI runtime gets a real AGENT adapter for the pinned chat-completions dialect, with capacity declared per model from required configuration. No route, worker or reader change: choosing which executor a run uses is IR-862. No live provider campaign, and no value here is approved.

**Code.** `ai/infrastructure/openai_adapter.py` adds `OpenAICompatibleAgentProvider` (adapter `openai-compatible`, `paid = True`) beside the unchanged `OpenAILLMProvider`, so `generate_response` callers are untouched. It accepts a pin only on its configured endpoint, a listed model, `chat-completions-1`, the configured data policy and capabilities it declares. It sends exactly what `ChatCompletions.encode` produces to `<endpoint>/chat/completions` and decodes the wire body with `ChatCompletions.decode`, so ordered tool groups, parallel call ids, stop reasons and opaque artifacts are the IR-727 dialect's own. It uses plain `httpx` instead of the vendor SDK, so no retry layer exists and no library logs the payload. Transport errors and 408/409/429/5xx raise `TransientProviderError("status N")`, and any other non-2xx raises the new `ProviderRejected("status N")`, which `AgentExecutor` reports as `unavailable` (`provider_rejected`). Neither carries content. A non-JSON 2xx body decodes as `malformed`. `ai/infrastructure/agent_config.py` reads `AGENT_LLM_ENDPOINT`, `_API_KEY`, `_MODELS`, `_CAPABILITIES`, `_DATA_POLICY` and `_CAPACITIES` fail-closed (`NotConfigured` naming the key, never the key's value), and `from_settings` reads them before an adapter exists. Each capacity must state all six `Capacity` fields and nothing else, and may only name a listed model. A listed model with no declaration has `capacity() → None`, so IR-732 refuses it as `capacity_unknown`. `ai/admission/scope.py` adds `admitted_send()`, which `AdmittedAgentProvider` wraps around each physical send. Outside it the adapter refuses with `AdmissionDenied("not_admitted")` before encoding anything. The account digest covers endpoint and key, never the key itself.

**Tests.** `apps/ai/tests/test_ai_runtime_openai_agent_contract.py` (45, no database, no network): recorded vendor responses are replayed through the real adapter over `httpx.MockTransport`.
- **What is sent and returned:** the exact request body, URL and auth header. A direct answer is final, with reported usage. A parallel tool group keeps its order and ids, and round-trips its results and opaque artifact unchanged.
- **Non-final completions:** length, reasoning-only (text and artifact), tool-only, an unknown finish reason and a non-JSON body are each reported as what they are.
- **Admission:** the adapter sends nothing outside an admitted attempt. The executor refuses it unwrapped as `not_admitted`. With limits unset, `AdmittedAgentProvider` refuses as `not_configured` with no request.
- **Failures:** 503, 429, 500, a connect error and a read timeout are each one request and a `TransientProviderError`. 400/401/403/404/422 are one request and `ProviderRejected`, carrying only the status.
- **Logs:** a DEBUG-level log capture holds no key, question, answer or artifact.
- **Pins:** every mismatched pin field is unaccepted and unsent.
- **Configuration:** each missing key is named. Partial, extra, non-positive, non-numeric and unlisted capacities refuse to start. A well-known model name gets no assumed capacity.
- **Legacy:** the `generate_response` adapter is unchanged.

`apps/ai/tests/test_ai_runtime_openai_agent_db.py` (8, real PostgreSQL) is the ticket's demonstration through `AdmittedAgentProvider` with the real ledger and guard:
- a direct answer completes a run and settles to reported usage, with the reserved cap equal to the cap sent;
- a parallel tool group and a truncated completion each come back typed and settled;
- a 503 then a retry are two settled attempts;
- with one limit unset (prices, campaign cost) the next attempt sends nothing and reserves nothing;
- an unpriced model is refused unsent.

The contract files ran green locally, the new one together with IR-727's, IR-728's and IR-732's suites (135 tests). The PostgreSQL file was **not run locally**: the only reachable Postgres belonged to another worktree's stack with different credentials, so CI is its first run.

**Not done here.** The "recorded" responses are fixture bodies written in the vendor's chat-completions shape, not captures of a live vendor call: none has been made. IR-727's own suite still runs only against the recording provider; its artifact, tool-group and stop-reason cases are repeated here against the real adapter instead of parametrizing that file. The admitted-send gate is a context flag that `AdmittedAgentProvider` sets: it stops an accidental unadmitted send, not code that opens the flag itself. 409 is classed as transient. No vendor's capacity is verified, and nothing checks a declaration against the vendor. No worker or route builds this adapter (IR-862), so "validated at start" means `from_settings` refuses before an adapter exists. Wiring it at worker start is IR-862's. The `no-training` data policy is a declaration; recording the vendor's terms is a human step. No live provider call has been made.

**Status.** Implemented; awaiting review.
