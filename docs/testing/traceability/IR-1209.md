## IR-1209

**Requirement:** **Selecting text in the paper reader stays on the text being dragged through** — no FR- id; a bug reported in team testing, 2026-11-17

**Cause:** a page's text layer is transparent spans over the canvas, with gaps between them (margins, leading, the space between columns). Over a gap the pointer is over no text, so the browser resolved the selection's end to whatever text came next in the layer's DOM order: the next line, the other column, the rest of the page. pdf.js's own viewer (`TextLayerBuilder`) prevents this with an `endOfContent` element in each layer and a `selecting` class while a selection is made; IRIS draws its layers with pdf.js's bare `TextLayer` (`lib/pdf.ts`, IR-353), which has neither. The watermark (IR-1128/IR-1198) and the review-thread and citation overlays take no pointer events and were not involved.

**Implementation:** `frontend/src/lib/textSelection.ts`, `bindTextSelection(layer)`: a port of `TextLayerBuilder`'s selection handling (pdfjs-dist 6.3). Each bound layer ends with an `.endOfContent` element; a press, or a selection reaching the layer, marks it `.selecting`; pointer release, window blur, a key release outside a drag, or a cleared selection puts every layer back. In browsers that still resolve gaps by DOM order (Chromium before 148, Safari) the element is moved to just after the text where the selection ends, stepping out of a Find `<mark>` so it never lands inside a word. Firefox and Chromium 148+ skip the move, as in pdf.js: Firefox is recognised from the end element's own `user-select: none`, read as `-moz-user-select`. One set of document listeners serves every layer. `index.css` adds pdf.js's two rules: the element sits below the page, and covers the whole layer behind the spans while `.selecting`. `PaperPdfReader.tsx` binds each page's layer in the effect that draws it, once the spans are drawn, and unbinds before that effect clears the layer for another page.

**Test:** `lib/textSelection.test.ts` (10, jsdom; it finds the element and spans by class and position, since the element has no role or name and its place is what is tested): one end element after the text; `.selecting` from press to pointer release; only the pages the selection touches; the element moved after the selection's end; stepping out of a find match; reset on a cleared selection and on window blur; no move in Chromium 150 or in Firefox; unbinding removes the element and the layer's press listener. **Real drag, in Chromium:** `e2e/smoke/text-selection.spec.ts` with a two-column PDF (`twoColumnPdf` in `e2e/support/pdf.ts`): a drag along one line ending over the gap between the columns selects only that line; a drag across two lines of one column ending over the gap selects only those lines; and on a single-column page a drag along one line ending in the margin selects only that line. Spans are found by their exact text. Highlights, Find, citations and the watermark: the existing `features/records/paper-view` suite.

**Review:** a standards and a spec review found two defects, fixed with tests: the Firefox check read the layer, not the end element, so Firefox would have moved the element pdf.js leaves alone (the Firefox test now covers it, and the skip tests end the selection mid-layer so a move would show); and a page change cleared the layer before the binding let go of it, now bound and unbound inside the effect that draws the layer. Also: a single-column drag test, `needsEndMove` instead of a name that read backwards, spans found by text in the smoke test, and one PDF writer shared by the e2e fixtures (`writePdf`).

**Evidence:** 2026-11-18, local, Playwright's Chromium 153. Built **without** the fix (`main`'s reader and `index.css`), all three drag tests failed: the one-line drag selected "Left column line one" and "Left column line two". Built with it, all three passed, 5 runs each (`--repeat-each=5`, 15 of 15). `npm test` **237 files, 3456 passed** (3 skipped); the whole smoke tier (`npm run test:smoke`) **445 passed**; paper-view tests 56 files, 986 passed; `tsc` and `eslint` clean. Not checked by hand: Safari and Firefox, and a real two-column thesis.

**Follow-up, IR-1225 (2026-11-18):** the two-line drag test failed on CI for PRs #876 and #877, which do not touch the reader. CI's recording showed the cause. The text first appeared at 101% zoom, and the reader then refit to its pane at 140% (`REFIT_DELAY_MS`, 120ms, after a width change). The test had measured the lines at 101%, so it pressed on blank page and selected nothing. `openPaper` now waits until line one has stopped moving for 300ms before measuring.

Reproduced locally by opening the paper in a 1100px window and widening it to 1280px as the text appeared. The old test then failed 6 of 9; the new one passed 15 of 15. Built **without** IR-1209's fix, the new test still fails all three drags. Built with the fix, it passed 30 of 30 (`--repeat-each=10`).
