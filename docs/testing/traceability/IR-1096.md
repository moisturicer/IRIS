# IR-1096: Publish and My Library's research tabs only for users who can author

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** no FR- id. Epic IR-920 (S2 Epic: Frontend UI/UX Redesign). [`frontend_ui_audit_spec.md`](../../frontend_ui_audit_spec.md) §4.5 (amends IR-374 §4.9).

## Capability source

The server did not expose an authoring capability, so this change adds one. **New field: `can_author` on `GET /users/me/` and the sign-in `user` payload** (`MeSerializer`, read-only, own payload only, no migration). It is `core.permissions.can_author(user)`, the function `IsAuthor` now calls, so the flag and the gate on `POST /records/` are one rule (Student or Adviser). No separate backend ticket: the backend half ships in this PR, at the owner's direction.

## What changed

- **Backend.** `core/permissions.can_author()`; `IsAuthor` delegates to it; `MeSerializer.can_author`.
- **Frontend.** `User.can_author`, read through `canAuthor()` in `lib/access.ts` (a missing flag counts as no). Discover's Publish button and empty-state action, My Library's Publish and research tabs (Overview, My submissions), and Help's "Publishing your research" section follow it. A non-author's My Library shows Saved papers and Download requests only. `PublishDialog` no longer opens for them: a `?publish=` link opens a short "Publishing isn't available to your account" dialog instead of nothing, and starts no draft.
- **No role-name check remains** on these paths. The screen map's `submit` entry stays only as the record of the `/records/add` redirect.
- **There is no top-bar Publish in the code**; the places that offer it are Discover and My Library, both covered.

## Tests

- `backend/apps/accounts/test_can_author.py`: true for Student and Adviser; false for RDCO, ITSO, IERC, KTTO, System Admin and an account with no role; an office coordinator still false; carried on sign-in; absent from other users' payloads (`UserSerializer`, `AdviserOptionSerializer`); read-only on PATCH; the flag and `IsAuthor` agree for every role.
- `lib/access.test.ts`: `canAuthor` reads only the flag.
- `DiscoverPage.test.tsx`, `MyLibraryPage.test.tsx`, `HelpPage.test.tsx`, `PublishDialog.test.tsx`: the capability is mocked. A Student the server refuses sees no Publish and only the two reader tabs; a non-Student the server allows sees both; a payload with no flag cannot author; the deep link explains and starts nothing. Authors unchanged.
- e2e smoke fixture (`e2e/smoke/support/fixtures.ts`) now carries `can_author`.

## Evidence

- Frontend, run locally 2026-11-15: `tsc --noEmit` clean; the five touched suites pass (259 tests).
- **Backend tests were not run locally** (no PostgreSQL in this environment); `manage.py check` passes and the new module collects (8 tests). CI is the gate.
- **Deliberate test change:** `PublishDialog.test.tsx` "does not open for someone who cannot author" asserted no dialog at all; the ticket requires a deep link to explain, so it now asserts the explanation.
- **Not checked:** in a browser or by a screen reader.
- **Review fixes applied:** the "unavailable" dialog's copy states no role rule (it would go stale if the server's rule changed); the docstring no longer cites the frozen SRS; Help reads the flag directly; the My Library local is `mayAuthor`.
- **Decision:** `LibraryOverview` and `MyResearchList` keep their own Publish links ungated; they render only inside the author tabs, which a non-author cannot reach.
