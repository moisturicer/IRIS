## IR-1319

**Requirement:** An Adviser opening an empty My Library from inside the app gets its data in under 400 ms at the median on `npm run preview:local`, measured with IR-1314's probe over 10 runs. `/records/mine/`'s output and who may see it are unchanged. No FR- id. Found by IR-1314, which measured a median of 526 ms (max 684 ms) for this case.

**Outcome: not reproduced, no code change.** On origin/main `b018b491` the case already meets the bar, by the same probe, under every condition tried below. Neither of the suspected causes holds: `/records/mine/` and `/dashboard/stats/` are each cheap on the server, and the stats read costs a reviewer no more than a non-reviewer.

**Setup (2026-11-24, locally):** the Compose stack from the main checkout, with `backend` and `migrate` mounted from an origin/main worktree, so the server ran origin/main's code. `npm run preview:local` was built from the same worktree. Chromium through Playwright, signed in through the form, using the seed accounts `adviser@iris.test` (an author with no own records and no saves; lands on My Reviews) and `ierc@iris.test` (not an author; lands on My Reviews). The Adviser's list was empty (`/records/mine/` returned `[]`). IR-1314's PR #1002 was not yet merged; the frontend build it adds was measured separately (row 3).

The sidebar's stats read starts 27 ms earlier and is mostly done before My Library's reads begin. In row 6 it is sent twice, once for each address change.

`/dashboard/stats/`'s slowest query is My Reviews' waiting count (`reviews_reviewerseat` join): 8 ms for the Adviser, 6 ms for IERC. The Adviser's empty `/records/mine/` runs one query, because `workflow_facts` and `clearance_strips` have no records to look at.

**A measuring trap, recorded so nobody repeats it:** timed in-process with Django's test client, every request also pays for django-debug-toolbar (`config/settings/development.py`), about 43 of a 58 ms request. The client's address is 127.0.0.1, which is in `INTERNAL_IPS`. The browser's requests reach the container from the Docker bridge (172.19.0.1), so the toolbar doesn't run for them, and the curl numbers above are the real ones.

### Why IR-1314 measured 526 ms

Not determined. The code that My Library and the sidebar call (`RecordViewSet.mine`, `DashboardStatsView`, `apps.reviews.my_reviews`) is the same in `c789b054` (the main checkout, which Compose mounts by default and so most likely what IR-1314's backend ran) and in `b018b491`, measured here. The difference was therefore the machine's state at the time. One possibility, **not verified**: IR-1314 ran its 111-file `npm run test:changed` the same day, and a concurrent test run or a busy Celery worker would slow a single-process runserver this way. On a quiet machine the case is a third of the bar.

### Production

Running the production worker model (row 7 and row 8) didn't change the picture, because the six reads are cheap and four workers handle them about as fast as runserver's threads. This measures the worker model only, on development settings and this machine. It says nothing about the AWS server, which wasn't started.

**Evidence:** the numbers above, 2026-11-24, on origin/main `b018b491`. Temporary probes and scripts were kept out of the repo. No code, test or setting was changed, so no test run was required. `/records/mine/`'s output and visibility are untouched (AC 3).

**Status:** **PARTIAL** until the PR is reviewed. Measured; no fix needed. AC 1 is this file. AC 2 is met on origin/main as it stands. AC 3 holds trivially. AC 4 doesn't apply: the cause isn't the worker count or the deployment, and no deployment change is proposed. Closing it is Ashlee's call.
