# IR-1320: Deploys update the AI's own tables

[Back to the matrix](../TRACEABILITY.md)

**Requirement:** a deploy applies pending `iris_ai` migrations before the AI gateway and AI workers start, with no manual step. A failure stops `scripts/deploy.sh` and names it. Requested by Hermoine Zozobrado on 2026-11-24. No FR- id. Epic IR-805 (Deployment).

**Why:** `deploy.sh` (IR-1018) already rebuilds every service in `docker-compose.prod.yml`, including the AI gateway, the AI runs worker and the Celery workers, and Django's `migrate` runs on every `up`. The AI runtime's schema `iris_ai` is updated only by `python -m ai.runs.migrate`, which no deploy ran. After the 2026-11-17 deploy nobody could confirm 0019 and 0020 were applied.

**Design:** this follows ADR-014's IR-826 amendment. The maintenance login goes only to the one-shot command, and never to `ai/.env` or a running service.

## What changed

- **`docker-compose.prod.yml`:** a one-shot `ai-migrate` service, built from `./ai`, runs `python -m ai.runs.migrate`.
  - **Login:** it uses the database owner from the repo-root `.env`. The address is `RUNS_MIGRATION_DATABASE_URL=postgresql://${DB_USER}@db:5432/${DB_NAME}`, and the password goes in `PGPASSWORD`, which asyncpg reads when the address has none. So a password needs no URL quoting.
  - **No `ai/.env`:** it never sees the runtime login or a vendor key.
  - **Network:** private only.
  - **Order:** it starts after Django's `migrate` completes, because some `iris_ai` files read Django's tables. `ai-gateway` and `ai-runs-worker` start only after it completes successfully.
- **`scripts/deploy.sh`:** `migrate` and `ai-migrate` are its one-shot services (`ONE_SHOTS`). Each must exit 0, and a failure stops the run.
  - In step 3, a failed `up` names the first one-shot that didn't finish, in run order. The message is "ai-migrate didn't finish (exited 1): the AI schema update (iris_ai) failed", followed by its log.
  - In step 4, a one-shot found exited non-zero fails at once.
- **`deploy/tests/check_compose_prod.py`:** `ai-migrate` is a one-shot. The AI services must wait for it, and no other service may hold `RUNS_MIGRATION_DATABASE_URL`.
- **`ai/.dockerignore`** (new): the AI image had none, so `COPY . ./ai/` baked the server's `ai/.env`, with its vendor keys and runtime login, into every AI image as a file. It was never loaded, because the settings read `/app/.env`, but it was there. Now `.env` and `.env.*` are left out and `.env.example` is kept. The services still get their settings from Compose's `env_file`.
- **`deploy/README.md`:** step 3 names `ai-migrate`. A new section says what it does, where its login comes from, how to read what it applied, and that a new server needs `provision_research_roles` first.
