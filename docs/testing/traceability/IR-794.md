# IR-794: A daily job erases personal data past the retention periods the System Admin sets

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** ADR-051 decision 19 (subtask 15 of IR-779). No `FR-` id.

**Status: PARTIAL.** The job, the registry and the first type exist. Only download notes are registered. Removed and deleted comment text, comment reports (IR-420) and per-account view records register when those features ship, each with its own setting migration. No period is approved, so every setting is blank and production erases nothing.

**What was built**

- `apps/audit/retention.py`: a registry of `RetentionType(key, setting_key, erase)` and `run_retention`, which reads each type's period from system settings, calls `erase(cutoff)` for the types that have one, and writes one `RETENTION_CLEANUP_RUN` audit event (`audit/0016`) with `{"counts": {type: n}}`. The whole run is one transaction, with the event written directly so a failed write rolls the erasure back. The periods are read under a row lock, as the settings PATCH does. One type that keeps failing stops the others and fails the task daily, which is the cost of never leaving an erasure unrecorded.
- `apps/audit/tasks.py` and the `retention-cleanup` beat entry: daily at 03:00 Manila (19:00 UTC).
- `apps/records/retention.py`: registers `download_notes`, which blanks `DownloadRequest.note` and `rdco_note` on every finished request whose last activity (created, decided, revoked, cancelled or the end of an approved grant; a revoked grant counts from the revocation) is older than the period. Pending requests are never touched. A note exactly one period old is kept.
- `accounts/0019` creates `retention.download_notes_days` blank, because a settings PATCH never creates a key (IR-667).
- `SystemSettingView.patch` refuses a retention period that is neither blank nor a positive whole number of days. The job treats such a value as blank anyway and logs a warning, so a value written some other way can't make it guess.
- `backend/.env.example` has no entry: the periods are system settings, not environment variables, and nothing is read from the environment. A comment there says so.

**Not covered, by decision**

- `Notification.message` copies RDCO's note when a request is declined or revoked (`notify_download_reviewed`, `notify_download_revoked`). That is a second copy of the text, and this job doesn't reach it. Notification retention isn't in IR-794's criteria; it needs its own type and the data protection officer's answer (IR-123).
- Audit events are exempt, as ADR-051 says. The `DOWNLOAD` audit event naming a downloader can't be erased, and IR-123's checklist still needs a different answer for it.

**Tests:** `apps/audit/tests/test_retention.py`, with the clock frozen by passing `now`:

- blank, missing and malformed periods erase nothing, and every registered type has a blank setting from the migrations;
- the boundary: a note exactly one period old is kept, one second older is erased;
- a second and third run change nothing, the next day erases what has since come due, and a run that fails part-way erases nothing and writes no event;
- the run's event holds counts and no note text, email or title;
- during a run no UPDATE or DELETE statement touches the audit table, and the existing audit rows are unchanged;
- a stand-in type registers and is erased by the same job under its own period, and a blank period leaves it alone;
- the beat entry, the task, and the settings API (System Admin sets, RDCO refused, a non-numeric value refused, every change audited with old and new).
