# IR-997: a guided tour of the Review workspace

**Requirements:** none by `FR-` label. A frontend onboarding subtask of IR-870. No ADR changes: it explains controls the workspace already has and adds no capability, permission or workflow rule.

What changed (frontend only):

- **Offer** (`ReviewWorkspaceLayout.tsx`). A first-time reviewer sees a small, dismissible "New to the Review workspace?" card in the review pane's header (beside **Open review pane** while a narrow window keeps the pane closed), with **Start tour** and **Not now**. Nothing opens by itself. Whether it was offered is kept in `localStorage` (`tour/tourStorage.ts`, wrapped in try/catch), so it is a per-browser convenience that nothing server-side sees.
- **Start again.** A **Take a tour** button stays in the pane header. While a narrow window keeps the pane closed, the same button sits beside **Open review pane**.
- **The tour** (`tour/GuidedTour.tsx`, `tour/tourSteps.ts`). One highlighted area at a time: the paper, the pane's sections, **Your review**, and **People & details** (the **Details** tab when the sidebar is folded; the launcher when the pane is closed on a narrow window). The text names only the tabs that exist (Changes needs two Versions). Each step shows "Step n of N", **Next** / **Previous**, and **Skip tour**; the last step's Next reads **Done**.
- **Not modal.** The highlight is drawn and takes no clicks, so no target problem can leave a blocking overlay. The card is a dialog that takes focus on open, keeps Tab inside, closes on Escape and hands focus back to whatever opened it (`useDialogFocus`).
- **Unavailable targets.** A step whose target is missing, inert or hidden is dropped from the walk and from its count, re-checked each render. The current step is remembered by id, so opening the pane mid-tour restarts the walk instead of skipping a step. With none left the tour closes. If the opener is out of reach on close, focus goes to a button that is not.
- **No effect on the review.** Closing leaves the tab, the open threads, the drawer and every record untouched. The tour makes no API call.

**Evidence:** run 2026-11-12 on Windows.

- `ReviewTour.test.tsx`: **18 tests passed**. They cover the offer, dismissal across visits and storage that throws, step order, progress, Previous, Done, the tab list with and without Changes, no paper, the narrow launcher step and offer, the walk restarting when the pane opens, the folded Details step, Skip, Escape, focus in and back, the Threads tab left selected with no extra read, starting again, and axe.
- `npm run test:changed`: **15 files, 306 tests passed**.
- `tsc --noEmit` is clean. `eslint` on `paper-view` gives 0 errors; its one warning is in `PaperViewPage.tsx`, which this change doesn't touch.

**Per browser, not per reviewer:** whether the tour was offered is a `localStorage` flag, because the ticket bars server state. A second reviewer on a shared browser is not offered it, and a new device offers it again; **Take a tour** is always there.

**Not proven:** where the card and highlight sit on a real page. jsdom computes no layout, so placement, clamping on a phone and scrolling a target into view are untested; that needs a manual look at the three breakpoints. Colour contrast also stays a manual check. The full frontend suite was left to CI.

**Not covered:** the author's layout (`AuthorReviewWorkspace`) has no tour. Its pane is only Conversation and Threads, with no footer or sidebar, so this copy would be wrong there; that would be a separate ticket.
