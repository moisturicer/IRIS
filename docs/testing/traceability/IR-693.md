## IR-693

**Requirement:** RDCO and the System Admin see every reported Comment on one page and remove it with a reason or dismiss its reports; they can also remove any comment from the paper. ADR-032 §7, amendment 2026-10-31, and its build decisions of 2026-11-15; spec IR-420. No FR- id. The server side is IR-691.

**Design:** ADR-032 (the 2026-11-15 build decisions: one queue both roles share at `/moderation/comments`, Remove in the queue and on the paper, the sidebar counts the queue).

**Implementation:**

- `frontend/src/features/admin/ReportedCommentsPage.tsx`: each item shows the writer, its paper (linked), the wording as reported and, when the writer edited it since, the wording now, the reasons with how many gave each, *Other*'s notes and when it was first reported. It never names a reporter. **Remove** opens `RdcoNoteDialog` for the reason the writer is told; **Dismiss** closes the reports. After either, success or not, the queue and the sidebar count are read again, so a 409 from someone acting first ends with the page current. A reply the page cannot draw counts as a failed read, never as an empty queue.
- `frontend/src/api/moderation.ts`: the queue, `remove/` and `dismiss/`.
- Paper View: `CommentItem.tsx` offers **Remove** in a comment's menu when the server says `can_remove` and the comment is someone else's and standing; `CommentsSection.tsx` asks for the reason in the same dialog. Closing it, after a removal or a refusal, reads the thread and the sidebar count again; so does a report, so Report leaves the menu of a comment the reader reported.
- Navigation: `lib/access.ts` has two entries at one path, `reportedComments` (RDCO's section) and `adminReportedComments` (Administration), as Notices does; the router guards it for both roles. The sidebar reads `reported_comments` from the queue count and badges both entries; each count is checked on its own, because the System Admin's reply holds only that one.
