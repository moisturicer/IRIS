## IR-440

**Requirement:** **Retrieval looks past 40 candidates** — no FR- id; a bug fix, not a technique

**Design:** [ADR-023 §Amendment](../../adr/023-retrieval-quality-evaluation.md) (the harness is what found it) · [ADR-013](../../adr/013-chunk-level-rag-pipeline.md)

**Implementation:** `apps/ai/retrieval/scan_depth.py` — `scan_depth()` sets `hnsw.ef_search` with `set_config(..., true)` (transaction-local, so safe behind PgBouncer transaction mode) around both stages of `TwoStageRetriever`, which reads its rows inside the block. Setting `AI_HNSW_EF_SEARCH`, default 200, clamped to pgvector's 1..1000. pgvector's own default of 40 meant the reranker's `recall_limit` of 100 was never reached

**Test:** `apps/ai/retrieval/tests/test_two_stage.py::ScanDepthTests` — with sequential scan and sort disabled so the planner uses the HNSW index, a limit of 100 returns more than 40 rows (41 before the fix) and a low depth setting lowers the count

**Evidence:** Run `docs/evaluation/runs/20260930-182254-proxy-starter.json` (52 questions, 40-paper proxy tier, `degraded_questions` 0): recall@10 no-rerank 0.596 → 0.712, rerank 0.683 → 0.885; final-set rerank 0.663 → 0.846. Fusion re-measured on the new depth (`…-182520-…json`): rerank 0.885 → 0.894 (under one question), final-set 0.846 → 0.875, and without rerank it is worse (0.712 → 0.692), so most of IR-395's +0.192 was the cap, not keyword matching. Cost: a reranked 52-question run took 83 s at depth 40 and 98 s at 200 (+0.29 s per question); the reranker sees about 100 passages instead of about 40

**Status:** **IMPLEMENTED, tested, re-baselined.** A fixed depth goes stale as the corpus grows — iterative scan is the durable answer (follow-up)
