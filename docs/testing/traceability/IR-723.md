## IR-723 — Keep queued research running after the browser disconnects

**Basis and scope.** IR-723 under IR-713; authority ADR-049 §2, §3, §10, §12. Durable dispatch and fair admission for the AI runtime's own runs. Checkpoint recovery of a worker that dies mid-step is IR-724; Stop races are IR-726; moving every paid attempt onto shared admission is IR-725.

- **Durable work, then a wakeup.** `POST /api/v1/ai/runs` commits a `queued` run and only then wakes workers (`ai/runs/dispatch.py`: a bounded Redis list, `RUNS_REDIS_URL`, or none). Submission no longer runs the executor inline. A wakeup is a hint: workers (`python -m ai.runs.worker`, `ai/runs/worker.py`) claim from PostgreSQL under one short advisory lock (`RunStore.claim_next`) and scan every `RUNS_POLL_SECONDS` anyway, so a lost, failed or duplicated wakeup changes only when a committed run starts. A failed wakeup is logged, never surfaced.
- **Disconnect never cancels.** Only Stop ends a run early; the reader reconnects through `GET /runs/<id>`.
- **Worker authority.** The owner chose (2026-11-01) to store the submitting `reader_session` grant on the run (`reader_grant`, `grant_expires_at`; migration `ai/runs/migrations/0003_dispatch.sql`), readable only by `iris_ai_runtime`, cleared when the run ends. A worker claims a run only while its grant covers a whole lease (`RUNS_LEASE_SECONDS`); otherwise it waits, shown as `awaiting_reader: true`, for the reader to reconnect, and a status read with a fresher grant of **exactly** the Conversation's scope renews it, so a reconnect never widens what a run reads. A run whose reader never returns expires at its deadline. Like IR-719's choice this departs from ADR-049 §6–7's run-bound grant and control-plane renewal; the amendment is still to be written.
- **Bounded populations.** Admission takes one short advisory lock and refuses with `503 {"status": "busy", "reason": "reader_queue_full" | "queue_full"}` past `RUNS_MAX_ACTIVE_PER_READER` or `RUNS_MAX_QUEUED`, writing nothing; a repeated request identity is still its existing run. A Conversation keeps one state-advancing run (IR-722's index): a second question while one is queued is `409 run_in_progress`, a stale one `409 revision_conflict`; nothing is queued behind it or remapped.
- **Fair claiming.** Deep runs (`depth: "deep"`, ADR-049 §16) are capped at `RUNS_DEEP_CONCURRENCY` running at once, which must be below `RUNS_WORKER_CONCURRENCY`, so ordinary questions keep every other slot; below the cap a waiting deep run is claimed first, so it cannot starve. A reader already running `RUNS_MAX_RUNNING_PER_READER` waits. Each slot holds at most one database connection at a time.
- **Deadlines and latency.** Each depth has its own deadline (`RUNS_DEADLINE_SECONDS`, `RUNS_DEEP_DEADLINE_SECONDS`), fixed at admission; queue waiting counts against it, and claiming sweeps overdue runs to `expired`/`deadline`. The projection adds `depth`, `started_at`, `awaiting_reader`, `queued_seconds` and `latency_seconds`, the last two measured from submission.
- **Separate capacity.** Request handling is the gateway; interactive and deep runs are `ai-runs-worker` (Compose profile `runs`, opt-in); ingestion stays on the Celery `extraction`/`embedding` workers and never takes a research slot. No ingestion runs in the AI runtime yet (IR-737), so this separation is structural, not measured.
- **Fail closed.** Every new limit is required and none is approved (`ai/.env.example`); an unset one keeps the routes `unavailable` and the worker refuses to start.

**Tests.** `apps/ai/tests/test_ai_runtime_dispatch_db.py` (11, real PostgreSQL, a throwaway `iris_ai_runtime` login, Django-issued grants, independent worker processes `ai/tests/dispatch_worker.py`): a run committed while its wakeup fails survives the reader leaving and is answered once by two independent workers; with real Redis, repeated wakeups plus a worker killed mid-run and three restarted workers deliver one Turn and one `completed` (the dead worker's lease is expired by hand, since lease recovery timing is IR-724's); a lapsed grant is not run, an unscoped reconnect does not renew a Paper Chat run, a matching one does, and the grant is cleared at the end; queue waiting counts against the unchanged original deadline and an overdue queued run is `expired` without starting; each depth keeps its deadline and an unknown depth is 422; full queues answer `busy` and write nothing; a second question on a queued Conversation is refused; deep work gets its slot and never more, and one reader cannot hold every slot; and a declared synthetic workload — 2 processes × 2 slots, deep cap 1, 3 deep runs of 1.5 s and 6 ordinary of 0.2 s from nine readers — completes everything with at most one deep run at a time, every ordinary run started before the first deep one could end, and at most four runtime connections observed. `ai/tests/test_runs_config.py` covers the new required limits and the deep-below-slots rule. IR-722's and IR-719's suites now drain the queue in-process from their fixture (`Drain`) because inline execution is gone — a deliberate fixture change, not a weakened assertion; the pinned schema assertion moves to `0003_dispatch.sql`. The synthetic and Redis tests passed three repeated runs.

**Migration evidence.** On a copy of the dev database (63 Records), 2026-11-01: Django migrations and `provision_research_roles`, then `0001`/`0002`, a queued run inserted, then `0003_dispatch.sql` applied over it (`depth` `ordinary`, no grant, so it can only expire), and a re-run applied nothing; `iris_ai_runtime` may update `reader_grant` and `iris_django_runtime` may not read it. The copy was dropped.

**Not done here.** The ADR-049 amendment recording the stored-grant choice is not written. The executor keeps the grant it was claimed with: a renewal reaches the next claim, not a running executor, so a run longer than `AI_RESEARCH_GRANT_TTL_SECONDS` (default 300 s, at most 900 s) loses its tools mid-run; deep deadlines beyond that need IR-724's renewal. `RunStore.admit`'s population bounds default to none for store-level callers; only the service, which always passes them, is fail-closed. The ticket's independent demonstration is covered across three tests, not run as one scenario. Ingestion separation is structural only (no ingestion runs in the AI runtime). A worker that dies mid-run is reclaimed only after its lease and starts again (IR-724 checkpoints). Stop does not reach an executor already running (IR-726). The deterministic executor proves contracts, not paid capacity; no production concurrency, deadline or queue value is chosen, and nothing is measured beyond the synthetic workload. The reader UI does not use these routes.

**Status.** Implemented; awaiting review.
