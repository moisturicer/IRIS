## IR-378

**Requirement:** **Inference tasks and Profiles — a caller names a task instead of asking for "the LLM"** — no FR- id; part C of IR-375's spec, and the expand half of expand–contract

**Design:** [ADR-036 §Amendment](../../adr/036-openai-compatible-inference-provider.md) (one adapter per protocol, **vendor chosen per Inference task**, not per environment) · [ADR-008 §Amendment](../../adr/008-ai-degradation-to-fts.md) (a fallback list of models inside **one** vendor account; cross-vendor failover still refused)

**Implementation:** `apps/ai/inference/tasks.py` — the closed four-name set (`answer`, `resolve`, `summary`, `describe_figure`); an unrecognised name raises `UnknownInferenceTask` rather than resolving to a default · `apps/ai/inference/profiles.py` — one `Profile` per task carrying vendor, model, ordered same-vendor fallback models, reasoning visibility and the uniform `NO_TRAINING` data policy, resolved from per-task `LLM_<TASK>_*` settings on demand, never at import · `apps/ai/inference/providers.py` — builds the provider a Profile describes through the existing resilience stack, and keeps appending the legacy cross-vendor `LLM_FALLBACK_*` entry for `answer` only, so an opted-in deployment is unchanged until the IR-375 contract ticket removes it · `apps/ai/composition.py` — `llm_for(task)` beside the existing `llm()`, Profiles resolved lazily and one provider cached per task; `answer_service()` now reaches its model as `InferenceTask.ANSWER`. `answer` inherits the flat `LLM_BASE_URL`/`LLM_API_KEY`/`LLM_MODEL`, so a deployment that sets none of the new variables behaves identically; the other three tasks are off until given a model. `resolve` and `summary` are **not wired to a caller yet** and `describe_figure` is declared and unused. **Recorded contradiction, not reconciled:** `LLM_RESOLUTION_MODEL` (IR-296) is what `CompositionRoot.resolver()` actually reads, while the new `LLM_RESOLVE_*` keys configure a `resolve` Profile no caller reaches — two live namespaces for one Inference task, noted in both settings blocks and `.env.example` until the resolve-wiring ticket collapses them

**Test:** `apps/ai/inference/tests/test_profiles.py` (17 — the closed set, the typo refusal, per-task vendors, the flat-settings inheritance, a named vendor stopping the flat **key** being inherited so a request cannot reach one vendor authenticated for another, an inherited base URL deciding the vendor it points at (IR-382 selects a dialect on that field), a self-hosted URL not refused where a *named* vendor outside the pair is, per-task reasoning visibility, a same-vendor fallback list, an unconfigured task raising rather than borrowing a model) · `apps/ai/inference/tests/test_reserved_task.py` (1, file scan — nothing under `apps/` reaches for `describe_figure`) · `apps/ai/tests/test_inference_tasks_http.py` (5, HTTP boundary — the `answer` task reaches the model *and key and base URL* its Profile names, with `openai.OpenAI` replaced by a recorder; the flat-settings deployment still reaches its old model; an injected fake bypasses Profile resolution; calling the legacy `llm()` first does not make every task answer, since it caches apart from the injection slot; an unknown task name is refused by the root)

**Evidence:** `apps/ai` **1092 passed, 2 failed**; full backend suite **1766 passed, 2 failed, 2 skipped, 1 xfailed** (2026-09-28). Both failures are pre-existing and environmental, not from this change: `test_llm_contracts.py`'s temperature and reasoning-effort assertions read the developer's own `backend/.env` (`LLM_TEMPERATURE=1`, `LLM_REASONING_EFFORT="high"`), and they fail identically on a stashed tree

**Status:** **IMPLEMENTED** — the foundation only. Startup refusal for a configured keyless task (IR-379), `summary` as its own task (IR-380), live Reasoning (IR-381), the per-vendor dialect (IR-382) and deleting `llm()` follow in their own tickets
