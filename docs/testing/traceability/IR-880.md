## IR-880 — Keep a long investigation reading after its reader grant's lifetime

**Basis and scope.** IR-880 under IR-713; authority ADR-049 §6, §7, §9 and the ticket's acceptance criteria. Grant renewal for a *running* run only. Stop, reconnect replay and Retry are IR-726's; grant lifetimes and the grant format are unchanged.

**The gap.** A worker's tools read under the `reader_session` grant the run was claimed with. A reader's reconnect (`RunStore.status`) already renews the grant stored on the run (IR-723), but only the next claim read it, so a run longer than `AI_RESEARCH_GRANT_TTL_SECONDS` lost its tools partway through even while the reader was connected. Provider admission (`SendGuard`) already read the stored `grant_expires_at`, so it already followed a renewal; the research tools did not.

**Code.**
- `ai/research/tools.py`: `ResearchTools(..., follow_stored_grant=False)`. When on, each call reads the run's `state`, `fence` and `reader_grant` inside the call's own short transaction, refuses a run that is not `running` on this fence (`run_ended`) or has no stored grant (`unauthorized`), verifies that grant in PostgreSQL as before, and additionally refuses it unless its scope (`rec`) equals the claim's scope exactly (`unauthorized`). The reader-matches-run check and the `FOR SHARE` run lock are unchanged. Off (the default), the constructor's grant is the authority, as before, so tests and callers that pass a specific grant are untouched.
- `ai/runs/service.py`: `RunService.execute` builds its tools with `follow_stored_grant=True`.
- No schema change, no migration, no change to `RunStore.status`' renewal rule (still: only a grant of exactly the Conversation's scope, and only when it expires later), no change to grant issue.

**Evidence (2026-11-05, this machine).** A throwaway `pgvector/pgvector:pg16` container and the `ir726-test` Python 3.12 image (repo dependencies installed) ran the branch, serially (`-n 0`). `test_ai_runtime_grant_renewal_db.py`: 11 passed. With the `RunService` wiring switched off, the reconnect test and the revoked-reader test failed (`failed` != `completed`; no `admission`), confirming they exercise the change; the wiring was restored. `test_ai_runtime_research_db.py` (the existing tools tests, unmodified), `apps/tests/test_parallel.py` and `apps/tests/test_enum_vocabulary.py`: all passed. The new module is registered in `backend/testing/parallel.py` `ROLE_MODULES`.

**Honest notes on what the tests found.** My first draft expected a differently scoped grant to leave the run untouched without error; `RunStore.status` already hides the run from another scope (`NotFound`), and lets an unscoped grant look at it without storing it. The tests record that real behaviour. The first draft also read the outcome through `status` with a grant that had lapsed or whose account had been deactivated, which is itself refused; the helper now reads the outcome as an operator would.

**Not verified / limits.**
- The rest of the backend suite, and the AI neighbours (`runs_db`, `dispatch_db`, `recovery_db`, `turn_recovery_db`, `agent_loop_db`, `lifecycle_db`) were not run locally; CI covers them. `turn_recovery_db` and several others build `ResearchTools` with the flag off, so they should be unaffected.
- A run continues only while *something* calls `RunStore.status` with a fresh grant. That is the reader's poll or reconnect; it is not a server heartbeat, so a reader whose client has stopped polling (and does not reconnect before the stored grant lapses) ends the run unauthorized. This is the ticket's intent (AC3), but it makes the reader's polling interval relevant: it must be shorter than `AI_RESEARCH_GRANT_TTL_SECONDS`. Whether the production reader polls often enough was not checked here.
- A tool call in flight when the grant lapses finishes under the grant it already verified for that transaction; the next call refuses.
- The agent executor's own handling of an `unauthorized` tool result (which public state a real run ends in) was not exercised; the test executor raises `Unavailable` on a refused read, so the ticket's "ends `unauthorized`" is asserted at the tool result and as a failed run, not through the agent loop.
- The test sleeps real seconds (about 4.6 s per investigation test) because PostgreSQL verifies expiry against its own clock; no clock is faked.
- Everything uses a scripted executor and Django-signed grants: no live provider was called and nothing measures paid capacity.
- `IR-880` lacks the `ready-for-agent` label in Jira although its description has criteria and a blocker.
