**Requirement:** Authentication

**Design:** **ADR owed** — the basis here is the requirement id alone; SDD M6 is frozen and is not authority (see CLAUDE.md)

**Implementation:** `apps/accounts`, SimpleJWT. **Frontend return-to-destination (IR-236):** `components/auth/ProtectedRoute.tsx` passes the attempted location to `/login` in router state; `features/auth/LoginPage.tsx` captures it on mount and navigates there on success, falling back to `lib/roleDashboard.ts`; `lib/redirectTarget.ts` is the single validator every destination passes through; `lib/authSession.ts`'s idle-timeout hard redirect carries the page in `?next=`. `router/PrivateRoute.tsx` **deleted** — a second, unimported guard that ignored the hydration flag

**Test:** `frontend/src/lib/redirectTarget.test.ts` (15), `frontend/src/components/auth/ProtectedRoute.test.tsx` (9), `frontend/src/features/auth/LoginPage.test.tsx` (11, of which 7 are new); shared fixtures in `frontend/src/test/authFixtures.ts`

**Evidence:** **IR-236, 2026-09-11:** `npm test` → **9 files, 76 tests, 0 failed**; `npx tsc --noEmit` clean; `npm run lint` 0 errors (9 pre-existing warnings, none in the touched files); `npm run build` green. Asserted: hydration incomplete renders the waiting state and does **not** redirect; no token redirects carrying the destination, query and fragment intact; an expired token redirects with its own `session_expired` reason; a valid token with a permitted role renders the route; a signed-in user lacking the role gets the 403 screen rather than login. Hostile destinations rejected in favour of the role default — off-origin, same-origin absolute, protocol-relative (`//`), its backslash spelling, control-character smuggling (`/<tab>/evil`), `javascript:`, `data:`, dot-segment assembly (`/..//evil` — see the third defect below), and the auth screens themselves. The two hostile-destination login tests also assert the rejected host is **absent** from the landing page, because the role default is where a visitor with no destination goes too — without that second assertion they would pass with the feature deleted. axe-core (serious/critical) on the rendered states; all queries by role and accessible name

**Status:** **PARTIAL** — rotation and blacklisting correct; **30-min inactivity expiry still absent server-side (NFR-S2)**. What IR-236 adds is that a deep link now survives sign-in, and it closed **three defects found by the tests and review rather than assumed**: (1) the expired-session `reason` never reached the login screen at all — `logout()` ran *during render*, re-rendering the guard before the redirect committed, so the second render took the "no session" branch and destroyed it; a ref now makes the decision sticky. (2) The guard's waiting state was an `aria-hidden` spinner in an unlabelled `div`, i.e. **silent to a screen reader** — it now carries `role="status"` with a name. (3) `safeRedirectPath` itself had a **live bypass**, caught by the spec review and reproduced before being fixed: `new URL` resolves `/..` by popping a segment, and popping the *empty leading* segment rewrites `/..//evil.example` into the pathname `//evil.example` — so the input never started with `//`, the origin was still ours, and the function returned the protocol-relative string it exists to refuse. The check now also runs on the **output**, which is the only placement a caller cannot walk around by making the parser do the assembling; `/review/12/../13` → `/review/13` still resolves, so the fix is not a blunt ban on `..`. **Carve-out, named rather than smoothed over:** the `?next=` query parameter is **not in IR-236's text**. It exists because the NFR-S2 idle path is a full page load that no in-memory state survives, and it is validated on arrival by the same predicate as router state — but it is a forgeable, shareable destination channel, and a hostile value is left in the address bar rather than stripped (inert, since every read re-validates). **A person should confirm that trade-off**
