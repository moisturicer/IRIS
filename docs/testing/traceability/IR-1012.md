## IR-1012 — Pool the AI runtime's database connections and size it for production load

**Basis and scope.** IR-1012 under IR-955. IR-1007's first burst ran PostgreSQL out of connections, because the gateway and runs worker opened a fresh `asyncpg` connection for every operation, and a refused connection answered HTTP 500 instead of `503 busy`. Its second burst answered 99 of 100 but queued: 8 worker slots and 4 deep slots (deep is the default depth) made an ordinary answer wait about three minutes. The owner asked for at least 20 simultaneous questions answered without delay (2026-11-10). The 20-question burst's spend (about US$0.10 on the development campaign) falls under the same request.

**What changed.**
- `ai/infrastructure/db.py` (new): one bounded `asyncpg` pool per process and event loop, turned on by `configure(dsn, size, acquire_seconds)`. Unconfigured, it opens a connection per use, as before, so tests and maintenance scripts behave unchanged. Waiting past the acquire timeout, or a connection PostgreSQL refuses (too many connections, starting up, nothing listening), raises `Exhausted`. Errors inside the caller's own work are never translated.
- `RunStore`, `ResearchTools` and the admission `Ledger` take connections from it. In the store, `Exhausted` becomes `Busy("database")`, which the routes already answer as `503 busy`. In the ledger it is a store failure (`store_unavailable`), and in a research tool it is a tool outage (IR-731).
- `RUNS_DB_POOL_SIZE` and `RUNS_DB_ACQUIRE_SECONDS` are required, like every `RUNS_*` limit. `ai.runs.worker.build` configures the pool, and the worker closes it on shutdown.
- **The grant cannot leak.** `iris_authz.begin_research` binds with `set_config(..., true)`, which is transaction-local, and asyncpg's release runs `RESET ALL`. A test proves a returned connection holds no grant.
- **Sizing** (`ai/.env.example`, `docker-compose*.yml`, `AI_RUNTIME_LIMITS.md`):
  - Worker: 24 slots and 20 deep per worker. Five workers in production (120 slots, 100 deep), 1 GB each, for 100 readers at once (owner's request, 2026-11-10).
  - Lanes: research 120, embedding 32, reranking 8. Account concurrency 128.
  - Pools: 30 per worker, above its 24 slots, because a tool call that waits on an earlier one in its group holds its connection. 8 per gateway process (4 × 8). That totals 182 runtime connections in production.
  - PostgreSQL: `max_connections` 300, `shared_buffers` and `effective_cache_size` from the host, `shm_size` 256 MB.
  - Django: 2 CPU, 2 GB.
  - `MAX_CONCURRENT_LLM` is removed: nothing read it.

**Not changed, and why.** Django keeps a connection per request. Under ASGI, its sync views run in one thread per worker, so 4 workers hold about 4 connections. Django's documentation advises against persistent connections under ASGI. PgBouncer is not added: with the runtime pooled, it is not needed at this size.

**Tests.**
- `backend/apps/ai/tests/test_ai_runtime_pool_db.py` (5, real PostgreSQL):
  - Ten readers at once share a pool of two.
  - An exhausted pool makes the store `busy` with reason `database`.
  - A refused connection (nothing listening) answers the reader `503 {"status": "busy", "reason": "database"}` through the real route.
  - A returned connection carries no reader's grant.
  - A submission completes through the pool.
- `ai/tests/test_runs_config.py`: a new test reads the pool settings. Both are required through the existing test over `LIMIT_NAMES`. The complete-settings fixture gains them, deliberately.
- `test_ai_runtime_runs_db.py`, `test_ai_runtime_admission_db.py` and `test_ai_runtime_research_db.py` pass unchanged (48).

**Paid bursts.** Each ran on the eval copy `iris_ir956_eval` (proxy corpus) with `openai/gpt-6-luna:floor` pinned `agent-research-8`. `eval_runtime_capacity` names its files after IR-1007.

*20 readers.*
- Conditions:
  - Eval copy `iris_ir956_eval` (proxy corpus, `max_connections` 100).
  - One worker with this change's limits and a pool of 20 (raised to 40 after review); one gateway process with a pool of 8.
  - `openai/gpt-6-luna:floor`, pinned `agent-research-8`.
  - 20 readers, 20 distinct questions, 5 of them deep.
- File: `20261110-111913-IR-1007-runtime-capacity.json`. `eval_runtime_capacity` names its files after IR-1007.

- **No question waited for a slot.** 20 runs fit 24 slots, so the medians are the runs' own research and writing time.
- **The one failure is the model's, not capacity.** `5663762f` ended `unavailable: malformed` after 3 attempts: the model returned output the executor could not read.
- This is a check of 20 at once, not IR-1007's 100-question measurement. The summary's claim is `unverified` (fewer than 100).

*100 readers, the production sizing above.*
- Conditions:
  - Five workers (24 slots, 20 deep, pool 30 each) and one gateway process with a pool of 32, standing in for 4 × 8.
  - The local PostgreSQL raised to `max_connections` 300.
  - 100 readers, 100 distinct questions, 25 deep.
- Files:
  - `20261110-115948-IR-1007-runtime-capacity.json`
  - `20261110-120345-IR-1007-runtime-capacity.json`, the same questions 25 minutes later

| | Run A | **Run B** |
|---|---|---|
| Harness database host | `localhost` | `127.0.0.1` |
| Answered | 100 / 100 | **100 / 100** |
| Claim | `measured` | `measured` |
| End to end, ordinary p50 / p95 | 131 / 157 s | **54 / 80 s** |
| End to end, deep p50 / p95 | 129 / 152 s | **54 / 87 s** |
| **Queue wait in the runtime, p50 / max** | 0.5 / 1.7 s | **0.2 / 1.0 s** |
| **Run time in the runtime, p50** | 15.6 s | **18.6 s** (p95 37.6 s) |
| Submissions reached the runtime over | 152 s | 52 s |
| Peak runtime connections | 124 | 112 |
| Peak runtime memory, 5 workers and the gateway together | 724 MB | 780 MB |
| Spend | US$0.37, 350 attempts | US$0.36, 353 attempts |

- Queue wait and run time come from `iris_ai.ask_run` (`created_at`, `started_at`, `finished_at`). The connection and memory peaks were sampled every 3 s.
- **The runtime answered 100 at once without queuing.** No run waited more than 1.7 s for a slot.
- **The rest of the end-to-end time is the harness, not the runtime.**
  - The harness fetches a fresh Django grant for every submission and every status poll, four at a time.
  - On this Windows host each Django connection through `localhost` costs 2.06 s, against 0.01 s through `127.0.0.1`, which is IPv6 falling back to IPv4.
  - Run A could therefore send only about two requests a second. Run B removed that cost, but the in-process grant edge still spread submissions over 52 s.
  - In production, nginx's `auth_request` asks Django for a grant on every runtime request too (`frontend/runtime-edge.conf`). That cost has not been measured on Linux.
- Memory stayed far below the 5 × 1 GB limits: about 130 MB per process.
- Run B repeated run A's questions, so the provider's prompt cache may have been warm. Neither run controls it.

**Acceptance criteria.**
1. Pooled connections are reused and bounded, and exhaustion is `503 busy`: the tests above. **Met.**
2. A pooled connection carries no reader's grant: `test_a_returned_connection_carries_no_readers_grant`. **Met.**
3. A simultaneous burst answering every question with no queue wait, file committed.
   - 20 readers: 19 of 20 answered. One ended `malformed` from the model.
   - 100 readers at the production sizing: **100 of 100, twice**, with a median queue wait under 1 s.
   - **Met for the runtime.** End-to-end latency through the harness is 54 s median, most of it the harness's grant edge.

**Not done here.**
- A burst through the real nginx edge and Django on Linux, which is where the per-request grant costs.
- A load test of the rest of the app (Django pages and uploads).
- The `malformed` model output.
