# IR-914: request timeout, cancellation and retry policy in the API client

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** no requirement row changes. Child of IR-899 (API integration, typed contracts and session handling). The decision is [ADR-061](../../adr/061-request-timeout-cancellation-and-retry.md), **Proposed**: the ticket reserves the timeout values for the team, so 30 seconds and 5 minutes are a proposal in `frontend/src/api/requestPolicy.ts` until a named person accepts or amends them.

**The change.**

- `apiClient` gives each request a timeout in its request interceptor: 30 s ordinary, 5 min for a `FormData` body or a blob response; a caller's own `timeout` wins.
- A request that exceeds it rejects with `RequestTimeoutError` (`timeoutMs`, `method`, `url`, `cause`).
- `useApiRead(read, deps)` aborts its read on unmount and on a change of inputs, drops a response that arrives after cancellation, reports `interrupted` for a timeout and offers `retry`.
- `DeleteRequestsPage` is the pilot: its list read uses the hook and shows `InterruptedState` with Retry on a timeout.

**What proves it** (queried by role and accessible name where it is a screen)

| Acceptance criterion | Test |
|---|---|
| The timeout values and the retry rule are decided and recorded | ADR-061 (Proposed; **not yet accepted**) |
| A request that exceeds the timeout fails with a typed error the UI can show | `requestPolicy.test.ts` "fails a request that exceeds the timeout with a typed error…"; the ordinary and transfer timeouts are asserted in the two tests above it |

| No write is retried automatically | `requestPolicy.test.ts` "never retries a write on its own, timed out or not" (POST and PATCH once each); and a timed-out read is not replayed either |
| A timed-out request reaches the UI as the interrupted state with a retry action | `useApiRead.test.ts` "reports a timed-out read as interrupted, and Retry reads again"; `DeleteRequestsPage.test.tsx` "shows a timed-out read as interrupted, and Retry reads again" |

Files: `src/api/client.test.ts` (the token refresh carries the timeout too), `src/api/requestPolicy.test.ts`, `src/hooks/useApiRead.test.ts`, `src/features/admin/DeleteRequestsPage.test.tsx`.

**Not covered, said plainly.**

- **Only one screen uses the hook.** About seventy components still fetch in their own `useEffect` and are not cancellable or protected from a stale response; they do now time out. "Every list and detail fetch can be cancelled" is therefore **not met across the app**; it is met for the mechanism and one screen. Migrating the rest, and adding `{ signal }` to the remaining API read functions, is follow-up work.
- **IR-895's "interrupted" state does not exist in the repository** (no match for it or its ticket key). `InterruptedState` is an interim built on `EmptyState`; IR-895 should replace or adopt it.
- The timeout itself is axios's adapter's work. The tests make the adapter fail the way it does (`ETIMEDOUT` with `clarifyTimeoutError`); no test waits out a real 30 seconds.
