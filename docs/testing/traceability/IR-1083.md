# IR-1083: a clearance strip on My Reviews, the office console and My Library

**Requirements:** clearance-aware resubmission (ADR-003), the thesis contribution. The audit that asked for the strip is WF-06 in `docs/frontend_ui_audit_spec.md` §4.4 (IR-1071). The matrix has no `FR-` row for a list-level view of it.

## What was wrong

Which clearances a resubmission kept was visible only inside the record, on the tracker. A reviewer or an author had to open each paper to see who still held a clearance and who had been reset. My Library had a one-line partial version built on the client from `holders` and `cleared_offices`; My Reviews and the office console had nothing, because their rows carried no clearance data at all.

## What changed

**Server: one builder, `apps/reviews/clearance_strip.py`.** `clearance_strips(record_ids)` returns, per record, one entry per specialist office that was routed it: `{party, label, kind, text, note, version}`. It adds no rule of its own. `clearance_state.carryover` says what a new version kept or reset, an open `ResubmissionRequest` says an office asked for a revision, and a live `ReviewerSeat` says someone is reviewing rather than the pool waiting. It reads six queries however many records are asked for. It carries no reviewer, comment or reason, so it is safe on every list that may name the record.

Words the server chooses: `Cleared`, `Reviewing v2`, `Unclaimed`, `Asked for revision`, the negative outcome's own label, and the note `Kept from v1` or `Reset by v2`. `kind` is a closed set (`kept`, `cleared`, `reviewing`, `unclaimed`, `revision`, `not_cleared`).

The same field, from the same builder, is now on: `GET /reviews/mine/` rows, `GET /reviews/office/` rows, `GET /records/mine/` rows and `GET /records/<id>/tracker/`. The record and its row in a list cannot disagree.

**Client: one component, `components/shared/ClearanceStrip.tsx`.** It prints `label`, `text` and `note` as given and chooses only a tone and an icon from `kind` (a `Record<ClearanceStripKind, …>`, so a new kind fails `tsc`). Colour and icon are never the only signal. It draws nothing for an empty strip. Used in `MyReviewsPage` and `OfficeConsolePage` (the card footer), `SubmissionRow` (replacing the local `ReviewTrack`) and `ReviewRoutingTracker`. IR-374 invariant 15 holds: the UI computes nothing about which clearances were kept.

**Behaviour change to flag:** My Library's old line also showed *"IERC reviewing"* for every holder, adviser and RDCO included. The strip covers the three clearing offices only; where the record is with the Adviser or RDCO, the row's status badge (`submitter_status.line`) still says so.

New frontend tests: `ClearanceStrip.test.tsx` (kept, reset, words printed as given, empty or missing draws nothing and does not throw, every kind carries a word, axe), and one kept-and-reset case in each of the four surface tests above. Fixture builders in six other test files gained `clearance_strip: []`; no assertion in them changed. `MyLibraryPage.test.tsx`'s *"shows each office's clearance, kept ones marked"* now asserts the strip's words instead of the old `ITSO cleared` / `· kept` fragments, deliberately: that line was replaced.

Backend: `apps/reviews/test_clearance_strip.py` (kept from v1; reset, reviewing v2; nothing kept before a new version; unclaimed; an unrouted office not drawn; an office whose work a Decision withdrew not drawn, as the tracker reads it; cleared again is no longer reset; no review content in an entry; a flat query count; the field on My Reviews, the console, My Library and the tracker, and the tracker equal to the builder). `test_my_research_list.py`'s `LIST_FIELDS` gained `clearance_strip`, deliberately.

**Not run locally:** the backend tests. This machine has no PostgreSQL or Docker, so only a syntax check was possible; CI is the first real run, and a failure there is a finding, not noise.

**Browser and contrast, 2026-11-14:** a throwaway harness (not committed) rendered the strip inside `ResearchCard` and `SubmissionRow` with the kept, reset, unclaimed, asked-for-revision and not-cleared states, in the built-in browser at 360 and 390 px. No horizontal overflow at either width; the entries stack one per line when the three offices do not fit, and a long title does not push them out. Measured contrast of the strip's text on its background: 17.49:1 (kept, cleared), 12.34:1 (reviewing, revision, not cleared), 10.27:1 (unclaimed) and 7.63:1 for the grey note ("Kept from v1"), at 12 px. **Not checked:** the real pages (My Reviews, the console, My Library, the tracker) with real data and actions, which need the full stack.

## Open for the reviewer

- **Privacy (a person's call).** The strip shows each routed office's state (Cleared, Not cleared, Asked for revision) to anyone who can already see the record's row. The tracker serves the same data and already reaches a non-participant office member (`test_tracker_carryover.py`), so no new audience gets it; the lists are a more prominent surface for it. The strip carries no reviewer, comment or reason. Not signed off here.
- **My Library no longer shows an "Adviser reviewing" / "RDCO reviewing" line.** The strip covers the three clearing offices only; the row's status badge (`submitter_status.line`) still says where an Adviser- or RDCO-held record is.
- **"Reviewing" also covers a colleague's seat still open** beside a Done one: the office has not finished (`seats.office_complete`). A reset clearance whose assignment a Decision withdrew is not drawn, matching the tracker's *Withdrawn*; a test pins it.
