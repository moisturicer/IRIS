## FR-M6-02

**Requirement:** DPA consent

**Design:** **ADR-019 owed** — the basis here is the requirement id alone; SDD M6 is frozen and is not authority (see CLAUDE.md)

**Implementation:** **Backend (IR-226):** `Record.dpa_accepted_at` / `dpa_accepted_by`, stamped by `RecordViewSet.submit` and by nothing else; `dpa_accepted` is a derived property, so no stored boolean can disagree with the timestamp. Neither field appears in `RecordWriteSerializer`'s allowlist. **Frontend:** `DpaConsentGate`, `DpaConsentModal`, `DpaConsentInline`; `recordsApi.submit(id, dpaAccepted)` takes consent as a **required** argument so a caller cannot omit it

**IR-127** makes the stamp gate something: `apps/ai/policy` is ADR-015 §Security Impact's disclosure gate, a pure decision over IP status, embargo and this consent stamp, refusing every failing input rather than the first. It reads `Record.dpa_accepted` rather than `User.consent_given`, the per-disclosure fact rather than the once-at-signup one. **It currently refuses every record**, because no embargo field exists and an undetermined embargo is treated as an embargo rather than assumed absent — the correct direction for a gate, and tracked as IR-250, which blocks IR-130 and IR-131.

**IR-850** makes this stamp also decide whether a PDF may be sent off campus to be read; a refused read waits and is queued by the submit that stamps consent ([IR-850](IR-850.md)).

**IR-791 replaces the per-paper stamp (ADR-054 decisions 1, 9-10, 17).** Consent is now the Contact person's AI answer, copied onto the paper as `Record.ai_consent` when its draft is created and kept; the gate and the Postgres indexing functions read it, and `dpa_accepted_at` no longer counts. `submit/` asks for and stamps nothing, Publish's `DpaConsentInline` is deleted and `recordsApi.submit(id)` takes no consent. The stamp columns stay as legacy data. Everything below this paragraph describes IR-226's mechanism as it was ([IR-791](IR-791.md)).

**Test:** `apps/records/tests.py::DpaConsentAtSubmitTests` (9), renamed `SubmitAsksNoConsentTests` and rewritten by IR-791

**Evidence:** `pytest apps/records/tests.py::DpaConsentAtSubmitTests` → **9 passed in 9.43s**, run in the backend image against this branch. Asserted: a submit with no consent is refused **and the record stays in `draft`** (the ordering assertion — a check after `lifecycle.apply` would refuse a record that had already entered a review queue); an explicit `false` is refused rather than treated as merely absent; a successful submit stamps who and when; resubmission preserves the *original* timestamp; and consent cannot be set by PATCH

**Status:** **IMPLEMENTED** (2026-09-10, IR-226) — **the previous IMPLEMENTED on this row was wrong and is corrected here.** It rested on two React components: the wizard's step-3 gate was browser-side only, `submit()` neither checked nor stored anything, and any direct API call bypassed it silently. The only persisted consent was `User.consent_given` — one boolean, set once at signup (FR-M6-06) — which records that a person accepted the terms, not that *this disclosure* was submitted under them. **Carve-outs, named rather than smoothed over:** (1) the migration is additive and deliberately **does not backfill** — pre-existing submitted records keep `dpa_accepted_at = NULL`, because stamping them would fabricate consent that was never given; those records are identifiable by that null. (2) **No `AuditEvent` is written**, since `AuditEvent` still has no workflow event types — that is IR-144, blocked on IR-138, and pre-empting its shape here would be guessing. The timestamp on the record is the evidence for now. (3) What the notice *says* is a separate, open problem: **IR-214** (signup consents to a ToS and Privacy Policy that do not exist) and **IR-123** (the RA 10173 text describes processing IRIS does not perform, flagged `needs-human-review`). This row covers whether acceptance is recorded, not whether the words are right — **a DPO still has to rule on those two before any real-participant validation**
