# IR-873: Version comparison and the Changes tab

**Requirements:** FR-M5-01 (a stable label only). The rule is [ADR-058](../../adr/058-each-version-keeps-its-text-and-its-files.md) §3 as amended 2026-11-08 (both sides read by one reader), and its IR-873 build notes.

Built in two parts. **This file covers part 1, the backend.** Part 2, the Changes tab, follows in its own PR.

What changed:

- **The comparison** (`apps/reviews/comparison.py`) is pure: two readings in, a comparison out, no database. Sections pair by heading key, then by content when renamed. Passages match exactly, then a reworded one pairs by similarity (`difflib`), and any difference left is *changed* with the differing words marked. A passage removed in one place and added word for word in another is *moved*. When a side's sections couldn't be identified it compares by page, and when the amount of text looks wrong it says so and marks the changes that could be missed text as `tentative`. It also compares documents (IR-872's rows) and offers `appears_in` for IR-876.
- **One reader on both sides** (`apps/records/review_text/readings.py`): a comparison sets two readings by the current reader side by side. A Version read by an earlier reader is read again from its own file, and that reading is stored beside the original, which the Version keeps pointing at. If the current reader fails on a side, the newest reader both already share is used, else the comparison is unavailable and the read is retried next time. Submitting a Version queues the current reader for the paper's earlier Versions.
- **Storage** (migration `records/0037`): `ReviewText.requested_reader`, and one reading per file per reader, unique.
- **The endpoint:** `GET /records/<id>/versions/compare/?from=N&to=M` under `may_read_review` (404 otherwise), audited, `Cache-Control: private, no-store`. Without a pair it compares the Version this reviewer last finished a review on → latest, or previous → latest. `state` is `ready`, `preparing`, `unavailable` or `no_text`, each with its message. The access matrix has a `record-version-compare` entry.
- **The reader is never named:** the text endpoint's `reader` field is removed, and no comparison response carries one.

**Evidence**

- `apps/reviews/test_comparison.py` (25 tests, pure, run on Windows): each pair is two PDFs drawn with reportlab and read by the real reader, with one known edit and its expected result:
  - unchanged: the same paper, and another typesetting of it (page size, running head, page-number position)
  - a changed number, a rewritten sentence, an added and a removed paragraph, a paragraph moved to another section, a renamed heading, an edited table row, a changed reference, a section moved whole: each reported as exactly that edit
  - a one-character change reads *changed* with that word marked; a section with a new heading and new text is removed plus added, never forced into a rename
  - a hyphen between letters is no change, one between digits is
  - by-page comparison when sections couldn't be identified, and *may be unreliable* with tentative removals when text shrinks on the same pages
  - the same two readings give the same result, with `COMPARISON_VERSION`
  - `appears_in` inside and across passages; documents unchanged, replaced, added or removed
  - the comparison's normalisation equals the reader's
- `apps/records/test_review_text_readings.py` (14 tests, database), with a newer reader simulated:
  - readings by the current reader are compared as they are, with no new reading
  - a newer reader reads both Versions again beside their originals, which are unchanged and still the Versions' own
  - asking again adds nothing; a failure falls back to a shared reader, or is unavailable and retried
  - submitting queues the same reader for earlier Versions; a Version with no text is no text whatever the reader
  - the endpoint: a ready comparison, *preparing*, *no text*, the default pair, refusals with a reason (400), a 404 for anyone the review refuses, and no response naming a reader
  - the web side names the reader exactly as the reader does
- Run 2026-11-08 on Windows against a throwaway pgvector container: the two files above, `test_review_text.py`, `test_review_text_reader.py`, `test_review_text_isolation.py`, `test_record_versions.py`, the access matrix and the enum vocabulary all pass. `test_new_version.py` has 8 failures, the same 8 on an untouched `main` (Windows refuses PDF uploads: no `resource` module).
- **Migration `records/0037` on a copy of the dev database** (18 Records, 18 Versions, migrated from `records/0021`), with one read and one unread review text added: the read text got its reader as `requested_reader`, the unread one stayed blank, the unique index exists, and it reverses and applies again.
