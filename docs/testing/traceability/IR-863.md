## IR-863 — Ask IRIS opens runtime runs behind a per-deployment switch

**Basis and scope.** IR-863 under IR-714; authority ADR-049. IR-730 built the `runs-reader-1` reader (`RuntimeReader`, the same-origin edge in `frontend/nginx.conf`) but switched it with a build-time flag baked into the JavaScript bundle (`VITE_AI_RUNTIME_READER_ENABLED`). This ticket makes the path a server-side deployment decision that the browser reads and cannot override, gives the reader distinct refused, busy, unavailable and not-found states, and adds an authenticated end-to-end test. Paper Chat migration, compaction (IR-754) and the production traffic switch (IR-742) are out of scope.

**Code.**
- **The switch** (`backend/config/settings/base.py`). `AI_RUNTIME_READER`, a boolean, `False` by default. `GET /api/v1/ai/reader/` (`ReaderPathView`, `apps/ai/views/grants.py`) answers `{"path": "runtime"}` or `{"path": "django"}` from that setting alone, `no-store`, to any signed-in reader.
- **The edge refuses while it is off.** `RuntimeEdgeGrantView` answers 403 before issuing anything when the switch is off. That is the status nginx's `auth_request` passes on, so the proxied `/api/v1/ai/runtime/…` routes refuse a browser that tries them on its own. No route, port or CORS rule is added; the reader still uses IR-730's proxy.
- **The browser reads it** (`frontend/src/api/runtimeReader.ts`). `useReaderPath()` reads `/ai/reader/` once per page load. If the read fails it falls back to Django, the path that answered before the switch existed, and the failure is not remembered. Ask IRIS (`RAGChatPage`) and Paper Chat (`PaperChatPanel`) mount neither path until the switch is known, so the Django page's requests are exactly what they were. Paper Chat keeps the composition IR-730 gave it, now under the same switch rather than a second one.
- **Reader states** (`RuntimeReader.tsx`):
  - busy (503 `busy`, 429) and unavailable (other 5xx): each has its own message, and both offer Reconnect;
  - refused (403) and an ended session (401): each has its own message, and neither offers Reconnect;
  - a conversation that can't be opened (404): offers *Start a new conversation*;
  - a protocol mismatch: asks the reader to reload.
  
  Cancelled, expired and failed runs keep IR-730's run states. A request that can't succeed is no longer kept for Reconnect. The mistake/citation notice stays in the composer throughout.
- **Deployment.** The build arg and the baked `/etc/nginx/iris/runtime-reader-enabled` file are gone. nginx's entrypoint now reads `AI_RUNTIME_READER` from its environment and still refuses to start when it is on without `AI_GATEWAY_SERVICE_SECRET`. `docker-compose.prod.yml` passes the repo-root `.env` value to both `backend` and `frontend`, so Django and nginx read one setting. CI's nginx step and `scripts/check_django_admin_allowlist.sh` no longer mount the file.

**Tests.**
- `backend/apps/ai/tests/test_runtime_reader_edge.py`: the switch alone names the path; a `?path=` or header sent by the browser changes nothing; off means the edge issues no grant (403). The two IR-730 tests now turn the switch on, because the edge serves only then.
- `backend/apps/ai/tests/test_runtime_reader_e2e.py`, on real PostgreSQL with the restricted runtime login:
  - an authenticated reader takes the edge grant from Django exactly as nginx asks for it, submits through the gateway, and the recording provider plans, searches two papers and cites both;
  - the answer is followed, delivered and reopened with a fresh grant, as after a reload;
  - status equals the live response, the reopened Conversation equals the delivered one, and the citations keep paper order;
  - every projection carries only allowlisted keys, with no reasoning, tool arguments, provider IDs or reason codes;
  
  The normalized public projections are committed as `frontend/src/test/fixtures/runtimeReader.recorded.json`. The test fails if what the server serves drifts from that recording. Regenerate it with `IRIS_WRITE_READER_RECORDING=1`.
- `frontend/src/features/ai/RAGChatPage.runtime.test.tsx` replays that recording through the Ask IRIS page via the accessible tree:
  - the question is delivered with its plan, *Answer ready*, the mistake notice and both citations in order;
  - the address moves to the conversation;
  - a reload of that address shows the same text and citations;
  - every runtime request goes to `/api/v1/ai/runtime/…` with `runs-reader-1` and no grant or service secret of the browser's own;
  - busy, unavailable and refused submissions each show their own state, and only busy and unavailable offer Reconnect;
  - a conversation that can't be opened offers a new one;
  - Stop operated by keyboard shows *Stopped*;
  - axe-core passes at serious/critical on every state.
- `frontend/src/features/ai/RAGChatPage.switchOff.test.tsx` covers the switch-off snapshot. Every request Ask IRIS makes to open and ask one question was recorded at the wire (axios adapter and `fetch`) from the page **before** this change, then left unchanged after it. The one added request, reading the switch, is asserted separately.
- `apps/tests/test_access_matrix.py` declares `ai-reader-path` as signed-in, and runs the AI routes with the switch on so the edge-grant row keeps testing who it authenticates.
- Changed deliberately: `RuntimeReader.test.tsx`'s busy case now rejects with the gateway's real `503 {"status": "busy"}` instead of a bare `Error("busy")`. The Django-path suites (`RAGChatPage.test.tsx`, `PaperChatDock.test.tsx`, `PaperViewPage.test.tsx`) pin `useReaderPath` to `django` instead of reaching the network.

**Evidence (2026-11-04).** Backend tests ran in a container built from the backend image with `requirements/development.txt` and `ai/requirements.txt`, against a throwaway `pgvector` Postgres and Redis. There is no local venv. The full backend and frontend suites, lint, build and the Compose and nginx CI jobs are left to CI; their result is the remaining evidence.
- `test_runtime_reader_edge.py`: 5 passed. `test_runtime_reader_e2e.py`: 1 passed.
- The access-matrix AI rows and the route-declaration tests passed.
- Frontend: 730 tests in `src/features/ai`, `src/features/records/paper-view` and `src/api` passed, and `tsc` is clean.
- nginx (`nginx-unprivileged:1.25-alpine`, real config and entrypoint):
  - `AI_RUNTIME_READER=true` with no secret refused to start;
  - with a test secret, and unset, `nginx -t` passed;
  - `scripts/check_django_admin_allowlist.sh` passed.
- `docker compose -f docker-compose.prod.yml config` passed; one root `.env` value reached both `backend` and `frontend`.

**Not done here.**
- The ticket's independent demonstration on a development stack wasn't run. `docker-compose.yml` serves the frontend from Vite, not nginx, so the `/api/v1/ai/runtime/…` edge exists only under the production Compose file.
- No paid provider was called; the recording provider proves the contract, not capacity or answer quality.
- Enabling the switch on a real deployment needs IR-861's recorded limits and a person's approval.
- The reader polls status once a second (IR-730); there is no push.
- A reader's numeric legacy Conversations still open on the Django page when the switch is on; they are not migrated. Django's `/ai/ask/` routes are not closed while the switch is on, so the switch decides which path the reader UI uses, not which one the server will answer.
- The end-to-end test joins its halves through the committed recording. Django's edge grant, the gateway and PostgreSQL run in one backend test, and the page replays what they served. No single test runs browser, nginx, Django and gateway together, and nginx's `auth_request` is checked by configuration (`nginx -t`), not by a request.
- The snapshot pins the requests Ask IRIS sends, with responses stubbed. Paper Chat's switch-off requests are covered by its existing suite, not by a snapshot.
- Paper Chat follows the same switch, as it followed IR-730's single build flag. Keeping Paper Chat on Django while Ask IRIS moves would need a second switch.
