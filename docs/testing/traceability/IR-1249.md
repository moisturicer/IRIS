## IR-1249

**Requirement:** The reference lists (classifications, PSCED codes, record types, colleges) are fetched once per session and shared, not on every visit, and forgotten on sign-out

**Design:** Jira IR-1249, from the local performance investigation (Ashlee Sean, 2026-11-20). Two corrections to the ticket's list:

- `records/interests/` is the reader's own, editable interests, so it is not cached.
- `records/facets/` (publication years) changes with every publication, so it is not cached either, as the ticket already said.

All four cached lists are `objects.all()` with no per-user filtering (`apps/records/views_reference.py`, `CollegeListView`), so no account can see another's. Setup cannot change them: the public record-type list is `id` and `name`, and Setup edits descriptions, templates and requirements through its own endpoint, so no invalidation hook is needed. An edit made in Django admin shows after a reload

**Implementation:**

- `frontend/src/api/referenceLists.ts` (new), `once(key, load)`:
  - Concurrent callers share the request in flight.
  - A failure is not kept.
  - Each caller gets its own `structuredClone` of the data.
- `forgetReferenceLists()` clears it.
- `recordsApi.classifications()` (whole list only; a paged request is not kept), `recordsApi.pscedList()`, `recordsApi.recordTypes()` and `accountsApi.colleges()` go through it. None of the six calling screens changed.
- `auth.store` `logout` calls `forgetReferenceLists()`, and `test/setup.ts` calls it after every test.

**Test:** `frontend/src/api/referenceLists.test.ts` checks:

- Each of the four lists is requested once for two concurrent calls and a later one.
- Each caller gets its own copy.
- A failure is retried.
- A paged classifications request is never kept.
- Sign-out forgets every list.
