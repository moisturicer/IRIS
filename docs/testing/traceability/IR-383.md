## IR-383

**Requirement:** **Question resolution runs as its own Inference task, on a model that exists** — no FR- id; part E of IR-375's spec, and the ticket that closes the two-namespace contradiction IR-378 recorded

**Design:** [ADR-036 §Amendment](../../adr/036-openai-compatible-inference-provider.md) (vendor and model chosen **per Inference task**) · [ADR-026 Decision 8](../../adr/026-conversational-retrieval-and-memory.md) (each enhancement technique independently switchable, so retrieval quality with and without it stays measurable under ADR-023)

**Implementation:** `apps/ai/composition.py` — `resolver()` builds its `QuestionResolver` over `llm_for(InferenceTask.RESOLVE)` instead of constructing a bare `OpenAICompatibleAdapter` on `LLM_RESOLUTION_MODEL`, so a withdrawn model is now caught by IR-379's startup check rather than by a reader's follow-up · `apps/ai/inference/profiles.py` — `resolve` joins `answer` in `_INHERITED_KEYS`, but inheriting the flat **vendor account only** (`LLM_BASE_URL`, `LLM_API_KEY`) and never the flat model: resolution has shipped since IR-296 over that account so it must keep working with no new configuration, while borrowing `LLM_MODEL` would send every rewrite to the expensive answer model · `config/settings/base.py` — `LLM_RESOLVE_MODEL` ships a default and `LLM_RESOLUTION_MODEL` is **deleted**; unlike `summary`, `resolve` is not off when unset, because switching it off is `AI_QUESTION_RESOLUTION_ENABLED` and that switch is unchanged · `apps/ai/inference/startup.py` — `RESOLUTION` moves out of `RESERVED_SEGMENTS` into a new `RENAMED_SEGMENTS`, so a leftover `LLM_RESOLUTION_MODEL` refuses startup with the rename in the message instead of being silently ignored; ignoring it is precisely how the withdrawn model would survive a redeploy · `frontend/src/features/ai/components/PassageQuote.tsx` — `ResolvedQuestionNotice`, rendered by `ChatMessageBubble` from a new `ChatMessage.resolvedQuestion` populated in `lib/chatMessages.ts` (replay) and `useAskStream.ts` (live). **A real gap found rather than assumed**: `resolved_question` had reached the wire and the TypeScript types since IR-296 but **no component rendered it**, so the "stays visible to the reader" criterion was not in fact met before this change and is met by new code, not by leaving something alone. **The default model was chosen by calling the vendor, not by reading a changelog**: `llama-3.1-8b-instant` returns HTTP 404 `model_not_found` at Groq and `openai/gpt-oss-20b` returns 200

**Test:** `apps/ai/inference/tests/test_profiles.py::ResolveProfileTests` (5 — the shipped model, independence from `answer`'s, the vendor account inherited while the flat model is not, a named vendor dropping the inherited key, and no reasoning configuration sent) · `apps/ai/tests/test_resolver_wiring.py` (5, new — `resolver()` reaches the `resolve` model while a different `answer` model is configured; the shipped default; reasoning suppressed with `LLM_REASONING_EFFORT=high` set; the off switch still returning `None`; an unconfigured `resolve` degrading to `None` rather than raising) · `apps/ai/inference/tests/test_startup.py` (+1 — the retired namespace refused, naming `LLM_RESOLVE_MODEL`) · `frontend/.../ChatMessageBubble.test.tsx` (+2 — the standalone question shown, and nothing shown when the question was searched as typed) · the 7 pre-existing `test_resolution_http.py` cases and 16 `test_resolution.py` cases **unchanged**, which is the "existing resolution tests pass unchanged, driven by scripted fakes" criterion

**Evidence:** `apps/ai/inference apps/ai/tests/test_resolution*.py apps/ai/tests/test_resolver_wiring.py` → **82 passed**. Full backend suite **1828 collected, 2 failed** (2026-09-28) — both are the pre-existing environmental `test_llm_contracts.py` failures IR-378 and IR-393 already record (they read the developer's own `backend/.env`: `LLM_TEMPERATURE=1`, `LLM_REASONING_EFFORT=high`) and neither is on a path this change touches. Frontend `npm test` → **424 passed, 49 files**; `tsc --noEmit` clean; `npm run lint` 0 errors. **Verified against the live vendor during development, not only against fakes**: driving the real `CompositionRoot().resolver()` with the project's Groq key, the history "What does the CNN leaf-disease paper conclude? / It reports 94% accuracy" and the follow-up "what about its limitations?" produced "What are the limitations of the CNN leaf-disease paper that reports 94% accuracy on leaf disease classification?", on `openai/gpt-oss-20b` with `reasoning_effort == ""`. The same run with `LLM_RESOLVE_MODEL=llama-3.1-8b-instant` logged the 404 and returned `None` — retrieval then searches the question as typed, which is the degradation criterion

**Status:** **IMPLEMENTED** — `resolve` is wired, independently configurable, reasoning-free, and the two live namespaces IR-378 recorded are now one. Deleting `llm()` is IR-388
