## IR-1049

**Requirement:** A new version that was saved is never reported as a failure. Work after the commit cannot turn a successful submit into a 5xx, whatever it fails to do is still done or can be done again, and the dialog never invites a retry that can only be refused. Follows IR-273 (ADR-003's clearance-aware resubmission); no FR- id.

**Design:** Jira IR-1049. Decided 2026-11-15: Hermoine Zozobrado was asked and left these open, so the defaults below were taken and sent to her:

1. **Every step after the commit is `robust`.** Celery already retries a failed publish (`task_publish_retry`, on by default: three tries within about a second). A step that still raises is logged by Django (`django.db.backends.base`, ERROR, with its traceback) and the steps after it still run.
2. **Recovery uses what exists; no new scheduled job.** A lost manuscript read leaves its `PdfExtraction` row `queued` for `reextract_manuscripts --record N`. A lost review-text read is sent again when the comparison is opened (`readings._requeue_if_lost`). Threads are placed again after each reading. The reviewers' notices need no queue.
3. **The shared helpers too**, not only the new-version path: `documents.sources.reset_manuscript` and `queue_upload_read` (Publish, uploads, releases) and `review_text.store.attach` / `readings._queue` (every Version and comparison).
4. **The dialog checks before it speaks.** After a failure the server gives no reason for (a 5xx, a gateway timeout, a dropped connection), it reads the record again: the version is there, so the owner sees the normal "v*N* submitted…" message; it is not, so the page shows the record as it stands, with "Please try again." only while a revision is still asked for; the record cannot be read either, so the owner is asked to reload before trying again.

**Cause (suspected, not confirmed).** The server's logs for 2026-11-13 were not read: the server was stopped, and each deploy since then has rebuilt the backend container, which discards its logs. In the code, five steps ran after `submit_new_version` committed, inside the request, and four could raise: queueing the review-text read, preparing earlier Versions' readings, placing the threads, and queueing the manuscript read. A Celery publish that failed in any of them raised out of the commit, so `POST /records/<id>/new-version/` answered 500 with v2 saved, and every step after it was skipped, the reviewers' notices included. A proxy timeout or a failure building the tracker would look the same to the owner; the dialog's re-read covers those.

**Implementation:**

- `backend/apps/reviews/new_version.py`: `place_review_threads` and `notify_new_version` run with `robust=True`; the module note says why.
- `backend/apps/records/review_text/store.py` and `readings.py`: the review-text read and `prepare_earlier`, `robust=True`.
- `backend/apps/documents/sources.py`: the manuscript read and both supporting-document reads, `robust=True`.
- `frontend/src/features/records/paper-view/NewVersionDialog.tsx`: on a failure with no `detail`, `recordsApi.detail` decides what to say; a new `onRefreshed` prop hands the re-read record to `PaperViewPage`, which shows it.

**Tests:**

- `backend/apps/reviews/test_new_version.py::SavedVersionIsReportedSavedTests` (an `APITransactionTestCase`, so the commit is real and post-commit work runs inside the request, as in production): with every Celery publish refused, `new-version/` answers 200 with the tracker, v2 exists and the request is resolved, and the failures are logged; IERC's reviewer is still notified, the extraction row waits `queued` on v2's revision, and v2's review text waits `pending`.
- `backend/apps/documents/tests/test_queue_down.py`: a manuscript read and a supporting-document read that cannot be sent leave the row `queued`, log the error and raise nothing.
- `frontend/src/features/records/paper-view/NewVersionDialog.test.tsx`, "a failure the server gives no reason for (IR-1049)": a 500 and a 504 with the version saved report it submitted, with no error; not saved, the error invites a retry and the page gets the re-read record; no revision asked for any more, no retry is suggested; the re-read failing asks for a reload; Submit and Cancel stay busy while it checks. The refusal test now also asserts no re-read when the server says why.
