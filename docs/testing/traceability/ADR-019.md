## ADR-019

**Requirement:** **Persisted conversation history** — no FR- id exists for this; [ADR-019](../../adr/019-persisted-unified-conversation-history.md) is the requirement, and ADR-019 §Related Requirements says so explicitly

**Design:** **ADR-019** (one Conversation model, both surfaces, persisted history), amended by IR-294 §A stored citation is a pointer

**Implementation:** **IR-295 (part A):** `apps/ai/models/conversation.py` — `Conversation` (one `User`, optional `Record`, CASCADE), `Turn` (question + answer + state, stored together) and `TurnCitation` (record, chunk, page — **no text**), replacing the two field-less `pass` classes migration 0001 created and nothing ever wrote to; migration `0008_conversations_and_turns`. `POST /ai/ask/` takes an optional `conversation_id` and appends a Turn; `GET/POST /ai/conversations/` and `GET/PATCH/DELETE /ai/conversations/<pk>/` list, read, rename and delete. Every queryset is scoped to `request.user` by `views/conversations.py::_owned` — **scoped, not permission-classed**, so a refusal is a 404 identical to a missing row (the IR-153 shape). `conversations.py::turns_for_reader` re-checks every stored citation against `Record.objects.visible_to(user)` on each read, so a pointer into a Record the reader lost access to is dropped rather than rendered. The wire's answer-state mapping moved to `presentation.py` so a replayed Turn and a live answer cannot drift. `Turn.state` stores the **domain** state and is mapped to the wire on read, so renaming an API string cannot reinterpret old rows. `record` is set when a Conversation starts and is not writable afterwards. **IR-296 (part B):** `apps/ai/resolution.py` — `QuestionResolver.resolve(question, turns)` rewrites a follow-up into a standalone question before retrieval runs, guarded by `has_back_reference` (a cheap word check, no model call) and returning `None` outright with no history at all; a failed model call is caught (`LLMUnavailable`) and also falls back to `None` rather than erroring — both fall back to the raw question, exactly as before this ticket. `Turn.resolved_question` (migration `0009_turn_resolved_question`) stores what actually ran, blank in every fallback case. `views/chatbot.py::ChatQueryView` resolves *above* the retriever — `GroundedAnswerService.answer()` and the `Retriever` port are unchanged, per IR-294's Testing Decisions ("No new seams. Resolution is a module, not a port...") — and both retrieval and synthesis run on the resolved question when one exists; the raw question is still what is stored and shown as `question`. `composition.py::CompositionRoot.resolver()` is the independent switch (`AI_QUESTION_RESOLUTION_ENABLED`, `None` when off) and the separate, smaller model (`LLM_RESOLUTION_MODEL`, sharing `LLM_BASE_URL`/`LLM_API_KEY` with the answering model per ADR-036's one-adapter shape). The cache is Django's default cache, keyed like the query-embedding cache in `resilience/query_cache.py` (question + the resolved history's Turn ids, normalized and hashed) — wired directly here rather than deferred, because resolution needs no `EmbeddingSpace` id at construction, unlike that cache. **IR-297 (part C):** `apps/ai/memory.py` — `ConversationMemory.recall(conversation, query_vector, space_id, exclude_ids)` finds Turns from earlier in a Conversation relevant to the question just asked, by `CosineDistance` over `TurnEmbedding` rows scoped to that Conversation and that `space_id` — never a second implementation's job, a module like `resolution.py`, for the identical reason (IR-294 Testing Decisions: one implementation, no vendor at all, fully exercisable through HTTP). `TurnEmbedding` (migration `0010_turn_embedding`) mirrors `ChunkEmbedding`'s shape exactly, keyed on `(turn, space)`, so a vector from a retired space is never compared against a current one. **The memory vector is the search vector**: `RetrievalResult` and `GroundedAnswer` both grew a `query_vector`/`embedding_space_id` pair carrying the embedding `TwoStageRetriever` already computed to search the corpus, and `conversations.py::record_turn` writes it onto the new `TurnEmbedding` — no second `embed_query` call, pinned by a call-count assertion. `answers/citations.py::build_prompt` gained `history` (the Conversation's recent Turns, verbatim, bounded by the same `resolution.MAX_HISTORY_TURNS` window resolution already uses) and `recalled` (memory's finds, labelled separately, in full — **nothing is summarised**); `GroundedAnswerService.answer()` takes the Conversation and its recent Turns and only ever calls memory when both a Conversation and a configured `memory()` collaborator exist. `composition.py::CompositionRoot.memory()` is the independent switch (`AI_CONVERSATION_MEMORY_ENABLED`, `None` when off) — unlike the resolver, this collaborator never calls a vendor, so there is no key that could be missing. A missing query vector (a degraded, full-text retrieval, or no active space) degrades recall to `[]` with a logged warning rather than raising, so a Conversation whose vectors are unavailable falls back to the recent-Turns window it already had. **IR-298 (part D):** Paper Chat is a Conversation that happens to have a Record attached, same models and same API as Ask IRIS — the title-prefix scoping hack (`aiApi.ask(\`${record.title}. ${question}\`)`) is gone from `PaperChatDock.tsx`. Retrieval scoping stays out of the `Retriever` port on purpose (IR-294 story 31): `TwoStageRetriever` and `FullTextRetriever` (`retrieval/degraded.py`) each take an optional `record` at **construction**, narrowing `visible_to(user)` to that one Record before anything is scored rather than instead of it — a Record can stop being readable after a Conversation was scoped to it, and both retrievers re-check on every call. `composition.py::CompositionRoot.retriever()`/`answer_service()` gained a call-time `record` parameter that builds a differently-scoped stack per request; the `Retriever.retrieve(question, user, limit)` signature itself is untouched, so this is not the fourth-implementation-widening ADR-026 warns against. `views/chatbot.py::ChatQueryView` reads an optional `widen` flag: scoped by default when the Conversation carries a Record, unscoped only for the one question that asked to widen — never remembered onto the next question, asserted by `test_widening_is_a_per_question_choice_not_a_standing_one`. `Turn.widened` (migration `0011_turn_widened`) stores which scope actually produced each answer, and the `ask` response's `widened` field and `ConversationListCreateView`'s `?record=` filter (for "does a conversation already exist for this paper") are new. **Frontend:** `lib/chatMessages.ts` (`newChatMessage`, `turnToMessages`) is the one mapping from a live answer or a replayed Turn to the `ChatMessage` shape both `RAGChatPage.tsx` and `PaperChatDock.tsx` render through `ChatMessageBubble` — Ask IRIS and Paper Chat now read and write the same Conversations through the same API, with no second chat system. `lib/chatStorage.ts` and `buildRagQuestion` (the question-concatenation helper) are deleted, along with `types/chat.ts`'s local `Conversation` type; `RAGChatPage.tsx` lists, creates, selects and deletes Conversations through `aiApi.conversations`, and a question is sent as itself — no transcript gluing. A replayed citation carries only its pointer (record, chunk, page) until IR-299 re-resolves the quote, so `ChatMessageBubble`'s `PassageCitation` and `SourceContextPanel` render a bare link rather than a blank quote when `text`/`record_title` are absent. `PassageQuote.tsx::ScopeNotice` is the one place a widened answer says so, live or replayed. A dismissible notice (`RAGChatPage.tsx`) explains the sidebar emptying when a browser still holds the pre-IR-298 `iris_rag_conversations` key, and clears it on dismissal — old local chats are not migrated (IR-294 §Further Notes: demo and testing conversations against a stub corpus). **Post-review fixes (2026-09-22, same commit range):** the `"text" in citation` quote-presence check was duplicated between `ChatMessageBubble.tsx` and `SourceContextPanel.tsx`; both now call one `hasCitationQuote()` in `lib/citedPage.ts`. `aiApi.conversations.rename` was speculative — added for CRUD completeness, called from nowhere — and is removed; nothing in this ticket needs renaming a Conversation. Paper Chat's find-the-conversation-or-start-one sequence (`list` → `get` or `create`) moved out of `PaperChatDock.tsx`'s effect into `aiApi.conversations.findOrCreateForRecord()`, which owns the decision instead of the component reaching into three separate calls. `RAGChatPage.tsx`'s `?record=` deep link created a scoped Conversation and displayed the prefilled question as an inert user bubble that was never actually asked — a real bug, not merely a smell — since Conversations no longer live in `localStorage` where the old code at least persisted the same half-finished state; `sendQuestion()` (shared by this path and `handleSend`) now actually calls `aiApi.ask` for it, so the deep link lands on a real, stored answer. **IR-299 (part E):** `conversations.py::turns_for_reader` re-resolves each stored citation against two batched lookups for the whole transcript, not one pair per citation — which cited Records `Record.objects.visible_to(user)` still allows, and which cited chunks are still live (`DocumentChunk.objects.filter(deleted_at__isnull=True)`; re-chunking tombstones a chunk rather than deleting the row, IR-115). The new `_resolve_citation` helper returns `None` for a Record the reader may no longer see (dropped, unchanged from IR-295 — existence must not leak), the full `Citation` shape (`text`, `record_title`, `page`, `context_path`, all read live off the chunk, never the stored `page` column) when the Record is visible and the chunk is live, and a bare pointer (`marker`, `record_id`, `chunk_id`, `page` from the stored column) when the Record is visible but its chunk was tombstoned — a record-level link rather than a stale or fabricated quote, exactly the degradation IR-294 §Acceptance asks for. No frontend change: `hasCitationQuote()` (`lib/citedPage.ts`) already branched on `"text" in citation`, so a replayed Turn whose citations now carry `text` renders the quote through the exact code path a live answer already used
