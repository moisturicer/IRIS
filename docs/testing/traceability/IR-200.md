## IR-200 — Recreating the backend container no longer breaks the API through nginx

Defect 2 (the sign-in page blaming the password) moved to IR-533 and was fixed by IR-536. This covers Defect 1.

**Cause.** `proxy_pass http://backend:8000;` with a literal host makes nginx look `backend` up once, when it loads, and keep that address. A recreated backend container gets a new address, so every API call failed until nginx restarted.

**Fix.** `frontend/nginx.conf` and `frontend/nginx.dev.conf` set Docker's resolver (`127.0.0.11`, answers reused for 10s) at server level. Every backend location, and the Ask IRIS grant subrequest in `runtime-edge.conf`, proxies to `$iris_backend`, which makes nginx look the name up again instead of pinning it. nginx now also starts with no backend running. When several containers answer to `backend`, nginx takes turns between them, which is what a later backend-replica change would rely on.

`scripts/deploy.sh` no longer restarts `frontend` after every rebuild. It restarts it only when the page answers and the API doesn't, and says so ("restarted frontend (IR-200)"), so each deploy's output shows whether the fallback was still needed. `deploy/tests/deploy_checks.sh` covers a healthy rebuild (no restart) and a stale API after a rebuild (one restart, then success).

## Hand checks, 2026-11-15

Run by Claude Code at Ashlee Sean's direction, on Docker Desktop (Windows), with stand-in containers in place of Django and Vite. Local only: not the iris-demo server.

1. **Dev edge (`nginx.dev.conf`), set up as `docker-compose.yml` runs it.** `/api/`, `/static/` and `/django-admin/` reached the backend stand-in (200), and `/` reached the Vite stand-in (200). The backend stand-in was replaced by a new container at a new address, and after 11s `/api/` reached the new one with no edge restart. **Pass.**
2. **Ask IRIS grant subrequest (`nginx.conf` + `runtime-edge.conf`).** A request to `/api/v1/ai/runtime/runs?after=3` with `Authorization`, `X-IRIS-Record` and `Accept: text/event-stream` made the backend stand-in receive `GET /api/v1/ai/runtime/edge-grant/`: no query string, the same Authorization and Record, `Accept: application/json`. Its 401 came back to the client as 401. Same as before the change. **Pass.**

3. **The ticket's own reproduction, on a local copy of the real stack.** A separate Compose project (`iris-ir200`, no published ports, so the other local stack was untouched) ran `db`, `redis`, `migrate`, the real Django `backend` (dev settings, `runserver`) and nginx with this branch's `frontend/nginx.conf`. Accounts came from `seed_demo --accounts-only`.
   - Sign-in as `student@iris.test` through nginx: **200**, backend at 172.21.0.4.
   - The backend was stopped, a placeholder container took its old address so Docker had to give it a new one, and `docker compose up -d --force-recreate --no-deps backend` ran. The backend came back at 172.21.0.6. Sign-in through the same nginx, never restarted (its start time unchanged): **200** after 12s. **Pass.**
   - Django's redirect for `/api/v1/colleges` (no slash) came back as `301 Location: /api/v1/colleges/`, a relative path, so losing `proxy_redirect default` with a variable upstream changes nothing.
   - **Control:** the same steps with `main`'s `nginx.conf` and `runtime-edge.conf`. Sign-in 200 before; after the recreate (172.21.0.6 → 172.21.0.5) **502**, still **502** 30s later; **200** only after restarting nginx. This is the defect as reported.
4. **`deploy/tests/deploy_checks.sh`** (fake docker): 78 checks passed, including the new rebuild-with-stale-API case. shellcheck clean on `deploy.sh`, `deploy_checks.sh` and the new check script.
