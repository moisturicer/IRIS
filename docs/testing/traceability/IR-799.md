# IR-799: RDCO publishes a new notice version by pasting it

[Back to the matrix](../TRACEABILITY.md)

**Requirements:** ADR-051 decisions 16 and 17, with ADR-054's single notice, **as amended by ADR-063 decision 9: only RDCO publishes.** The ticket was written when RDCO *or* the System Admin published. ADR-063 (accepted 2026-11-08) took publishing from the System Admin, and Hermoine Zozobrado's comment on IR-799 asked for this ticket to match. The ADR wins over the ticket's wording, so the System Admin is **refused** a publish here. It still lists every version, and it sees each publication in the Audit Log. IR-972 tracks the rest of that change. No FR- id. The notice's wording stays with IR-123.

**The model (`accounts/0022`):**

- `DataNotice.text`: a pasted version's whole text, plain, with its line breaks. Version 1 came from frontend code as structured `sections` and is left exactly as migration 0019 wrote it. `title` and `sections` now allow empty values, because a pasted version has neither. `display_text()` gives either shape as plain text, so the Notices page can start "filled with the current text" (decision 16), version 1 included.
- **A version never changes (decision 17).** `save()` already refused an edit. Now `delete()`, `QuerySet.update()` and `QuerySet.delete()` refuse as well. No route edits or deletes a version.

**The API:**

- `GET /auth/notice/versions/` (`notice-versions`), RDCO and the System Admin: every version, newest first, each with `published_by` (id, name, email; `null` for version 1, which a migration created) and `published_at`.
- `POST /auth/notice/versions/`, **RDCO only**, body `{based_on_version, text}`, answers **201** with the new version, which is current at once.
  - **Validation:** blank or whitespace-only text is a 400. So is anything over `notice.NOTICE_TEXT_MAX_LENGTH` (50,000 characters; version 1 as text is far under it, and a test checks). Line endings become `\n` and trailing whitespace goes. Nothing else changes: text is never parsed, rendered or sanitized, so `<script>` is stored and returned as those characters in a JSON string. Rendering it as text is the frontend's job.
  - **Two people at once:** a publish whose `based_on_version` isn't the current version is refused with **409 `notice_stale`** and the current notice, the same shape a stale answer gets. The check runs under a row lock on the current version, and the unique version number backs it up.
- `GET /auth/notice/versions/impact/` (`notice-impact`), RDCO only: `{current_version, accounts_to_answer}`. The count is every live account (`is_active`, not deleted). Nobody can have answered a version that isn't published yet, so everyone live has to answer.
- `GET /auth/notice/` (public, unchanged access) now also carries `text`. For a pasted version it fills `title` ("Data notice") and puts the whole text in one untitled section, so today's screens show it before IR-800 moves them to `text`.

**Publishing isn't answering.** `publish_notice` never writes the publisher's answer. The new routes aren't in `ALLOWED_WHILE_UNANSWERED`, so the publisher is blocked like everyone else until they answer the version they published. A second RDCO who started from the old version is blocked first by the new notice. Once they've answered, their paste is still refused as stale.

**Audit:** `NOTICE_PUBLISHED` (`audit/0022`, choices only), written in the publish's transaction. `user` is the publisher, and the metadata holds `notice_version`, `previous_notice_version`, `characters` and `sha256`, never the text. It's added to `docs/evaluation/AUDIT_EXPORT.md` and labelled in `frontend/src/types/audit.ts`, which `AuditLogPage.test.tsx` requires for every backend type.

**Authorization matrix:** `notice-versions` GET is `ACCOUNT_ADMINS` (RDCO and the System Admin), POST is `RDCO_ONLY`, and `notice-impact` GET is `RDCO_ONLY`, in `apps/tests/access/table.py`. `test_notice_block_every_route.py`'s lists are unchanged, because none of these routes stays open before someone answers. The sweep covers them from the table on its own.

**A test that changed because behaviour did:** `test_notice.py::test_no_notice_yet_blocks_nobody` deleted every version with `DataNotice.objects.all().delete()` to stand in for a database with no notice. A queryset delete now refuses, so the test uses `_raw_delete`. What it asserts is unchanged.

**Tests:** `apps/accounts/test_notice_publish.py`, at the HTTP boundary with real tokens (21 tests):

- RDCO publishes: the next version, current at once, line breaks kept.
- A pasted version still reaches the screens that render sections.
- HTML comes back as the characters pasted.
- Blank and oversized text are refused, and the limit itself is accepted.
- Version 1 as text fits the limit.
- A stale publish is refused, and so is a version newer than any published.
- Publishing isn't answering: the publisher is blocked until they answer, then let through.
- The audit row, and no audit row on a refusal.
- Every other role (Student, Adviser, KTTO, ITSO, IERC, System Admin, role-less) gets 403 on publish, and an anonymous caller gets 401.
- PUT, PATCH and DELETE get 405, and there's no per-version route.
- RDCO and the System Admin list every version, with who published it and when. Every other role gets 403, and an anonymous caller gets 401.
- Anyone reads the current version, signed in or not.
- The impact count matches the live accounts and excludes inactive and deleted ones; it's RDCO-only.
- Model and queryset edits and deletes are refused.

The matrix rows cover every role again.
