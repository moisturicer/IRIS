## IR-924 — nginx names the character set on what it answers itself (ASVS 14.4.1)

Found by IR-829: the app's HTML, nginx's 404s and the `/django-admin/` refusal went out as bare `text/html`. The pages declare `<meta charset="UTF-8">`, so this was defence in depth, not an exploitable gap.

**Fix.** `frontend/nginx.conf` sets `charset utf-8;` at server level. `charset_types` replaces nginx's default list: it keeps `text/plain`, `text/xml` and `application/javascript`, and adds `text/css`, `text/javascript` and `image/svg+xml` (nginx always covers `text/html`). A proxied response that already names a charset keeps its own, because `override_charset` is off. JSON, PDFs and the Ask IRIS event stream are not in the list and are unchanged.

**CI.** The "nginx sends the browser security headers" step now checks that `/`, `/discover`, a script, a stylesheet, the SVG favicon, a missing asset (404), the activation path and the `/django-admin/` refusal (403) all carry `charset=utf-8`. The stylesheet and SVG are what fail if `charset_types` is removed.
